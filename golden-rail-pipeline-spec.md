# Build Spec: The Golden Rail Custom Goal Pipeline

## Context

Today, custom goals in `goalDecomposer.ts` are generated by Gemini in a single-shot pass, purely from model memory — no search, no verification, no cross-checking. Certified presets (the 10 hardcoded ones) are high quality because they're grounded in named, real methodologies (VDOT, Krashen, Helms, etc.) and never invented per-request.

This spec implements a pipeline that gives **every custom goal** the same grounding certified presets get — by researching the real, proven method for that goal live, verifying it, and only then writing the roadmap. Goals with no proven method get an honest fallback, not a fake badge of authority.

Do not silently deviate from this spec. If something below is ambiguous or conflicts with the existing codebase, stop and ask rather than guessing.

---

## Infrastructure Requirements

1. **Search provider: Tavily.** Use the `search` and `extract` endpoints. Do NOT use Gemini's native `googleSearch` grounding tool — it doesn't expose raw ranked results, so we can't apply our own trust-tier filtering or cross-source verification in code. We need raw JSON: `{ title, url, snippet/content, score }` per result.
   - Start on Tavily's free tier (1,000 credits/month) for development and initial testing.
   - Add a `TAVILY_API_KEY` env var.
2. **Vector similarity: pgvector.** Enable the `pgvector` extension on the Postgres database for embedding-based cache matching.
3. **Embeddings:** use `text-embedding-004` (or whatever embedding model is already available via the existing Google AI SDK) to embed clarified goal outcomes for cache lookups.

## Database Schema Changes

Add to `backend/prisma/schema.prisma`:

```prisma
model Goal {
  // ...existing fields...

  isGoldenRail        Boolean   @default(false)
  canonicalMethodName String?
  canonicalAuthority  String?
  canonicalSourceUrl  String?
  methodConfidence    String?   // "high_consensus" | "medium_consensus" | "first_principles"
  velocityTable       Json?     // Week 1 -> Week 12 metric matrix, derived from research
  canonicalKey        String?   // hierarchical domain key, e.g. "lang.japanese.jlpt_n3"
}

model ResearchCache {
  id              String   @id @default(uuid())
  canonicalKey    String   @unique          // e.g. "lang.japanese.jlpt_n3"
  outcomeEmbedding Unsupported("vector(768)") // pgvector column; adjust dims to match embedding model
  canonicalMethod Json     // { methodName, authority, sourceUrl, confidence, velocityTable, rawFindings }
  hitCount        Int      @default(1)
  userFeedbackScore Float? // populated once a feedback mechanism exists; nullable until then
  readyForPromotion Boolean @default(false)
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt
  lastUsedAt      DateTime @default(now())
}
```

Promotion threshold: flag `readyForPromotion = true` when `hitCount >= 10`. Do NOT gate promotion on `userFeedbackScore` until a real feedback-collection mechanism is built and shipped — until then that field stays informational only, not a gate condition.

## Pipeline Stages

### Stage 1 — Goal Clarification (existing, minor change)

Keep the existing `clarifyGoalWithAI` behavior (refine outcome, extract domain, sub-skills, diagnostic questions), with one addition: it must also emit a **hierarchical `canonicalKey`** string, dot-separated, e.g. `fitness.running.10k`, `lang.japanese.jlpt_n3`, `music.guitar.acoustic`. Add this instruction to the existing prompt:

```text
Additionally, output a `canonicalKey`: a lowercase, dot-separated hierarchical
domain key that uniquely identifies this goal's category, general enough that
close variants of the same goal (different phrasing, same underlying ambition)
would map to the SAME key. Format: <broad_domain>.<sub_domain>.<specific_goal>.
Examples: "fitness.running.10k", "lang.japanese.jlpt_n3", "music.guitar.acoustic_songs".
```

Add `canonicalKey: string` to the Stage 1 JSON schema.

### Stage 1.5 — Cache Resolution (NEW)

Before doing any research, check if this goal has already been researched:

1. **Tier 1 — exact key match:** `SELECT * FROM "ResearchCache" WHERE "canonicalKey" = $1`. If found, skip to Stage 4 using the cached `canonicalMethod`. Increment `hitCount` and update `lastUsedAt`.
2. **Tier 2 — embedding similarity fallback:** if Tier 1 misses, embed the `clarifiedOutcome` string and run cosine similarity against `outcomeEmbedding` in `ResearchCache`, threshold `> 0.88`, `ORDER BY similarity DESC LIMIT 1`. If a match clears the threshold, treat as a cache hit — same increment/update behavior, skip to Stage 4.
3. **Miss:** proceed to Stage 2.

### Stage 2 — Canon Research (NEW)

Only runs on a cache miss.

1. Generate 2-3 distinct search queries for the goal (vary phrasing — e.g. "X study method", "X proven approach", "X practitioner timeline"). Have the LLM generate these query variants from the clarified outcome, or template them; either is fine, but they must be genuinely distinct angles, not near-duplicates.
2. Run all queries against Tavily's search endpoint in parallel. Use `extract` on the top 3-5 result URLs per query to pull real content, not just snippets.
3. **Before any of this hits the LLM, run a blacklist filter in code** on the query strings and returned domains — reject queries/results matching known unsafe categories (crash diets, extreme fasting, high-leverage trading schemes, unregulated substances, etc. — build and maintain this list; it will always be incomplete, treat it as a floor not a ceiling).
4. **Trust-tier the results in code**, not in the prompt:
   - HIGH: named published authors/books, official certification bodies, accredited institutions
   - MEDIUM: large established communities/wikis with sustained track record
   - LOW: single-author blog posts, unverified forum comments, SEO content
   Use simple heuristics to start (domain allowlists for known authorities, .edu/.gov/.org weighting, etc.) — this doesn't need to be perfect on day one, but it must be deterministic code, not an LLM guessing at trust.
5. Feed the ranked, filtered results into an LLM synthesis call that:
   - Identifies whether 2+ independent HIGH/MEDIUM sources agree on a named method/authority
   - If yes: extract `methodName`, `authority`, best `sourceUrl` (must be a real URL from the actual search results — never let the model type one out), and set `methodConfidence: "high_consensus"` or `"medium_consensus"`
   - If sources disagree or nothing solid turns up: set `methodConfidence: "first_principles"` and skip method-naming — do not force an answer

### Stage 3 — Velocity Table Derivation (NEW)

Only runs when `methodConfidence` is `high_consensus` or `medium_consensus`.

Prompt the LLM to extract concrete numeric targets from the Stage 2 findings (not invent them):
- `week1Targets`: array of `{ metric, value, unit }`
- `week12Targets`: same shape
- `progressionFormula`: one sentence on how it ramps

If the goal has no natural numeric dimension, skip this — keep milestone ordering from Stage 2 instead, no fabricated numbers.

**Sanity check (in the same call or a follow-up):** verify week1 targets are less demanding than week12 targets, units are consistent and real, and the progression isn't a discontinuous jump. If it fails, regenerate once; if it fails twice, downgrade `methodConfidence` to `"first_principles"` and flag for later review rather than serving broken numbers.

### Stage 4 — Deterministic Safety Clamps (NEW — runs on ALL paths, cached or fresh)

After Stage 3 (or immediately after a cache hit retrieves a stored velocity table), run the generated/retrieved numeric values through hard-coded validation, in TypeScript, before anything reaches the task-writing stage:

- Endurance/running volume: week-over-week increase capped at 10%. Clamp, don't reject.
- Caloric deficit: hard-clamped between 250-600 kcal/day regardless of source.
- Resistance training: no compound lift scheduled at 100% 1RM or 0 RIR in weeks 1-3.
- (Extend this list over time as new risk categories are observed in production — this is a living list, treat any addition as improving coverage, not completing it.)

If a value is clamped, log it (goal id, original value, clamped value) for later review — don't silently discard the signal that the source data was pushing an unsafe number.

### Stage 5 — 12-Week Plan & Task Generation (existing `generate12WeekPlanWithAI`, modified)

Same structure as today (12-week periodization, daily tasks, 3 evidence layers, implementation intentions, challenge widgets) with these changes to the prompt:

1. Inject the velocity table / milestone data from Stage 3 (or cache) as **mandatory grounding** — every numeric value in `detailedSteps` must derive from it, not be invented per-step.
2. If `methodConfidence` is `high_consensus`/`medium_consensus`: instruct the model to use the real terminology, tools, and milestone names surfaced in Stage 2 research (not generic phrasing).
3. **`resourceUrl` handling — critical:** the model must NOT generate `resourceUrl` freely. Only URLs that came back from Stage 2's actual Tavily results may be used. If no real URL exists for a given step, omit `resourceUrl` entirely (keep `resourceTitle`/`resourceType`/`resourceWhy` as text-only guidance). Never let the LLM invent a plausible-looking link.
4. Keep the existing conflict rule (adherence > mechanism in weeks 1-8, reversed in 9-12, safety overrides both) exactly as-is — that logic isn't changing.

### Stage 6 — Present the Basis to the User (frontend)

Show a badge reflecting actual `methodConfidence`, not a blanket "certified" claim:

- `high_consensus` / `medium_consensus`: "🛡️ Anchored to: {canonicalMethodName} ({canonicalAuthority})"
- `first_principles`: "⚡ First-Principles Trajectory — No single certified consensus method exists for this goal; this plan is built from general skill-acquisition principles."

Never show the high-confidence badge unless `methodConfidence` genuinely earned it through Stage 2's cross-check.

### Stage 7 — Cache Write (NEW)

On a cache miss that completes Stages 2-3 successfully, write a new `ResearchCache` row: `canonicalKey`, embedded outcome, `canonicalMethod` (methodName, authority, sourceUrl, confidence, velocityTable, raw findings for future reuse), `hitCount: 1`.

### Stage 8 — Weekly Adaptation (existing `adaptUpcomingWeekTasksWithAI`, modified)

Pass the stored `velocityTable` and `canonicalMethodName`/`canonicalAuthority` (from the `Goal` record) into every weekly adaptation call. Instruct the model explicitly: de-load or advance pacing *within* the existing method's structure and numbers — do not drift into generic advice disconnected from the original grounding.

## Latency & UX

Do NOT assume this is fast. Full cache-miss pipeline (search + extract + synthesis + velocity + plan generation) should be assumed to run 15-25+ seconds until actually measured. Build:

1. An SSE (Server-Sent Events) streaming endpoint that emits progress events as each stage completes (e.g. `analyzing`, `searching`, `grounding`, `generating`, `complete`).
2. Frontend UI that renders these as a live research stepper, not a static spinner — see UX badge copy above for tone.
3. **Actually benchmark the real pipeline once built** and adjust the UX copy/timing expectations to match measured P50/P90, not estimated numbers.

---

## Explicit Non-Goals / Guardrails for This Build

- Do not let `methodConfidence: "high_consensus"` be claimed without a real Stage 2 cross-source agreement check having actually run and passed.
- Do not generate any `resourceUrl` that didn't come from a real Tavily result.
- Do not gate the promotion flywheel on `userFeedbackScore` until feedback collection actually exists.
- Do not treat the safety clamp list as complete — it's a floor, log clamp events for review.
- Do not skip Stage 4 safety clamps on cache hits — cached data still needs to pass through clamps since clamp rules may be added/changed after the cache entry was written.
