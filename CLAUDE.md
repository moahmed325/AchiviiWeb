# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Achivii turns a goal into a 12-week (90-day) deliberate-practice plan. It is an npm workspaces monorepo:
`frontend/` (React 19, Vite, Tailwind v4, deployed to Vercel) and `backend/` (Express, Prisma, PostgreSQL with pgvector, deployed to Render via `render.yaml`).

## Commands

From the repo root:

```bash
npm install                 # all workspaces
npm run backend             # API on :5000 (tsx watch)
npm run frontend            # Vite on :5173 (the e2e and CORS defaults expect 5173)
npm run build               # build both workspaces
```

The root `package-lock.json` is the only lockfile and is committed. CI, Vercel and Render install with `npm ci`, so they get exactly what it pins and fail if it is out of date. To change a dependency, run `npm install` at the repo root and commit `package-lock.json` with the `package.json` change.

Node 22 everywhere, pinned as `"engines": { "node": "22.x" }` (major only). Vercel reads the root `package.json`; Render reads `backend/package.json`, because its `rootDir` is `backend` (it installs from the root lockfile, but takes the Node version from the package.json in its rootDir). CI's `setup-node` reads the same two files (`node-version-file`) and fails if they differ, so change both together. Vercel builds from the root `vercel.json` (`cd frontend && npm ci`); there is no other Vercel config.

Backend (`cd backend`):

```bash
npm test                                  # vitest run (node env; the GEMINI key is blanked in vitest.config.ts)
npx vitest run test/safetyClamps.test.ts  # one file
npx vitest run -t "daily limit"           # by test name
npm run build                             # tsc -> dist/
npx prisma migrate dev                    # new migration
npx prisma migrate deploy                 # apply migrations (never `db push`, see below)
npm run ping:llm                          # live provider probe (needs a real key)
```

Backend tests live in two places: `backend/test/*.test.ts` (plan engine, safety and scheduling logic) and next to the code in `backend/src/**/*.test.ts` (billing and routes).

Backend tests mock `lib/prisma.js`, so none need a database. In a fresh checkout run `npx prisma generate` first, or `tsc` reports missing Prisma types.

Frontend (`cd frontend`):

```bash
npm test                                 # vitest + Testing Library in jsdom (src/**/*.test.{ts,tsx}); at most 6 workers (vitest.config.ts, B-36)
npx vitest run src/components/ui/Button.test.tsx
npm run lint                             # whole frontend; baseline is 0 errors, 2 warnings
npx eslint <changed files>               # files you touch must be lint-clean
npm run build                            # tsc && vite build
npm run e2e                              # same as npx playwright test: e2e/*.spec.ts, API mocked via e2e/mockApi.ts; starts Vite itself
npm run e2e -- e2e/today.spec.ts          # args pass through; CI runs every e2e spec (not e2e/live), split into 3 shards (see .github/workflows/ci.yml)
# e2e runs on port 5174 (E2E_PORT to change it) with a fake Supabase; sign in with signIn() from e2e/mockApi.ts
# Vite serves the worktree's live files: take an e2e baseline from a separate clean checkout, not the worktree you are editing
npx playwright test e2e/today.spec.ts --project=mobile
LIVE_API=1 npx playwright test e2e/live  # real backend on :5000, creates accounts
```

Playwright runs with one worker on purpose (parallel workers stall the Vite dev server) and has `desktop` (1440x900) and `mobile` (390x844, touch) projects.

## Database

- Postgres is required everywhere, local included; there is no SQLite mode. The database must allow the pgvector extension, because the migrations run `CREATE EXTENSION vector` for the `research_cache` table's `vector(768)` column.
- Always use `prisma migrate deploy`, never `prisma db push`. `db push` skips the migrations folder, which holds `CREATE EXTENSION vector` and the raw-SQL indexes, so the database drifts from the migration history.
- For Supabase use the session pooler connection string; the direct host is IPv6-only.
- Models: `User`, `Subscription`, `WebhookEvent`, `Goal`, `RoadmapWeek`, `DailyTask`, `WeeklyReview`, `ResearchCache` (`backend/prisma/schema.prisma`). No code reads or writes `ResearchCache` any more (the live research pipeline was removed); the table and its migrations stay until dropping them is decided separately.

## Backend architecture

`src/index.ts` mounts `/api/health`, `/api/auth`, `/api/goal`, `/api/billing`. The Lemon Squeezy webhook (`/api/billing/webhook`) is mounted **before** `express.json()` with `express.raw()` so its signature can be verified against the raw body; keep that order. CORS allows `CLIENT_ORIGIN` (comma-separated), localhost :5173/:3000, and any `*.vercel.app` origin.

Auth: the frontend signs in with Supabase and sends the access token as `Authorization: Bearer`. `lib/supabaseAuth.ts` verifies it, and `routes/auth.ts` resolves it to a Prisma `User` by `auth_user_id`, linking an existing user by email the first time.

Goal creation (`POST /api/goal/create` in `routes/goal.ts`):

1. **Clarify** (`lib/ai/clarify.ts`, `POST /api/goal/clarify`) turns the raw goal into a clarified outcome, a domain and follow-up questions.
2. **Preset match** (`findPresetForGoal`): the 10 certified pathways in `lib/ai/presets/` (run10k, guitar, saas, spanish, recomp, youtube, book, deepwork, chess, speech) give the roadmap a fixed method. Any other goal is custom and needs Pro (`authorizeNewCustomGoal`).
3. **Roadmap** (`lib/ai/roadmap.ts`, `generateRoadmap`): one model call picks the method (or keeps the preset's) and writes the phases and each of the 12 weeks' target and test. Goal text that matches the unsafe-framing rules in `research/safetyFilter.ts` (`screenQuery`) is refused with a 422 before any model call, and a method the model rates below 3 on safety is rejected. Code, not the model, decides how fast a number target climbs (plan-safety-limits M1.2, RULE-2, RULE-3): inside `checkRoadmapAnswer`, after the unit is unified and before the stated-target check, `safeTargetClimb` (`lib/safety/targetSteps.ts`) reads the target's family (running distance, running time, lift load, body weight, body fat, calorie deficit; `targetFamily`, PSL-10) and lowers any week that climbs faster than a safe step (`nextSafeStep`, numbers in `lib/safety/limits.ts`) to that step, week 1 against the starting point (not checked when there is none, `no_start`) and each later week against the lowered week before; an easier week is never changed, and a deficit target above 600 kcal is lowered to 600. The roadmap keeps the model's values as `loweredTargets: { week, model, safe }[]` (stored in `Goal.roadmap`; missing means none) and `RoadmapWeek.target` holds the safe value. A number named in the goal (`research/statedTarget.ts`, which also reads kg, km, lb, mi, a body-fat percent, "lose N" against the starting point and "in N minutes" as at most, PSL-5) must appear in the week-12 target; a number the model's own week 12 met and only the lowering put out of reach is accepted at the highest safe step, and the `finalGoal` mention check is skipped when week 12 was lowered. Goal create logs one `[Safety]` `target_step` line per lowered week after the goal is saved (with the goal id), plus `unknown_family` for a physical-looking target no family reads and `no_start` (`logRoadmapTargets`). Older goals are lowered on read, never stored (M1.3, RULE-9, `safeGoalTargets` in `lib/safety/storedTargets.ts`): `presentGoal` and `writeNextWeek` run the same check on the stored weeks (all 12, or on a goal with light tests weeks 4, 8 and 12 four safe steps apart with the light weeks following, `safeCheckWeekClimb`), rebuild only code-written text of a changed week (`objective`; a pathway's test, `keyMilestone` and week 12's `finalTest` from the preset when the stored test is the preset's own; otherwise, as on a custom goal, only the pass mark), and a goal created since M1.2 comes back unchanged. A closed week (`completed` or jumped) keeps its stored target and is never lowered: the check starts from the last closed week's stored target (on a light-test goal the last closed of weeks 4 and 8), or from the starting point when none is closed, the same in both readers. `presentGoal` sends `week12Line` (`{ safe, goal }` or null; for "lose N" `goal` is the starting point minus N, null with no start) whenever week 12 was lowered, at create or on read; the app shows it under week 12's target on the Roadmap (current week 12 and the Destination), Today's closing stretch and the review's next week (`frontend/src/lib/week12Line.ts`). `writeNextWeek` logs `target_step` with outcome `lowered_on_read` when the week it writes was lowered on read; `presentGoal` logs nothing. After the check passes, code puts the pathway's hand-written weekly tests in place of the model's (weekly update M2.1, RULE-19, WU-43; `withPathwayTests`, the `weeklyTests` field of each preset, `{target}` filled with that week's `formatTarget`): every pathway's test measures the target, and week 12's is the `finalTest`. On run10k, recomp, speech and spanish only weeks 4, 8 and 12 (`BIG_TEST_WEEKS`) have that big test; every other week is a light week: the light test with pass mark "Done as written", `light: true` on the stored test (missing means false: older goals and custom goals), and the next big week's target (`nextCheckWeek`), shown as "Next check, week {n}: {target}" and logged with "I did it" as `{ value: 'Done', passed: true, note }` (`frontend/src/lib/lightTest.ts`). The 40% week-1 rule is checked on the model's answer, before the light weeks take week 4's target, not after. The model's tests on such a pathway are thrown away, so they skip B-63's roadmap test scan and the one-type check (`RoadmapCheckContext.pathwayTests`, WU-44); custom goals keep both. The week writer is told a light week's target is the next check, not tested, and the session its test belongs to (`lightTestSession`). The roadmap prompt tells custom goals the test rule: part of a normal session, no special tools, short, no all-out effort, no max, nothing to failure, any harder test only in weeks 4, 8 and 12. Not behind any switch.
4. **Recovery profile** (`lib/recovery/`, docs/archive/method-aware-recovery): before week 1, the goal gets a checked profile saying what each kind of step does when its day doesn't happen, stored under `recovery` in `Goal.roadmap`. A pathway gets its hand-written profile; a custom goal gets a keyword-picked template, or the profile call when `CUSTOM_RECOVERY_PROFILES_ENABLED` is exactly `true` (off by default, `sync: false`). An older goal gets one at its next weekly review. Only the carry planner acts on it, and only behind `METHOD_RECOVERY_ENABLED` (see Missed sessions below).
5. **One week at a time** (`lib/ai/weekPlan.ts`, `generateWeekPlan`): only week 1 is written at creation, polished and checked by `taskRules.ts` and `scheduleRepair.ts`; `highLoad.ts` marks strain steps. Each later week is written after the weekly review (`lib/planV2.ts`, `writeNextWeek`). On a load goal (plan-safety-limits M2.1, RULE-4, PSL-8; `loadGoalFor` in `lib/safety/stepLoad.ts`: `isHighLoadGoal`, or the week's target has a family) both callers pass `loadGoal: { running }`, and the schema and prompt ask for a step `load` (`runMinutes`, `runKm`, `hardRun`, `kcalDeficit`, `kcalIntake`, `percent1RM`, `rir`, `toFailure`, `maxTest`; `parseStepLoad` keeps only finite numbers 0 or more, `percent1RM` at most 100, and real booleans), stored as written in the step JSON (no migration; the app never shows it). A step the model flags `highLoad`, a step of a run kind (`easy_session`, `quality_session`, `long_session`) or the lift kind (`strength_workout`), a strength-template cardio step (`conditioning`, the runs of a custom weight-loss goal), and the model's own test step on a running goal must carry it (the 10-minute version when the day's priority-1 step must); any load that names `runMinutes` or `runKm` must also give `hardRun`. A missing one is a soft retry reason, listed first among the soft reasons, and on the last attempt the step is kept and logged as `[Safety]` `load_missing` / `kept`. Code-made steps (the code-made test step, the light step, the re-test steps, the fallback 10-minute version and `describeDay`'s) carry no load; when code changes a step's minutes (`fitStepMinutes`, the 10-minute cap) `load.runMinutes` scales down with them when a step is shortened and never grows when one is made longer (`withMinutes`), `runKm` never. On a load goal `writeNextWeek` also passes `baseWeek` (M2.2a, B-64, `baseWeekOf` in `lib/safety/weekLoad.ts`, from the closing week's rows; on a first week back M2.2b's `firstWeekBackBaseOf`, below), and its week call always gets `goalId`; goal create's week 1 has no base. Any other goal's call is exactly as before (its input only adds `goalId`, which only the log reads).
6. **Safety limits.** Every limit number lives in `lib/safety/limits.ts` (plan-safety-limits RULE-1); the text scan, the week prompt and the old clamps import it. A new goal's roadmap targets are lowered to safe steps at roadmap time (step 3). The old velocity-table clamps (`research/safetyClamps.ts`, `applySafetyClamps`) run only on a goal's stored velocity table, when the goal is returned (`presentGoal` in `routes/goal.ts`); no code writes a velocity table any more, so they act on no plan v2 goal (retired in plan-safety-limits M3.1). On a load goal a week's sessions are held to numbers (M2.2a, RULE-5, RULE-6, PSL-15; `lib/safety/weekLoad.ts`, checked in `safetyBreaches`): a step is a run when its load gives `runMinutes` or `runKm` above 0 (`hardRun` decides a hard run), a run kind or the model's test step on a running goal with no running number counts its minutes (a `quality_session` is hard, and so is that test step in a measured week), the code-made test step on a running goal counts its minutes (hard when measured, easy when the light step); rest-day runs count, 10-minute versions don't. The week is in km only when every run gives km, otherwise in minutes (`runMinutes` where given, else the step's minutes; a `runMinutes` above the step is counted as written and logged `run_minutes_over_step` / `counted` on the accepted answer). Limits: the running total at most the base week plus 10% or 10 minutes / 1 km (two units compared in minutes; not checked without a base); the longest run at most 50% of the week with 3 or more runs, or with no base and fewer runs at most 30 minutes / 5 km; a known base of 0 runs is held like week 1, with every run at most 30 minutes / 5 km whatever their number (PSL-16); at most 2 hard runs; every step and 10-minute version `kcalDeficit` at most 600 and `kcalIntake` at least 1200; weeks 1 to 3 `percent1RM` at most 80, `rir` at least 3, no `toFailure`, no `maxTest`. The base week (`baseWeekOf`) is the closing week's planned running (offered days, copies once by `stepKey`), or what was done when under 70% of it; a run with no running number, or a week with no load on any step (written before M2.1), makes it unknown: no base, never 0, logged once per call as `no_base` on a running goal, or when a run step of the base week had no load (`runWithoutLoad`). A breach is a hard retry reason naming the step (or "This week"), the limit and both numbers, logged with the goal id; an answer refused for a day-level reason (a missing day, too few steps, no test step, no title) is still checked on the days that parsed, and those safety reasons go first in its retry reason, each logged once as `retry` (`failed` on the last attempt; `dayLevelReason`); when the last answer is refused only for safety breaches, attempt 1's answer is checked again as a last attempt and, if it passes every check, is the week, logged once with outcome `first_answer` (`firstAnswer` in `generateWeekPlan`, no extra model call); PSL-3 lets a load rule the stored test's own text breaks through on the test step, except in a light week, where a test-step load breach counts for the light-step swap; a week breach blocks it, and the swap is kept only when the swapped week passes the week checks again (else the week fails); where a running-total limit holds, the light step takes at most the whole running minutes left under it, never longer than it was, and is not shortened below a 10-minute version (M2.2b review, `runningLimitMinutes`). The handoff (`placeHandoff`) never places a step whose load names running (it waits), so placement can't raise the checked running. The SAFETY LIMITS block on a load goal names last week's base and the most allowed, the longest-run rule, the hard-run limit and the intake floor (every high-load preset is a load goal; without a load goal there is no block). A first week back of a load goal (`firstWeekBack` given, a break) is held to what was last done (M2.2b, RULE-7, PSL-18): `writeWeekAfter` reads the goal's weeks before the closing week in one query (`weekNumber < n`, not caught: a failed read fails the close and saves nothing) and passes them as `olderWeeks`; `firstWeekBackBaseOf` walks back from the closing week counting done running only (`doneRunningOf`, M2.2a's done rules, no 70% rule), passes over a week with none (a jumped week has no rows), stops at an unknown base at the first done run with no running number (or done days of a week written before M2.1), and takes the first week with done running above 0 as the base (`BaseWeek.firstWeekBack: { fromWeek, percent }`); none anywhere is a known 0-run base. Its running total is at most the base's done total with no allowance, `FIRST_WEEK_BACK_LONG_BREAK_PERCENT` (50) of it after a break of `LONG_BREAK_DAYS` (21) or more (`awayDays`; until weekly-update M3.4), never below `FIRST_WEEK_BACK_MIN_MINUTES` (30) / `FIRST_WEEK_BACK_MIN_KM` (5) (`firstWeekBackLimit`); an unknown base after a break is held like a 0-run base (PSL-16), told and refused as "last week's running isn't known", with `no_base` logged as before. The running line names the number ("- Running: first week back; at most {n} {unit} in total, what they last completed (week {w})."), and each such call logs one `[Safety]` `first_week_back_base` line (the week read and its total or `none` / `unknown`, the share, the limit). Every other week, a close that is not a break and a goal that is not a load goal are exactly as before (no older-weeks read). B-63's stopgap (`ai/safetyScan.ts`) also still scans text: for a high-load goal the week prompt gets a SAFETY LIMITS block, and the week call refuses a high-load step (a run10k or recomp step, or any step flagged `highLoad`) that names a deficit above 600 kcal, or in weeks 1 to 3 more than 80% of 1RM, fewer than 3 reps in reserve, a set to failure or a max test (one retry, then the week fails with the existing 503); the roadmap refuses a week test that breaks the same rules. A sentence copied from the stored weekly test is logged, not refused, except in a high-load first week back (weekly update M1.5b, WU-41), which is scanned with the weeks 1 to 3 rules and a time-trial rule and refuses it. Every hit logs a `[Safety]` line. On a goal that is not a load goal the running ramp and hard-run count are only told.
7. **No fallback plan**: if the roadmap or week 1 can't be written, goal create answers an honest 503 ("Couldn't design your roadmap right now" / "Couldn't write your first week right now. Please try again.") and saves nothing, for certified presets and custom goals alike. An unsafe goal answers 422. No new plan v1 goal is ever created (docs/decisions.md ND-21).

`goalDecomposer.ts` now only holds the shared plan types (`DailyTaskPlan`, `DetailedStep`, `UserRoutineInput`) and re-exports `clarifyGoalWithAI`. `lib/research/` holds the unsafe-goal screen, stated targets, safety clamps and `formatBasisBadge` (`planGrounding.ts`); there is no live web search, research cache or embedding call.

LLM providers: `lib/ai/gemini.ts` holds the cascade: **Gemini only**, then a miss. Gemini retries busy and rate-limit errors, and retries once without the schema if the API rejects it. There is no fallback provider for now (Groq was removed); a second provider would go in the cascade. `modelJson.ts` repairs and parses model JSON, `retry.ts` gives one retry.

Plan v2 (`lib/planV2.ts`, `ai/weekPlan.ts`, `ai/roadmap.ts`, spec in `docs/architecture/plan-v2.md`): weekly targets that adapt. Each week the user logs a weekly test (`POST /api/goal/weeks/:weekNumber/review`), the remaining targets are updated, and the next week is written. Plan v2 is the only plan model (ND-21): every goal is created with `planVersion: 2` and plan v1 code is gone. Endpoints that need a roadmap refuse a goal that is not v2 with `409 not_plan_v2` (weekly review, test result, reconcile and the missed-session actions); the frontend gives such a goal no phases and no late-test card. Don't add v1 branches back. The `planVersion` column and its default of 1 stay in the schema for now.

Missed sessions (`lib/missedSessions.ts`, `lib/carryForward.ts`, `POST /api/goal/reconcile`): carry-forward writes happen only when `MISSED_SESSIONS_CARRY_ENABLED` is exactly `true`. It is on in production (the notice that explains a moved step shipped in missed sessions M3.1). It is managed in the Render dashboard only (`sync: false` in `render.yaml`, so unset means off) and is the kill switch (ND-15); never turn it on or off from code or tests.

Method-aware recovery in carry-forward (`lib/recovery/carry.ts`, `planRecovery`, M3.1a to M3.1d): when `METHOD_RECOVERY_ENABLED` is exactly `true` (read per request; `sync: false` in `render.yaml`, so unset means off; on in production since 2026-10-16, O2; managed in the Render dashboard only, and it is this feature's kill switch), a missed day whose steps all have known kinds in a valid profile follows each kind's action (move to the first later day that fits, a `continueFrom` marker for continue, nothing for let go and fixed), and the reconcile body adds `carry.outcomes` (which rules each missed day followed and its outcome), `carry.continues`, `carry.alreadyContinued`, `carry.reorders`, `carry.easyStart` and what was stored (`writtenContinues`, `writtenReorders`, `writtenEasyStart`). A moved hard step skips any day within the profile's rest gap of another hard step (RULE-14, counted over every done or open day of the goal); a hard step that takes the place of a hard step is only checked for sharing that day (MR-29). Steps of an in-order move kind are never lost (RULE-20, MR-30): `recovery/inOrder.ts` (`inOrderQueue`) lists each week's steps of the kind not done yet, in written order, from the stored week, ignoring any step a later week already holds or that is done on any day; for the week holding today and the week before it (older weeks keep the ordinary move rules), the remaining sessions of the kind keep their days and hold that queue in order (`shiftedFrom` marker naming the day the step was written on); a session that cannot take the next step safely gives its own step up, unless it is the day's only step (then the kind waits, `only_step`: a day is never left empty); the steps left over are listed for next week (`toNextWeek` records on the queue's first missed step, `reorders[].toNextWeek`, counted in `weekCounts.toNextWeek`, outcome `next_week`; in week 12 they are `reorders[].leftOut`, outcome `left_out`, and the count is 0). Next week continues from them (M3.1d, MR-32, `recovery/handoff.ts`): with the switch on, `writeNextWeek` reads the finished week (`weekHandoff`), tells the week writer where the person is (`whereTheyAre`, a prompt block), and after the call code places the carried steps in the new week's first sessions of their kind (`placeHandoff`, same fit and rest-gap rules, a `shiftedFrom` marker); what does not fit waits as `toNextWeek` records inside the new week, and a carry or reorder that removes a step holding records moves them onto a step it keeps (`keepRecords`). A day whose priority-1 step code changes gets a matching title, 10-minute version and intention (`recovery/dayText.ts`; `writeRecovery` writes them for reordered days). The review route passes the week before so a break across the week change counts, and each wait is logged (`[Recovery] Handoff wait`). A non-hard moved step that found no room takes next week's first session of its kind when it fits; a hard one is only told. Nothing in the handoff can fail the week call. `writeRecovery` saves every reordered day in one `prisma.$transaction`, all or nothing. After an open gap, the first hard step back gets RULE-21's easy line (on the hard test step when the test day is the first day back; `recovery/easyStart.ts`), and a swap keeps it on that step, once, written in the swap's transaction (B-49, `easyLineAfterSwap`); the warm-up line goes only on physical steps (MR-31). The person's actions follow RULE-16 (M3.2, `recovery/swap.ts`): one pure check (`methodSwapRefusal`, RULE-12 to RULE-14, refusing only a breach the swap creates or a rest-gap closeness it narrows) decides the swap route, the key-session hold (a key session is held only when its priority-1 step moves and that swap passes; a held offer's receiving day never takes a continue marker, the continue is no room) and `carry.choices` (`today`: `taskId`, `setAside`, `swapWith`; `held[]`: `taskId`, `receivingTaskId`, `moveNowTaskId`), listing the same hold as the body's `carry.held`, with the move-now and swap days read from the plan as stored after the run's writes (`planChoices`, `openSwapRefusal`, `moveNowTarget` in `reconcileCore.ts`); with the carry switch off it is `{ today: null, held: [] }`. Swap refuses `fixed_step`, `out_of_order` and `rest_gap` with the switch on, and a day holding a `shiftedFrom` step (`holds_carry`) or a `continueFrom` marker (`holds_continue`; not when the marker's day is done, B-50) in any switch state, and an open swap also refuses a day holding a `carriedFrom` step (`holds_carry`; not when its source day is done and still holds that step, B-52, B-55, MR-37, `isDoneCopy` in `recovery/inOrder.ts`); carry-now refuses `would_not_move` (switch on) when the held main step of a day that follows the new rules would not move; a held day under RULE-18 keeps today's carry-now. With the switch on, the signals add `line` (M3.3, `buildSignals`, MR-35): the one miss line Today and the Dashboard show, chosen on the server from `carry.outcomes` and the stored markers (`carriedFrom`, `shiftedFrom`, `continueFrom`; a done source day names no day, B-50, and a carry from a done day that still holds the step gets no line or `carried` signal in any switch state, B-52, B-55); Today's actions read `carry.choices` instead of working them out. Off, or for a day without kinds, the plan and body are exactly missed sessions' (`planCarries`). Writes still need `MISSED_SESSIONS_CARRY_ENABLED`. Never turn it on from code or tests.

Week close (weekly update M1.2a, `lib/weekClose/`, docs/features/weekly-update): a week closes through one shared save, `saveWeekClose` in `weekClose/close.ts`, whether by the weekly review or automatically. The week after is written first (`writeWeekAfter`: the recovery profile, the week before with the method switch on, then `writeNextWeek`, the model call, outside any transaction); then one `prisma.$transaction` holds every write, starting with a conditional update of the closing week from `active` to `completed` (`closedBy` `review` or `auto`, `closedAt`). ## Frontend architecture

- `App.tsx`: `AuthProvider` > `GoalProvider` > `BrowserRouter` > `AppShell`. Secondary pages are lazy-loaded. `ProtectedRoute requireGoal` gates routes on having an active goal.
- `lib/api.ts` is the fetch client; `resolveApiBaseUrl()` uses `VITE_API_BASE_URL` (falls back to localhost:5000 in dev, the Render URL in production).
- `context/GoalContext.tsx` holds the active goal; `lib/journeyAdapter.ts` and `hooks/useJourneyData.ts` shape it for the journey and roadmap views.
- Feature folders under `components/` (`today`, `focus`, `journey`, `review`, `progress`, `achievement`, `coach`, `billing`, `onboarding`, `pathways`, `marketing`); shared primitives in `components/ui/`.
- `/__ui` (dev server only) previews every primitive in every state.

### Frontend rules (from `Design.md`, read it before frontend work)

- Use the primitives from `components/ui` (Button, Field/Input, Dialog, Surface, Tabs, ProgressBar, StepMarker, states). Don't build another button, input, dialog or card; if a variant is missing, add it to the primitive and to `/__ui`.
- Tokens are role-named in `@theme` in `src/index.css`. Never hard-code hex, font size, radius or shadow; add a token instead.
- Dark only. No gradients or gradient text, one icon family (lucide-react, stroke 1.5), motion always has a reduced-motion path.
- `ui-root` on the outermost element of each screen; `focus-ring` on any custom focusable element; `cx()` for class merging; `className` on primitives is for layout only.
- Pathway data lives only in `lib/certifiedPresets.ts`; galleries use `PathwayLibrary`/`PathwayStrip` and launches go through `usePathwayLaunch`.
- Tests sit next to the component as `*.test.tsx` and query by role and accessible name, not class names.

### Working on a milestone

When you are given a milestone to implement:

1. Your instructions are the **Prompt** section of the milestone file. Also read what it lists under "Read first". Do only that milestone.
2. Run `git status` first and note anything already changed. Work on the branch you were given; never commit or push to `main`.
3. Check the code before trusting the prompt or the docs. If they disagree in a way that changes the work, stop and report it.
4. Stop and report, instead of working around it, when: a decision the work needs is not made; a schema migration or new dependency is needed that the prompt does not allow; unrelated refactoring is needed; or the scope would have to grow.
5. Before changing anything, run the checks the prompt lists on your starting commit, using the repo's own scripts (see Commands); those numbers are your baseline. Run them again at the end and compare.
6. Write your results in the **Report** section of the same milestone file; screenshots go in `milestones/<id>-evidence/`. Give evidence for every requirement, and never claim a check you did not run.
7. Do not edit `03-phases.md`, `02-feature.md`, any `decisions.md` or `docs/backlog.md`; the reviewing chat updates them. Put anything they should change under "Differences from the docs" in your report.
8. List every problem you notice under "Problems found" in your report, even outside the milestone, with where you would put it. Do not fix problems outside the milestone. List any "good to have" idea that is not a problem under "Ideas"; do not build it or edit `docs/ideas.md` (the review copies the ones worth keeping).
9. Keep the shared docs true. If your change makes `CLAUDE.md`, `Design.md` or a doc in `docs/architecture/` wrong, update it in the same branch and list it in your report.

### Quick fixes

A quick fix is a small item from `docs/backlog.md` (`B-n`), given to you as a short prompt instead of a milestone file. Follow steps 2 to 5, 8 and 9 above, and also:

- Fix only the backlog items named in the prompt, and name them in the commit message (`fix(today): show the 10-minute version's minutes (B-1)`).
- Stop and report if the fix needs a product decision the prompt does not make, a change to stored data, or more than one branch of work. It then becomes a feature.
- Report in your reply, not in a file: what changed and where, the evidence for "fixed", commands and results against the baseline, any problems found, and any ideas (as in step 8).
