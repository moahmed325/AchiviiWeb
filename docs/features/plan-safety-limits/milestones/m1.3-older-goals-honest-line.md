### Requirements
1. **One pure function lowers stored weeks.** Put it with the limits code (recommended `backend/src/lib/safety/storedTargets.ts`). Input: the goal's stored `RoadmapWeek` rows, the stored roadmap's `startingPoint.value`, `finalTest` and `loweredTargets`, and the goal's pathway (`pathwayFor(rawGoal, clarifiedOutcome)`). Output: new week objects and a new `finalTest`, the input left unchanged, plus the lowered list `{ week, model, safe }[]` (the stored `loweredTargets` merged with the ones found now; a week appears once). Jumped weeks are checked like any other week: their target still sets the step for the next week. (RULE-9)
2. **Which weeks are checked.** A goal with no light test: all 12 weeks, as `safeTargetClimb` does (week 1 against the starting point; none means week 1 is not checked, PSL-11 Q14). A goal with any `light: true` test: weeks 4, 8 and 12 only, week 4 against the starting point, each one at most four safe steps beyond the one before (apply `nextSafeStep` four times in a row, so a goal created since M1.2 is never lowered again). Then each light week takes its big week's lowered target (`nextCheckWeek`). Add the four-step check to `targetSteps.ts` beside `safeTargetClimb`; do not copy its rules. (RULE-2, PSL-11 Q1)
3. **Rebuild only what code wrote (PSL-7).** For each week whose target changed: `objective` is `formatTarget(target)`. On a pathway with `weeklyTests`, a measured week's test is refilled from the preset as `withPathwayTests` does (reuse it or a shared helper; don't write the template code twice), and when week 12 changed, `finalTest` becomes week 12's refilled instructions. A light week's test does not change. On a custom goal, the test and `finalTest` stay as stored, even if they name the old number. `keyMilestone` is rebuilt from the week's test the way `roadmapWeekRows` builds it. `finalGoal` and `clarifiedOutcome` never change. A week whose target did not change is returned exactly as stored.
4. **`presentGoal` sends the lowered plan.** Run the function in `presentGoal` on the goal's `roadmapWeeks` and `roadmap`, so every response from the four routes in Context carries the safe targets. It writes nothing: no Prisma call, and the stored row and `Goal.roadmap` stay byte-for-byte unchanged. It logs nothing, because `/active` runs on every app load. A goal without a v2 roadmap, or without `roadmapWeeks` in the object, is returned as today.
5. **`writeNextWeek` tells the week writer the safe targets.** Run the same function before the week call, and pass the lowered `next.target`, `next.test` and `done.target`. For a goal with nothing to lower, the week call's input, and so the prompt, stays exactly as today (R-1, `weekPrompt.before-m2.1.txt` unchanged). When the week being written had its target lowered on read, log one `[Safety]` line with the goal id: rule `target_step`, that week, model and safe values, outcome `lowered_on_read`. Add the outcome where `logSafetyHit`'s outcomes are typed. (RULE-9, RULE-10)
6. **The honest line.** `presentGoal` adds one field (recommended `week12Line: { safe: string; goal: string } | null`). It is set when week 12 is in the lowered list (stored or found now): `safe` is the safe value and `goal` the model's value, each as rounded amount and unit, with no metric and no "or less" (`10 km`, `48 minutes`, `22 %` as `formatTarget` rounds). One frontend helper builds the exact copy from `02-feature.md` section 6: "Week 12 aims at {safe}, a safe step. Your {goal} goal is the next step." Show it, as quiet secondary text under week 12's target, in the places PSL-9 names: the Roadmap page's `CurrentWeek` when week 12 is the current week, and the `Destination`; Today's closing stretch under the Summit Target; the review's next-week target when week 12 is next. Use the existing primitives and tokens (Design.md). (RULE-3, AC-3, PSL-9)
