### Goal

### Requirements
1. **The load type.** Add an optional `load` to `DetailedStep` (`goalDecomposer.ts`) with the fields in `02-feature.md` section 7: `runMinutes`, `runKm`, `hardRun`, `kcalDeficit`, `kcalIntake`, `percent1RM`, `rir`, `toFailure`, `maxTest`. Every field is optional. Parse it in one small function: a number is kept only when it is finite and 0 or more (`percent1RM` at most 100); a yes/no only when it is a real boolean; anything else is dropped. A load with no field left counts as missing. (PSL-4)
2. **Which goals are asked (a "load goal").** A goal is asked for load when it is `isHighLoadGoal`, or the week's target has a family (`targetFamily` with `run10k`). Work this out once in each caller of `generateWeekPlan` (goal create and `writeNextWeek`) and pass it as one new optional input field, alongside whether it is a running goal (run10k, or a running-distance or running-time family; used only for the test step, requirement 4). For any other goal, the schema object and the prompt are exactly as today: `weekResponseSchema` still returns `WEEK_RESPONSE_SCHEMA` itself, and both fixtures stay byte-for-byte the same. (RULE-4, section 7 "Must not break")
3. **The schema and the prompt, for load goals only.** The step schema and the 10-minute version's schema each get an optional `load` object property, never in `required`, because only some steps need it. The step-fields list in the prompt gets one line saying which steps carry `load` and what each field means, in plain words, worded from requirement 4 (the run fields and the lift fields on every load goal). Add a fixture for a run10k week 1 prompt and a test that it differs from main's run10k prompt only by the new lines.
4. **Which steps must carry a load (PSL-8).** On a load goal, a step needs a load when: the model flagged it `highLoad`; or its kind is a run kind (`easy_session`, `quality_session`, `long_session`) or the lift kind (`strength_workout`), whatever the target's family (a custom weight-loss goal with runs or strength sessions is asked too, or M2.2 cannot check it); or, on a running goal, it is the model's own test step (`TEST_STEP`), whatever its flag (PSL-11 Q9). A step that needs a load is missing one when: a run step (a running kind, or the test step on a running goal) has neither `runMinutes` nor `runKm`, or has no `hardRun`; a lift step (`strength_workout`) has neither `rir` nor `percent1RM`; any other such step has no field at all. Warm-ups, food logging and other steps need none. The 10-minute version needs a load exactly when the day's priority-1 step does. Code-made steps (`testStepFor`, `lightTestStep`, the fallback 10-minute version) never need one.
5. **A missing load is a soft retry reason (RULE-4, AC-4).** Add it to `soft` in `checkWeekAnswer`, naming the step and what is missing (for example: `Day 2 step "Easy run" needs its load: runMinutes or runKm, and hardRun.`). On the last attempt the step is kept without a load, B-63's scan runs exactly as today, and one `[Safety]` line is logged for each step kept that way (rule `load_missing`, outcome `kept`, with the goal id). Add the rule and outcome where `logSafetyHit`'s values are typed. A missing load never turns a week that main would save into a 503.
6. **Code never copies or keeps a wrong load (M1.1 section 3).** The 10-minute-version fallback (`weekPlan.ts:654`) and `describeDay`'s 10-minute version (`dayText.ts`) carry no `load`. The light-week swap drops the refused step's `load`. When `fitStepMinutes` changes a step's minutes, `load.runMinutes` scales by the same ratio, rounded to a whole minute; when the 10-minute cap shortens the model's 10-minute version, its `runMinutes` is scaled the same way. `runKm` is never scaled, because the step's text names the distance. Keeping km as written while the minutes shrink over-counts the planned distance, which is the safe side for the running total; M2.2 must not scale it down. All other fields stay as the model wrote them. (PSL-11 Q10)
7. **Stored as written.** `load` is saved inside the step JSON, unchanged by `polishDays`, `markHighLoad`, carries, swaps and the handoff (they spread the step). No migration (PSL-4). Nothing in the frontend reads or shows it.

### Decisions I made
1. **One input field `loadGoal?: { running: boolean }`** (present means a load goal), not two fields (`loadGoal: boolean`, `runningGoal: boolean`). The prompt asks for one new field, and "running" only means something on a load goal.
2. **The load is parsed only on a load goal** (`toStep(..., withLoad)`), not on every goal. If the model sends a stray `load` on a typing goal (for example when Gemini drops the schema), the stored step is exactly what main stores.
3. **Strict numbers:** a numeric string such as `"5"` is dropped, not converted as `int()` does for `minutes`. The prompt says a number is kept only when it is finite, and a safety number should come as a number.
4. **Rest-day steps follow the same rules:** a light rest-day step that the model flags `highLoad` needs a load (rest days have no kind, so only the flag applies). Other option: skip rest days. Why: PSL-8 has no day exception, and a flagged easy jog on a rest day is running that M2.2 will count.
5. **A step written with 0 minutes keeps its `runMinutes` as written** when code gives it minutes, because there is no ratio. Other option: drop `runMinutes`. Why: dropping it would turn a step that had its load into one that is missing it, after the check.
6. **The rest-day 15-minute cap also scales `runMinutes`** (`withMinutes`), not only `fitStepMinutes` and the 10-minute cap. It is a third place where code changes a step's minutes.
7. **A test step the light swap replaced is not logged as `load_missing`:** the step in the week is then code-made. This is checked by title after the swap.
8. **The prompt line names "the weekly test step" only on a running goal**, matching `loadNeed`.
9. **`loadGoalFor` finds the pathway the way `isHighLoadGoal` does** (`findPresetForGoal(rawGoal) || findPresetForGoal(clarifiedOutcome)`) in both callers, instead of using goal create's own `preset` variable, so goal create and later weeks always agree.

### Stop-if review
- **Schema refusal:** not seen, but not tested live. The model is mocked in every test and no live call was made (`npm run ping:llm` only probes the provider). The new property is a plain nested `object` with `number` / `boolean` fields and no `required`, which fits Gemini's schema subset. If Gemini refused it anyway, `gemini.ts` retries once without the schema and `toStep` still reads `load`, so loads would still arrive, just less reliably.
- **Run or lift kinds under other ids:** none in any pathway or keyword template. I listed all 13 templates' kind ids: only `endurance` has run kinds, only `strength` has `strength_workout`, and only run10k and recomp map to those templates (`pathways.ts`). The **profile call** can add new kind ids (its prompt says a kind whose job no template kind does "gets a new id"), so a custom goal could get, for example, a `tempo_run` kind. Requirement 4 would miss it unless the model flags the step `highLoad`. The call only runs when `CUSTOM_RECOVERY_PROFILES_ENABLED` is exactly `true`, which is off, so no live goal has such a kind today. I did not stop; see Problems found.
- **503 from load:** a missing load is only ever a soft reason, and it gives way on the last attempt (tested). As with every soft reason, the second answer could have a hard breach the first did not, so a week main would have saved on attempt 1 could fail on attempt 2. That comes from AC-4's retry itself, not from extra code here.

### Questions for M2.2
1. **What a step with no load counts as** (recommended safe defaults):
   - *Kept on the last attempt* (`load_missing`): count it by its kind and minutes. A run kind (or the model's test step on a running goal) counts its whole `durationMinutes` as running when its own week is checked, and **0** when that week later serves as the base week. A `quality_session` counts as a hard run. A lift step has no number, so RULE-8's text scan decides. Why: counting the minutes keeps this week's check strict, and leaving them out of the base keeps next week's allowance low; both errors land on the safe side.
   - *An older week's step* (written before M2.1): PSL-11 Q13 already says running kinds' minutes, else the text scan only. Recommend the same split as above for the base week.
   - *A code-made step:* PSL-11 Q9 counts a code-made test step's minutes as running on a running goal. Recommend the measured test (a non-light week) counts as one hard run and the light step as easy. A fallback 10-minute version done instead of a run counts its minutes (at most 10) as running when `usedMinimumVersion`.
2. **`runMinutes` larger than the step's `durationMinutes`** (the model writes both): refuse, clamp or count as written? Recommend counting as written (the safe side for the week's own check) and logging it.
3. **Both `runKm` and `runMinutes` given:** the running total is in km only when every run gives km. Recommend: a step with both counts in km; a week with any minutes-only run is counted in minutes, using `runMinutes` where given and `durationMinutes` otherwise.
4. **Rest-day flagged steps** carry a load (decision 4). Should M2.2 count a rest-day jog in the running total? Recommend yes.
5. **Profile-call kinds** (Problems found): should a profile kind marked `highLoad` also need a load?
6. **A `conditioning` step with no running** (a walk; review fix 1): it must give some load, so the model may send `runMinutes: 0, hardRun: false` or only food fields. M2.2 should count only a `conditioning` step with `runMinutes` or `runKm` above 0 as a run.
