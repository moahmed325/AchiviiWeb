### Goal
On a physical goal (a load goal), a week whose running, lifting or calorie numbers break a limit is refused: one retry, then no week and the existing 503. Every later week's running total is held to the base week plus the allowance. The writer is told the actual number. A goal that is not a load goal is exactly as before.

### Requirements
1. **Count a week's running (one pure module, `lib/safety/weekLoad.ts`).** From a week's steps, work out: the running total and its unit, the total in minutes (for mixed-unit comparisons), the longest run, the number of runs, the number of hard runs, and whether the running is **unknown**. The rules:
   - A step is a run when its load gives `runMinutes` or `runKm` above 0 (PSL-11 Q9, PSL-15 (6)). A run kind, or the model's test step on a running goal, with no load is a run counted by its `durationMinutes` (PSL-15 (1)). `load.hardRun` decides a hard run; a `quality_session` with no load is a hard run.
   - Code-made steps (PSL-15 (1)): the code-made test step on a running goal counts its minutes as running, and in a measured week (not light) as one hard run. The light step counts as easy running. A code-made 10-minute version done instead of a run counts its minutes (at most 10) as running.
   - The unit is km only when every run gives `runKm`; otherwise minutes, using `runMinutes` where given and `durationMinutes` where not (PSL-15 (3)). A `runMinutes` above the step's `durationMinutes` is counted as written (PSL-15 (2)).
   - Rest-day runs count (PSL-15 (4)).
   - `runKm` is never scaled (PSL-14).
   - Every number used comes from `limits.ts`. If you need a number that isn't there, stop (see Stop if).
2. **The base week (B-64, PSL-11 Q8, PSL-15 (1)).** In `writeNextWeek`, from `finishedTasks`:
   - **Planned** counts the main steps of every day that is not `notOffered`. Rest days count only for the runs on them.
   - **Done** counts completed, offered days: their steps' load, or the 10-minute version's when `usedMinimumVersion`. A `carriedFrom`/`shiftedFrom` copy counts once (`isDoneCopy`'s rule).
   - **Base** is planned, or done when done is under `BASE_WEEK_DONE_PERCENT` of planned.
   - When any run step, planned or done, has no load (a step kept on the last attempt, or a week written before M2.1), the base is **unknown**. That means no base, never 0: the running-total check is skipped, as in week 1, logged once per week call as `[Safety]` `no_base` with the goal id, and every other limit still applies.
   - A known week that ran 0 is a real 0: the allowance only (`02-feature.md` section 5).
   - Pass the base (or no base) to `generateWeekPlan` as one new optional `WeekCallInput` field, given only on a load goal, and pass `goalId: goal.id` (B-64).
   - Goal create's week 1 has no base.
   - Until M2.2b, a first week back is counted from the closing week like any other week.
3. **The week limits (RULE-5).** In `checkWeekAnswer`, on a load goal only, over the days the model wrote:
   - **Running total:** at most base + the larger of `RUNNING_TOTAL_STEP_PERCENT`% and the allowance (`_MIN_MINUTES` in minutes, `_MIN_KM` in km). When the base and this week are in different units, compare both in minutes (PSL-15 (3)). No base: not checked.
   - **Longest run (PSL-15 (7)):** in a week with 3 or more runs, at most `LONGEST_RUN_MAX_PERCENT`% of this week's running total. In a week with no base (week 1, or an unknown base) and fewer than 3 runs, at most a fixed cap: 30 minutes, or 5 km when the week is counted in km. A week with a base and fewer than 3 runs has no longest-run check (the running total caps it). Add the 3, the 30 minutes and the 5 km to `limits.ts`, with a comment naming PSL-15.
   - **Hard runs:** at most `HARD_RUNS_MAX`.
   - **Every step and 10-minute version:** `kcalDeficit` at most `CALORIE_DEFICIT_MAX` (a lower deficit is never refused), and `kcalIntake` at least `DAILY_INTAKE_MIN_KCAL`.
   - **Weeks 1 to `EARLY_WEEKS`:** `percent1RM` at most `EARLY_WEEK_MAX_1RM_PERCENT`, `rir` at least `EARLY_WEEK_MIN_RIR`, no `toFailure: true`, no `maxTest: true`. From week 4 these four aren't checked.
   - 10-minute versions get the per-step checks but are not added to this week's running total.
   - At the limit passes; one step past is refused.
4. **A breach is a hard reason (RULE-6, AC-6).** It goes with the existing hard reasons: one retry, then `generateWeekPlan` returns null and both callers answer their existing 503 with nothing saved.
   - Each reason names the step (or "This week"), the limit and both numbers. Example: `This week's running is 75 minutes; the most allowed is 70 (last week 60, plus 10 minutes).`
   - Each breach writes one `[Safety]` line with the goal id, week, rule, number and outcome, using the existing `logSafetyHit`. Add the new rules to `SafetyRule`, worded like the existing ones.
   - PSL-3 holds for loads too. On the test step, a load breach of a rule that the stored test's own text breaks is logged as `test_text`, not refused, except in a light week (`isLightWeek`), where nothing from the test is let through.
   - M1.5b's fallback: a load breach on the test step counts as a refusal on the test step, so on the last attempt `LIGHT_TEST_STEP` takes its place exactly as a scan refusal would.
   - A week-level breach (total, longest run, hard runs) is not on any one step and never triggers that fallback.
   - B-63's text scan runs exactly as today (RULE-8, R-6).
5. **The running line from the limits module (PSL-11 Q17).** The SAFETY LIMITS block is told on every load goal, not only on `highLoadGoal`; this changes a custom physical goal's prompt on purpose. Build every number in the block from `limits.ts`. With a base, the running line names the number: most allowed this week, and last week's base, in the unit compared. Also tell: the longest-run rule, the hard-run limit, and the intake floor (new line).
   - The typing goal's fixtures (`weekPrompt.before-m2.1.txt`, `weekPrompt.with-profile.txt`) stay byte-for-byte the same.
   - Update the run10k fixture (`weekPrompt.run10k-m2.1.txt`, or a new `-m2.2a` one) on purpose, with a test showing that only the SAFETY LIMITS lines differ.
6. **Logs.** `no_base` once per call (requirement 2). A `runMinutes` above `durationMinutes` once per step, on the accepted answer only (outcome `counted`).
7. **Tests.**
   - **AC-5:** each limit in requirement 3 refused at one step past and passed at the limit, for week 1 and a later week (week 1 has no running-total check).
   - **The base week:** planned versus done at under 70%; the 10-minute version's load when used; a copy counted once; not-offered days left out; a rest-day run counted; a `conditioning` walk not counted.
   - **Mo's two tests (PSL-15):** (a) a base week whose runs have no load, then a normal week, is written (no running-total refusal, `no_base` logged); (b) a base week in km and this week in minutes, or the reverse, compared in minutes (one test refused, one passed).
   - **The no-base cap (PSL-15 (7)):** a no-base week with one run over the cap is refused, and one under it passes, in minutes and in km; a 3-run week is held to 50% instead; a week with a base and 2 runs gets no longest-run check.
   - **A real 0:** a base week of 0 runs, all with loads, allows only the allowance.
   - **Mixed units in one week:** counted in minutes.
   - **`runMinutes` over `durationMinutes`:** counted as written and logged.
   - **Exceptions:** PSL-3's `test_text` exception on a load breach; the light-week fallback on a test-step load breach; a week-level breach giving no fallback.
   - **AC-6:** a second breach gives the 503 at goal create and at review with nothing saved (the existing mocked-Prisma tests, R-2).
   - **B-64:** `goalId` reaches the `[Safety]` line from `writeNextWeek`.
   - **Not a load goal:** schema, prompt and result exactly as today.

### Decisions I made
1. **Rule names.** A per-step load breach reuses the text scan's rule name (`deficit_over_600`, `over_80_percent_1rm`, `rir_below_3`, `to_failure`, `max_test`), with `matched` like `kcalDeficit 700` and `value` / `limit`. Other option: separate `load_*` names. Why: PSL-3 matches by rule against the stored test's scan, and it is the same rule.
2. **A week with no load on any step is "written before M2.1", so unknown.** Other option: find runs by kind only. Then an older kindless week would count as a real 0, and next week would get only the 10-minute allowance and 503s. A load goal's week since M2.1 always carries loads.
3. **Code-made test steps are recognised by their fixed text** (`codeMadeTestStep`: the light step's title, or `testStepFor`'s focus cue and pitfall), for this week and for the stored base. Other option: a marker field on the step, but that changes stored data.
4. **A day done through its 10-minute version with no running number,** whose priority-1 step is a run, counts the version's minutes (at most 10, known). This covers the code-made fallback and a model's version kept without load. Other option: unknown for the model's version. Why: code caps the version at 10 minutes, so the count is bounded either way.
5. **A run kind whose load says `runMinutes: 0` (or `runKm: 0`) is not a run.** Only a missing running number counts the step's minutes. Other option: count its minutes. Why: PSL-15 (6) says "above 0", and "no load" means no number.
6. **A run's minutes** are `runMinutes` when above 0, else the step's minutes. So a km step with `runMinutes: 0` still has minutes for a mixed-unit comparison.
7. **A 0-run base takes this week's unit,** so the allowance is 10 minutes or 1 km, as section 5 says. Other option: always minutes.
8. **Told limits are rounded down** (whole minutes, km to 0.1); the check uses the exact value. So the writer is never told more than is allowed.
9. **After a light-step swap the week checks run again** on the swapped week, so the saved week is the one that was checked. Other option: no re-check.
10. **The new block only on a load goal.** A `highLoadGoal` without a `loadGoal` (not reachable in the app; the B-63 tests use it) keeps the old block, with its numbers now from `limits.ts`. Why: keeps B-63's tests and both fixtures as they are.
11. **Load checks run on every step and 10-minute version of a load goal,** whatever its `highLoad` flag (requirement 3: "every step").
12. **`no_base` is logged in `generateWeekPlan`,** once per call, not per attempt.
13. **The model's own test step kept without a load** counts its minutes as easy, even in a measured week. This follows PSL-15 (1) literally, though code's measured test counts as hard. Other option: count it as hard (safer). See Problems found.
14. **`goalId` goes to every goal's week call from `writeNextWeek`** (B-64). A typing goal's input gains that one key, which only the log reads; `writeNextWeekHandoff.test.ts`'s expected input was updated.
15. **The hard-run line says "a hard weekly test counts as one",** so the model counts its measured test.
16. **A new fixture `weekPrompt.run10k-m2.2a.txt`;** the M2.1 fixture stays, and the test proves only the SAFETY LIMITS lines differ.

### Stop-if review
- **A pathway's method breaking a limit as written:** not found. Recomp's deficits are 250 to 500 and its week 1 is at 3 RIR. run10k's method (80/20, "never two hard days in a row") requires no number of quality sessions. A measured week (4, 8, 12) with the hard test plus 2 key quality runs would be 3 hard runs, but that is the model's choice, and the prompt now says a hard test counts. A beginner long run above half the week is also the model's choice: each practice day is the daily minutes. This could still bring 503s if the model keeps writing 3 hard runs; see Problems found.
- **The handoff or carry-forward raising the running total after the check: an edge, reported and not worked around.**
  - Carry-forward moves steps inside a week that was already counted and never adds one.
  - The handoff (method switch on) never places a run kind. `easy_session` is let go; `quality_session` and `long_session` are hard, so they are only told.
  - It does place non-hard `move` steps of other kinds in place of a same-kind step, and the day never gets longer: endurance `strength_and_mobility`, strength `mobility` and strength `catch_all`. If such a step carries a run load (say a jog tagged `catch_all` on a custom weight-loss goal), next week's running or hard-run count could rise above what was checked.
  - Not fixed here, because the Prompt puts the handoff out of scope. Fix: re-run `weekLoadBreaches` after `placeHandoff`, or never place a step whose load names running.
- **Data `DailyTask` doesn't store:** none needed. Both close paths load full rows of the closing week (`routes/goal.ts` review and close-week).
- **A number missing from `limits.ts`:** only the three PSL-15 (7) names; added.
- **A typing goal's prompt or schema:** unchanged.
- **Migration, dependency, frontend:** none.

### Problems found
1. **The handoff edge above** → review decision; backlog item, or M2.2b if it reads the placed week.
2. **The model's measured test step kept without a load counts as easy** (PSL-15 (1) literal, decision 13). Code's measured test counts as hard → feature `decisions.md` (a one-line PSL-15 follow-up).
3. **503 risk on run10k measured weeks** if the model keeps writing two quality runs next to the hard test → O2's log read (count `hard_runs_over_2` / `failed`).
4. **Rest-day steps lose their kind** (MR-15), so a rest-day run without a running number is invisible: neither counted nor making the base unknown. Low; M2.1 asks rest-day runs for a load only through `highLoad` → backlog (small).
5. **Goal create's week 1 still logs `goalId: null`,** because the goal isn't saved yet. Known since B-63; logging the goal id after save, as `logRoadmapTargets` does, would close it → backlog (small).
