### Goal
On a load goal, the first week back after a break runs no more than the person last did: the newest week with any done running, counted by what was done, with no allowance, half of it after a break of 21 days or more, and never held below 30 minutes / 5 km. Not knowing what was run never lifts the limits (RULE-7, PSL-18). Every other week, every goal that is not a load goal, and every close that is not a break is exactly as before.

### Decisions I made
1. **The long break and the floor together.** When both apply, the text is `(half of what they last did, week 3: 40, is 20; never below 30)`. The other option was the plain floor text, which drops the "half". I chose this because the prompt gave no example for the pair, and this one names every number.
2. **A second line in the first-week-back prompt.** The first line is exactly as the prompt gives it. It is followed by M2.2a's "Add up the runMinutes … at most {n} minutes" line, and a km base also gives the limit in minutes. The other option was the single line. I chose this because PSL-17's live check showed that the add-up sentence helps the model meet the total, and a km base would otherwise be silent about a week written in minutes.
3. **Done days of a week written before M2.1 stop the walk at unknown** (PSL-16 (3)'s reading). The other option was passing them over as "no done running". I chose this because both give the same limits (PSL-18 (5)), but "unknown" is the true log line.
4. **The share is decided in `planV2.ts`.** `firstWeekBackBaseOf` takes `percent`. The other option was to read `LONG_BREAK_DAYS` inside `weekLoad.ts`. I chose this so the safety module never imports `weekClose`.
5. **Where the load-goal check gets its target.** `writeWeekAfter` checks against the stored target of the week to be written; `writeNextWeek` uses the target as lowered on read. The other option was to pass a reader callback into `writeNextWeek`. I chose this because lowering never changes a target's family or preset, so the answer is the same, and the read stays in `writeWeekAfter` as the prompt says.
6. ~~The longest-run text on an unknown first-week-back base keeps PSL-16's wording.~~ Replaced by review fix 2.

### Differences from the docs
- **The status of a failed read.** The prompt says it gives a "503". In code, a throw inside `writeWeekAfter` reaches the route's catch, which answers **500** ("Failed to close the week." / the review's 500), the same as any other read there. Nothing is saved either way, and the app treats any 5xx alike (`closeFailed`). As told, I didn't catch it. If a 503 is wanted, it needs a catch, which the prompt forbids.
- **The `02-feature.md` base-week row and PSL-18** match what is built; no change needed.

### Problems found
- **Floor weeks may 503 on run10k (risk).** On a run10k first week back held to the floor (30 minutes total), the model must write short `runMinutes` inside 35–50-minute sessions. A code-made light test step counts its whole `durationMinutes` as running, so the light swap can fail the re-check and the week answers 503. The week is writable, but this wasn't checked live. → O2 / a live check before switching anything, like PSL-17's.
- **No unit on the limit in the retry text.** The text says "the most allowed is 60", with the unit only on "This week's running is 61 minutes", as M2.2a's text does. → `docs/backlog.md` if wanted.

### Ideas
