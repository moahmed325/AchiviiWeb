### Decisions I made
- **The hold line shows whenever a hold applies and next week then shows this week's target**, including when it was already planned at that target. The other option was to show it only when the fallback changed a week. I chose this because RULE-7 asks to say plainly when a target is held, and the line is true in both cases. A next week planned easier than this week is left alone and keeps `AUTO_CLOSE_INSIGHT`.
- **`held` in the log line is logged on every outcome**, as the holds in force (on a fallback, the ones it kept); `error` and `unreadable_targets` log `none`. The other option was logging it on fallbacks only. One field that always means the same thing is simpler to read.
- **The hold copies `input.target` itself** (its metric and unit too) onto the held weeks. The other option was copying only the value onto each planned week. This week's target is what the week shows, so the held week is exactly it.
- **WU-23's and WU-46's code sentences win over the hold line**, as they do over the model's sentence. The Prompt asks for this for WU-23, and I used the same order for next week lowered.
- **`sameUnit` lives in `research/statedTarget.ts`** next to `aliasesFor`, not in a new module. Its only dependency is there.
- **WU-51's reason gives both values** ("from 12 km to 13 km") so the retry knows what happened. I did not add the rule to the prompt itself, because the Prompt didn't ask for it (see Ideas).
- **Scoring keeps `both` as runs 1–2**, so M3.2's numbers stay comparable, and adds `run-3` beside them, not a runs 1–3 total.
- **Tags:** I tagged the 21 accepted sentences by the same standard as runs 1–2: vague but not wrong counts as a match, and a plain miss on held or lowered does not.
