### Context

- **The update.** `planWeeklyUpdate(goal, weekNumber, { userId, reflection, now, timezone })` in `backend/src/lib/weekClose/update.ts` runs only when `updateRuns` says so (`weeklyUpdateEnabled()`: `WEEK_CLOSE_ENABLED` and `WEEKLY_UPDATE_ENABLED` both exactly `true`, weeks 1 to 11, not a break). - **Its database reads.** `historyOf` (`prisma.weeklyReview.findMany`), `weekBeforeOf` (`prisma.dailyTask.findMany`, only with `METHOD_RECOVERY_ENABLED` on and week 2 on) and `countsOf` (`loadReconcileGoal` in `lib/reconcileCore.ts`, then `evaluate` and `weekCounts`; on any failure it sends only the sessions count and `detail: null`). `lib/prisma.ts` uses `global.prisma` when it is set (outside production), so a script that sets `global.prisma` to a small in-memory stand-in **before** it imports any `src/` module can run `planWeeklyUpdate` with no database. - **Light-test goals** (run10k, recomp, speech, spanish): the model sets only the big weeks left (4, 8, 12); code fills the light weeks. WU-47: no hold when next week shows week 12's target.
- **The precedent** is `backend/scripts/recovery-eval/` (method-aware recovery M2.2, `docs/archive/method-aware-recovery/milestones/m2.2-eval.md`): live roadmaps saved to JSON, hand-written answers committed before any scored call, pure scoring with tests, raw results saved so the review can re-score without new calls. `scripts/tag-failure-rate.ts` shows how a script loads `backend/.env` and stops without `GEMINI_API_KEY`.

3. **The expected answers, before any update call runs.** In `expected.json`, per case: the status a coach would give, next week's direction (`raise`, `hold`, `lower`), which hold must apply if any (`far_behind`, `not_logged`, `week_behind`, none), whether code must lower a week (and which), and whether week 12 must stay the final goal. Commit this before step 4 runs and never change it afterwards. If a case turns out to be built wrong, add a replacement case with its own new expected answer and say so; do not edit the old one.
4. **Run it.** `npx tsx scripts/update-eval/run.ts roadmaps | weeks | update | score`. The `update` step sets `global.prisma` to the in-memory stand-in, then imports and runs the real `planWeeklyUpdate` per case. The script does **not** set any switch itself: it refuses to run the `update` step unless `WEEK_CLOSE_ENABLED` and `WEEKLY_UPDATE_ENABLED` are `true` in the shell that runs it, and sets `METHOD_RECOVERY_ENABLED` per case only inside its own process, saying so in the report. It stops with a clear message if `GEMINI_API_KEY` is missing. It saves each case's `PlannedUpdate`, every attempt's raw model answer, the full `[WeeklyUpdate]` and `[Safety]` lines, and the time from start to return, to `run-1.json` and `run-2.json`. Run it **twice**. Never put keys in the repo or the report.
5. **Score (pure functions in `score.ts`, with `score.test.ts`).** Per run and both together:
   - outcomes: accepted, retry_accepted, fallback, of 24;
   - every rejection reason, grouped by check and ranked by count (first attempts and retries apart);
   - safety: weeks code lowered and on which goals; how often the model's first-asked week went above `safeMax`; any returned target that still climbs past a safe step from this week's (must be 0; check with the same climb, not by reading the log); week 12 left as the final goal except where WU-23 lowered it;
   - wording: every saved `insight` passes `sentenceReason` (must be all), and none names a status or says "on track", "behind" or anything meaning failed (RULE-3); then, hand-tagged in `wording-tags.json` after the runs, one tag per accepted case: does the sentence match what happened to next week's target (says held when held, lowered when lowered), and does a week-behind hold name the kind;
   - agreement with `expected.json`: status, direction, the hold, the lowering;
   - the stand-in's counts: how many cases got `detail: null` (should be 0; if not, the stand-in is wrong, not the product);
   - time: median and slowest per case, and the retry's share.
6. **Commands and output.** `score` prints the tables the report needs and writes `score.json`. Raw run files stay in the repo so the review can re-score without new calls.

### Decisions I made
1. **Case weeks written with `writeNextWeek(goal, week − 1, [], …)`**, the real week writer (it makes no database call). Other option: `generateWeekPlan` directly. Why: it is the path a real week takes, light-test session and load goal included. Passing no rows of the week before means a load goal's week has no base week (`no_base`), as for a goal whose base is unknown.
2. **The week before (`weekBeforeOf`) is answered with no rows.** Other option: write the week before live too (24 more week calls). Why: it is read only to see a break that started there, and no case has a break.
3. **Closed weeks older than the 3 history weeks are stored as passed at their own target, with status `on_track`** (light weeks "Done"). Other option: not logged. Why: a coherent past, and `lowerBoundOf` reads them.
4. **Clock and routine:** goal start 2026-08-03, time zone UTC, `now` = 10:00 on the day after the closing week (no gap, no move, no break), 45 minutes a day, `steady`. Other option: today's date. Why: fixed and repeatable.
5. **Raw answers captured by wrapping `fetch` in the script.** Other option: stub `generateStructuredContent`. Why: no `src/` change, and it records exactly what the API returned, 429s included.
6. **Reasons split into first attempt and retry** using the rejection text the retry prompt carries (`splitReasons`). Other option: re-running `checkWeeklyUpdate`. Why: the input isn't exposed without a `src/` change.
7. **Direction measured against this week's target as shown** (a light week shows its next big week's). "Against the plan" is also in `score.json` (`vsPlan`). For deliverables, "hold" means the same text and anything else is "raise".
8. **Lowering agrees when every expected week was lowered** (extra lowered weeks are allowed). Other option: an exact match. Why: how far the re-spread climb gets lowered depends on the model's numbers; the expected answer says which weeks must be.
9. **Holds read from the prompt the product sent** (code's not-logged and week-behind lines), plus far_behind when the status is `far_behind` and next week doesn't show week 12. Other option: recomputing `holdsOf`. Why: it is what the product actually enforced.
10. **Goal and case swaps (before their step's commit, so not "replacements"):**
    - The first book goal failed 4 roadmap calls (week 11 below week 10), so it was swapped for "Finish writing my non-fiction book" (step 1).
    - `guitar-w5-week-behind` was replaced by `spanish-w4-week-behind`: every guitar session holds a new-piece step, so missing them all left 1 of 5 sessions done (far behind, not the clean hold).
    - In 4 "a bit behind" cases, the key sessions were set to done, because missed key sessions are `far_behind` by the prompt's rule.
    - All of this happened before `expected.json` was committed; no case was changed afterwards.
11. **`update --dry`** blanks the key inside the process, to check the stand-in and the recording with no model call; used once before the runs, output not kept. Not asked for; it spends nothing.
12. **The `update` command needs `--run <n>`** so the two runs write `run-1.json` and `run-2.json`. The Prompt's command line shows it without the flag.
