### Context
Verify these; do not trust this prompt.
- **The update.** `planWeeklyUpdate(goal, weekNumber, { userId, reflection, now, timezone })` in `backend/src/lib/weekClose/update.ts` runs only when `updateRuns` says so (`weeklyUpdateEnabled()`: `WEEK_CLOSE_ENABLED` and `WEEKLY_UPDATE_ENABLED` both exactly `true`, weeks 1 to 11, not a break). It builds the `WeeklyUpdateInput`, calls `askWeeklyUpdate` (`lib/ai/weeklyUpdate.ts`: one call, one retry with the reasons, then the fallback), runs the accepted targets through the safety climb (`safeStoredTargets`), swaps in code's sentence when week 12 or next week was lowered (`week12Sentence`, `nextWeekSentence`), logs one `[WeeklyUpdate]` line and returns a `PlannedUpdate` (`outcome`, `status`, `insight`, `coachNote`, `weeks`, `week12`, `lowered`, `readBack`, `reasons`). It saves nothing: `saveWeekClose` does that later.
- **Its database reads.** `historyOf` (`prisma.weeklyReview.findMany`), `weekBeforeOf` (`prisma.dailyTask.findMany`, only with `METHOD_RECOVERY_ENABLED` on and week 2 on) and `countsOf` (`loadReconcileGoal` in `lib/reconcileCore.ts`, then `evaluate` and `weekCounts`; on any failure it sends only the sessions count and `detail: null`). `lib/prisma.ts` uses `global.prisma` when it is set (outside production), so a script that sets `global.prisma` to a small in-memory stand-in **before** it imports any `src/` module can run `planWeeklyUpdate` with no database. Check every query those three paths make and answer each from the case's data.
- **The checks it can reject for** are the reasons `checkWeeklyUpdate` returns (count, kind/metric/unit, below the last result, backwards, above week 12, week 12 changed, the `far_behind`, unlogged-test and week-behind holds, the sentence: `sentenceReason`), plus `no_answer`, `unreadable_targets` and `error`.
- **Light-test goals** (run10k, recomp, speech, spanish): the model sets only the big weeks left (4, 8, 12); code fills the light weeks. WU-47: no hold when next week shows week 12's target.
- **The precedent** is `backend/scripts/recovery-eval/` (method-aware recovery M2.2, `docs/archive/method-aware-recovery/milestones/m2.2-eval.md`): live roadmaps saved to JSON, hand-written answers committed before any scored call, pure scoring with tests, raw results saved so the review can re-score without new calls. `scripts/tag-failure-rate.ts` shows how a script loads `backend/.env` and stops without `GEMINI_API_KEY`.
- **Production has no `[WeeklyUpdate]` lines** (`WEEKLY_UPDATE_ENABLED` is off), so the weeks are hand-made (decided 2026-10-21). In production logs later, a `[WeeklyUpdate]` line with no `[WeekClose]` line for the same goal and week was not saved (the week write failed or the close was lost); this eval has no close, so it scores what `planWeeklyUpdate` returns.
- `backend/vitest.config.ts` has no `include`, so a `*.test.ts` under `backend/scripts/` runs in `npm test`; `tsconfig.json` builds only `src/`.

### Goal
A fixed set of hand-made closing weeks, the expected answer for each written before any scored call, the script that runs the real `planWeeklyUpdate` on them live, and two recorded runs scored for: outcomes and fallbacks, rejection reasons ranked, safety (AC-8), wording (AC-3, RULE-7), status and direction against the expected answers, and time. The numbers tell Mo whether the update is good enough to run inside the automatic close (M3.3, WU-21 (2)). No product code changes.

### Requirements
Put everything under `backend/scripts/update-eval/`. Do the steps in this order, one commit per step; the order is what keeps the answers honest.

1. **The goals (12).** All 10 pathways plus 2 custom goals (one with a number target, one with a deliverable target), in `goals.json` (raw goal, clarify domain, 2 to 3 clarify answers, a starting point where the goal has one). The script makes one live roadmap per goal with `generateRoadmap` (retry a failing one up to 3 times; if it still fails, swap the goal and say so) and saves the stored roadmap, the 12 weeks (target, test, `light`) and, with the recovery profile code uses at create, to `roadmaps.json`. Commit.
2. **The cases (24).** In `cases.json`, each case is one goal at one closing week with what happened, hand-written: the week number, this week's tasks (written live once per case with the existing week writer for that week number and saved, then their done / missed / 10-minute-version states set by hand), the test result or none, the reflection, up to 3 earlier weeks (target, result, sessions done of planned, `updateStatus`), and whether `METHOD_RECOVERY_ENABLED` is on for the case. Together the 24 cases cover at least:
   - ahead (the result beats next week's target), on track, a bit behind, far behind;
   - test not logged (RULE-5's hold), and the same at week 11 (no hold, WU-15);
   - an in-order kind a week behind (the WU-11 hold, the sentence naming the kind), and one only a step behind (must not block a raise);
   - a light-test goal in a light week, in a big week, and in a light week whose next check is week 12 (WU-47);
   - a running goal and a recomp goal where a raise past the safe step is likely (the lowering and `nextWeekSentence`), and one where week 12 has to be lowered (the WU-23 sentence);
   - a deliverable goal held, and one moving on;
   - a reflection that invites a forbidden word ("I missed two runs and failed the test") and one that asks a question;
   - two earlier `far_behind` weeks in the history, and a first week with no history.
   Each case has a one-line `why`. Commit.
3. **The expected answers, before any update call runs.** In `expected.json`, per case: the status a coach would give, next week's direction (`raise`, `hold`, `lower`), which hold must apply if any (`far_behind`, `not_logged`, `week_behind`, none), whether code must lower a week (and which), and whether week 12 must stay the final goal. Commit this before step 4 runs and never change it afterwards. If a case turns out to be built wrong, add a replacement case with its own new expected answer and say so; do not edit the old one.
4. **Run it.** `npx tsx scripts/update-eval/run.ts roadmaps | weeks | update | score`. The `update` step sets `global.prisma` to the in-memory stand-in, then imports and runs the real `planWeeklyUpdate` per case. The script does **not** set any switch itself: it refuses to run the `update` step unless `WEEK_CLOSE_ENABLED` and `WEEKLY_UPDATE_ENABLED` are `true` in the shell that runs it, and sets `METHOD_RECOVERY_ENABLED` per case only inside its own process, saying so in the report. It stops with a clear message if `GEMINI_API_KEY` is missing. It saves each case's `PlannedUpdate`, every attempt's raw model answer, the full `[WeeklyUpdate]` and `[Safety]` lines, and the time from start to return, to `run-1.json` and `run-2.json`. Run it **twice**. Never put keys in the repo or the report.
5. **Score (pure functions in `score.ts`, with `score.test.ts`).** Per run and both together:
   - outcomes: accepted, retry_accepted, fallback, of 24;
   - every rejection reason, grouped by check and ranked by count (first attempts and retries apart);
   - safety: weeks code lowered and on which goals; how often the model's first-asked week went above `safeMax`; any returned target that still climbs past a safe step from this week's (must be 0; check with the same climb, not by reading the log); week 12 left as the final goal except where WU-23 lowered it;
   - wording: every saved `insight` passes `sentenceReason` (must be all), and none names a status or says "on track", "behind" or anything meaning failed (RULE-3); then, hand-tagged in `wording-tags.json` after the runs, one tag per accepted case: does the sentence match what happened to next week's target (says held when held, lowered when lowered), and does a week-behind hold name the kind;
   - agreement with `expected.json`: status, direction, the hold, the lowering;
   - the stand-in's counts: how many cases got `detail: null` (should be 0; if not, the stand-in is wrong, not the product);
   - time: median and slowest per case, and the retry's share.
6. **Commands and output.** `score` prints the tables the report needs and writes `score.json`. Raw run files stay in the repo so the review can re-score without new calls.

### Out of scope

- Turning any switch on in Render (O2). The automatic close (M3.3), break restart (M3.4).

### Checks
- Backend `npm test` (the new `score.test.ts` adds to the count; nothing else changes) and `npm run build`. Measure both on your starting commit first; that is the baseline.

### Done when
Steps 1 to 6 are committed in order; the report gives both runs' tables, the ranked reasons, the safety and wording results, the agreement numbers, the time, two worst-looking sentences quoted with their case, and a short recommendation for M3.3 (go, or what must change first, as a list for Mo to decide).

### Stop if
- `planWeeklyUpdate` can't run on an in-memory goal through `global.prisma` without changing code under `src/`.
- A case's week can't be written live after 3 tries.
- A returned target climbs past a safe step, or an accepted `insight` fails `sentenceReason` (a product bug: report it with the case, don't work around it).
- The runs would take more than about 150 model calls in total.
