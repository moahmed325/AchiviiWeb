### Goal
With `WEEK_CLOSE_ENABLED` on, a day the person was never shown is never missed. Someone back 2 or more days after a week should have started gets the new week starting today, with the plan's end moved later by the same number of days, up to 28 days in total. Everything with a date follows the move.

### Requirements
1. **The gap (RULE-13, WU-20 (5)).** When a close writes week N+1 (by the review or automatically), the gap is the number of days from week N+1's planned start to the local date of the first open that tried to close week N (`closeTriedAt` when `closeTriedWeek` is N; otherwise now), in the person's time zone. Work it out once, before the model call, with the `lib/timezone.ts` helpers.
2. **Moving the plan (RULE-14, WU-13, WU-26).** For a gap of 2 or more days, move by `k = min(gap, 28 − movedDays)`.
   - When k > 0: shift `Goal.startDate` and `Goal.targetDate` by k days and add k to `movedDays`. Week N+1 is written from the shifted start, so it starts on the day they came back (or as near as the limit allows).
   - The shift is saved in the same all-or-nothing save as the close, after the conditional update wins. A losing request saves nothing (WU-27).
   - Week N's stored rows don't change.
   - A gap of 7 or more days is moved the same way here. M1.5 adds what a break adds on top (its length, the note, the choice card past the limit).
3. **Days not offered (WU-13, WU-28 (1)).** Every row of the new week dated before the day it is written (the person's local date) gets `notOffered = true` in the same save. This covers a 1-day gap, the part of a gap the limit couldn't move, and days spent on failed writes.
   - **The day kind (WU-33):** `classifyDays` gives such a row a new kind, `not_offered`.
   - Every consumer treats it like `rest` (never missed, never a gap day, never a carry source or target, no miss line, no swap, nothing in `weekCounts`), **except** that `inOrderQueue` counts its in-order steps as not done, so they queue into the days left.
   - In the report, give a table of every `kind` check you touched or checked, file and line, with the decision for `not_offered`.
   - `weekScore` leaves not-offered days out of the planned count (WU-33).
   - **A week whose every day is not offered** (the planned count is 0, e.g. the limit was already at 28) has no score, and it is never a divide by zero:
     - `RoadmapWeek.executionScore` stays empty (null).
     - The review row stores 0 of 0 with `scorePercentage` 0, because those columns can't be empty.
     - Every screen that shows a week's score treats 0 planned as "not counted": no percentage, never "0%".
     - `phaseGate` reports no benchmark for that week, and no screen shows a benchmark line for it.

### Decisions I made
1. **The stored flag is read in every switch state** (other option: only with the switch on). A day nobody was shown stays never missed after a kill-switch turn-off; with the switch off nothing writes the flag, so other goals are unchanged.
2. **The in-order queue's `toNextWeek` records may sit on a not-offered day's step**, as on a missed day's (other option: make the kind wait, so those steps would never queue). Kept after the review's early look: RULE-17's "never writes into days not offered" means never placing a step there; a record changes nothing shown (test added).
3. **Rest rows dated before the write are flagged too** ("every row"); they still classify as `rest`.
4. **The `[WeekClose]` log line is unchanged**: its `gapDays` still counts to now (an M1.2a test pins it); the move's gap counts to the first try.
5. **The answer's `scorePercentage` stays a number (0) for a week with no score**; the review row's `tasksPlanned` of 0 is the "not counted" signal (other option: `null`, which changes the answer's shape).
6. **"Not counted" copy on the review card**: "Not counted" and "No practice days were offered this week." (other option: a dash). New words, easy to change.
7. **Tapping a not-offered day opens the rest-day view** (review change 2): the card a rest day gets ("Monday's rest", the Rest day badge, "Log recovery complete", no Start, no steps, no 10-minute version), done by giving the card the day with `isRestDay` set and no steps. The stored title stays (the rest view shows the day's own title), so it reads e.g. "Lesson 100" under "Monday's rest". Logging recovery on it changes nothing in the plan (the kind stays `not_offered`, the score leaves it out).
8. **The week writer's "last week" summary leaves not-offered days out** (done/planned, key sessions skipped), so they have no effect on the next week (RULE-13: no status effect).
