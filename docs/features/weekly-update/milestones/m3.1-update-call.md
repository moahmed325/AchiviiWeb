### Goal
With both switches on, a weekly review of weeks 1 to 11 runs one update call before the week call. Code checks its targets (RULE-4) and keeps them safe (RULE-10); the accepted targets, the status, the sentence and the next week, written with the coach's note, are saved together in the close. A rejected or failed update leaves the targets as planned with the neutral line. With either switch off, the review is exactly as today.

### Decisions I made
1. **The climb's base on a light-test goal.** Chose: run the accepted targets through `safeStoredTargets` on the goal as it reads once this week is closed (this week marked `completed`, the shown targets as the closed weeks' values). For a goal without light tests, and for a big week (4, 8), that is exactly "from this week's target"; for a light week it starts from the last big week up to this one (or the starting point), four steps to the next big week. Other option: from the light week's own target (the next big week's current target). Why: that base is looser than the one `safeGoalTargets` uses on read, so a later read would lower what the update stored (a "Stop if"); this way a read can never lower it, and it is never looser than the prompt's reading. The model is told the same maximum.
2. **Text that follows a changed target is saved with it.** Chose: each changed week saves `target` plus `objective`, `keyMilestone` and `test`, rebuilt by the rule M1.3 uses on read (`withTargetText`, pulled out of `safeStoredTargets`): a pathway's own test re-filled, otherwise only the pass mark; a light test unchanged. Other option: save `target` only. Why: with only the target, the Roadmap's objective and the week's test would still name the old number, and the week writer would get a test whose pass mark disagrees with its target. Same rows, no schema change; please confirm this is within "the weeks left's target".
3. **`Goal.roadmap.finalTest` is not changed** when week 12's target changes. Other option: store the rebuilt `finalTest` too. Why: the prompt allows only week 12's `loweredTargets` entry in `Goal.roadmap`. Listed under Problems.
4. **Lower bound.** Chose: the newest measured week up to this one (not jumped, not a light test) whose result is a number in the target's unit (or has no unit). Other option: this week's result only. Why: "what they last achieved"; it also gives the light-test rule (the last big-test result) with one rule.
5. **A kind's sessions** leave out the test day, as the in-order queue does (it never reads the test day). Other option: every practice day holding the kind. Why: otherwise steps behind and sessions are counted over different days.
6. **Deliverables under any hold** (`far_behind`, unlogged test, a kind a week behind) must repeat this week's text exactly. Other option: only `far_behind`. Why: code can't tell a lower deliverable from a higher one, and the other two holds only block a raise.
7. **The sentence check:** empty, any `?`, or a word form of missed / behind / fail (missing, failing, failure...). No length check. Why: section 6's copy rules; "one sentence" is told, not counted.
8. **Week 12's sentence without a stated number** is "Week 12 aims at {safe}, a safe step." (as the app's `week12LineText` words it). Other option: always both sentences. Why: "filled as plan-safety-limits fills `week12Line`".
9. **Week 12's entry** keeps the `model` of an existing entry (from create or found on read), else week 12's current value. It is also stored when an older goal's week 12 was lowered only on read and the update now stores week 12's safe value, so `week12Line` keeps showing.
10. **When the logs are written.** The `[WeeklyUpdate]` line when the update finishes (so M3.2 sees every call, also when the week write fails or the close is lost); the `[Safety]` `lowered_on_update` lines only after the close is saved (they report stored changes).
11. **Unreadable targets** (not 12 readable weeks): the fallback with no model call, `reasons ["unreadable_targets"]`.
12. **Counts when reconcile does not apply:** the review's own count (`weekScore`), other counts 0. Reconcile applies to every plan v2 goal, so this is only a guard.
13. **The model returns whole targets**; code compares metric and unit ignoring case and spaces, and always keeps the current direction.
14. **Kinds listed:** only those with steps still to do, name in lower case. The profile is read as stored; an older goal with no profile gets one in `writeWeekAfter` (after the update), so its first update reads no kinds.
15. **`withUpdatedTargets` leaves `Goal.roadmap` as loaded.** `ensureRecoveryProfile` (in `writeWeekAfter`) stores the roadmap it is given outside the transaction, so giving it the week-12 entry would save it even when the close is lost. Tested.

### Review fixes (WU-46, on top of `6e078a4`)
1. **A hold wins over the lower bound; the bound never goes above week 12** (WU-46 (1), (2)). `boundOf` in `ai/weeklyUpdate.ts` caps the bound at week 12's current target. Under any hold on next week (`far_behind`, an unlogged test, a kind a week behind; none at week 11), next week's floor is this week's target when the bound is above it; the weeks after it keep the bound. The prompt gives the capped bound, and adds "A held week {n} may stay at this week's target instead." only when the bound is above this week's target. Tests: `far_behind` with a 12.5 km result passes at 12 km (and week 5 at 12.2 is still refused); an unlogged test with an older 12.5 km result passes at 12 km; without a hold next week still keeps the bound; a 25 km result with week 12 at 21 km passes at 21 km and the prompt says 21 km.
2. **Next week's safe-step line** (WU-46 (3)): `nextWeekSentence`. When next week is in `lowered` and week 12 is not, the insight is "Next week aims at {formatTarget}, a safe step." The route safety test now expects "Next week aims at Weekly running distance: 13.2 km, a safe step."
3. **No zeros when reconcile can't count**: `UpdateCounts.detail` is null then. The prompt says "Sessions done: {n} of {m}. Key sessions, 10-minute versions, missed and dropped days: not counted." (sessions from `weekScore`). Tested on the prompt line.
4. **The result's unit**: `resultNumber` (now exported) compares units with `aliasesFor` from `research/statedTarget.ts` (exported), both ways round, so "min" = "minutes" and "kilometres" = "km". No stop was needed. Tests in `test/weeklyUpdateResult.test.ts`.
5. **Compare against the read row**: `weeks` holds only weeks whose final target differs from the `safeGoalTargets` row.
