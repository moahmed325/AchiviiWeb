### Goal
With both switches on, a weekly review of weeks 1 to 11 runs one update call before the week call. Code checks its targets (RULE-4) and keeps them safe (RULE-10); the accepted targets, the status, the sentence and the next week, written with the coach's note, are saved together in the close. A rejected or failed update leaves the targets as planned with the neutral line. With either switch off, the review is exactly as today.

1. **When it runs (RULE-1, WU-45 (1)).** Only on the review path, only with `weeklyUpdateEnabled()`, only for weeks 1 to 11, and not on a close that is a break (`move.breakDays` set; M3.4). Otherwise nothing new runs and the review's input, model calls and saved rows are exactly as today (R-3, R-7).
2. **Inputs (RULE-2, WU-30 (5), WU-11).** This week's target and stored or sent test result (a light week's result is "done" with its note, not a number, WU-43 (2)); `weekCounts` for this week, from the same day kinds and carry plan reconcile works out, read only; the reflection; the last 3 weeks (target, result, sessions from their `WeeklyReview` rows, `updateStatus`); the weeks left with their current targets (from `safeGoalTargets`, as `writeNextWeek` reads them); for a number target with a family, the most next week may rise to (`nextSafeStep` from this week's target). With `METHOD_RECOVERY_ENABLED` on, each in-order kind's name, position and steps behind, and whether it is a week behind (code works this out: steps behind ≥ that kind's sessions in the finished week, and ≥ 2).
3. **The call.** A new module (for example `lib/ai/weeklyUpdate.ts`) with prompt 4 trimmed: no extensions, no checkpoint offer, no `retestFirst` (WU-45 (5)). It returns `status`, `nextTargets`, `messageToUser`, `guidanceForNextWeek`. Gemini through the existing cascade, schema and JSON repair as the other calls. On a light-test goal it asks only for the big weeks left (WU-45 (2)).
4. **Code checks (RULE-4, WU-15, WU-20 (3), WU-45).** Reject when: the count is wrong; a week's kind, metric or unit changes; a target is easier than the last result (on a light-test goal the last big-test result; no bound when there is no usable number); a week is easier than the one before; a week before 12 is harder than week 12's current target; week 12 is not its current target; `far_behind` and next week's target is not this week's; any in-order kind is a week behind and next week is higher than this week; the test was not logged and next week is higher than this week (WU-45 (4)); the sentence breaks RULE-7 (WU-45 (6)). None of the holds applies when next week is week 12. Deliverables: the count, still a deliverable, week 12's text unchanged, a held week's text equal to this week's. On a light-test goal "this week's target" is the target the week shows, and code fills each light week left with its next big week's target before the checks. One retry with the reasons; a second rejection, or no answer, is the fallback (requirement 7).
5. **Safety (RULE-10, AC-8, AC-11, WU-23, WU-45 (3)).** After the checks pass, code runs the targets left through the same climb as the roadmap, from this week's target (`safeTargetClimb`; `safeCheckWeekClimb` for a light-test goal's big weeks) and lowers any week that climbs past a safe step. Week 12 lowered only by this is accepted. When week 12 is lowered, its `loweredTargets` entry in `Goal.roadmap` is set (in the close's transaction) so `week12Line` keeps showing, and the sentence is code's: "Week 12 aims at {safe}, a safe step. Your {goal} goal is the next step." (exact; filled as plan-safety-limits fills `week12Line`). Each lowered week logs one `[Safety]` `target_step` line with outcome `lowered_on_update`.
6. **Saved together (RULE-9, RULE-3).** The update runs before `writeWeekAfter`, and the week call gets the new targets and `guidanceForNextWeek` as a coach's note (a new optional prompt line, present only when given: the week prompt is byte-for-byte unchanged without it, R-1 fixture).
