### Goal
A new goal on any of the 10 pathways gets the pathway's hand-written weekly tests. For run10k, recomp, speech and spanish, weeks 4, 8 and 12 have the big test, which measures the target. Every other week has a light test, logged as done plus a note, and shows the next check's target. A custom goal's test follows the light-test rule. Existing goals are unchanged. This is not behind any switch (RULE-19).

### Requirements
Terms: a **split pathway** is run10k, recomp, speech or spanish; **big weeks** are 4, 8 and 12; a **light week** is any other week of a split pathway.

1. **Hand-written tests (WU-43 (3)).** Each of the 10 pathways has its weekly test in its preset file (a new optional field on `CertifiedPresetBlueprint`; shape yours). For a split pathway that means a big test and a light test, as RULE-19 describes them. The other six get one test that measures the target every week. A test's text names the target by filling in that week's `formatTarget(target)` wherever it needs the number, and works for a number target and a deliverable target alike. You write the 10 tests' words: plain, short, no special tools, and no all-out effort except a split pathway's big test. List every one, in full, in the report for review.
2. **Code puts them in.** After `checkRoadmapAnswer` passes, a pure function (for example `withPathwayTests(roadmap, preset)`) replaces each week's model-written `test` with the pathway's, so only code decides the tests. Big weeks and the six other pathways get `passIf` naming the target. Light weeks get the light test with `passIf` exactly "Done as written" and `light: true` on the stored test. `light` is a new optional key in the `RoadmapWeek.test` JSON: new goals only, no migration, and missing means false everywhere. The hand-written tests must pass B-63's roadmap scan. Prove it with a test that runs the scan on every pathway's tests for weeks 1 to 12.
3. **Light weeks show the next check (WU-43 (1)).** For a split pathway, code sets each light week's stored `target` to the next big week's target: weeks 1 to 3 get week 4's, 5 to 7 get week 8's, 9 to 11 get week 12's. Weeks 4, 8 and 12 keep the model's targets, and week 12 is still the final goal. Do this in the same function as requirement 2. It must keep every `checkRoadmapAnswer` rule true; test that it does.
4. **Week 12 is the final test (WU-43 (7)).** For every pathway, `finalTest` matches week 12's test (its instructions, or one sentence made from them).
5. **The week writer (WU-43 (1), (5)).** In a light week, the week prompt says this week's test is the light test, and the target named is the next check's (week n), something to build toward and not to test this week. Tell the writer which session the test belongs to, so it puts that session on test day: run10k the long run, recomp the morning weigh-in, speech the section practice, spanish a speaking session. Add a cheap code check only if one is easy (for example, a run10k test day holds a step with "long run"). If no check is easy, list it under Problems found. WU-42's first-week-back light step stays as it is.
6. **Custom goals (WU-43 (4)).** The roadmap prompt's test lines say this: a test is part of a normal session, needs no special tools and is short, with no all-out effort, no max and nothing to failure. Any harder test (a full mock exam) goes only in weeks 4, 8 and 12. The mock-exam and harder-test lines are rewritten to match. Custom goals get no `light` flag and no target rewrite (requirement 3 is for split pathways only).
7. **Logging a light test.** Wherever a test result is entered (review step, late-test card, the week-close test card's "Log result"), a light week shows the light test, a note field and one button, "I did it". There is no number field and no comparison with the target. It saves `{ value: 'Done', passed: true, note }`, which the server's check already takes (verify). Not logging stays unlogged, exactly as now.
8. **Showing light weeks.** Wherever a week's target sits next to its test or result (the review step, the summary, Today's test day, the Roadmap and Progress weeks), a light week shows its target as "Next check, week {n}: {target}" (exact, with `{n}` the big week and `{target}` from `formatTarget`). A logged light result shows as "Done", plus the note when there is one, and is never set against the target. Weeks without `light` look exactly as now. Use the `components/ui` primitives (Design.md).
9. **Existing goals unchanged (RULE-19).** No migration and no backfill. A stored test without `light` is read as now on every screen and by the week writer.
