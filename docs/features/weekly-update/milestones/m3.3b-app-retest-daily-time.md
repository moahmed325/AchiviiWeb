# M3.3b — The app: re-test lines, the re-test result, the daily-time card

## Prompt

### Context
- M3.3a (merged `4bc9b4d`) built the server side. When both switches are on and the update ran, a close may start the new week with a code-made re-test of the closing week's test (`retestOf` in `backend/src/lib/weekClose/update.ts`; reasons `not_logged`, `two_hard_weeks`, or both, giving one re-test, WU-56). The step is placed by `checkWeekAnswer` in `backend/src/lib/ai/weekPlan.ts`: its title starts "Re-test: ", it is first in order on its day and ranks after the day's lead (WU-57). Only a **measured** re-test stores `retestOfWeek` (the closing week's number) on the new week's row (`retestOfWeekFor`). The easy re-test ("Re-test: an easy version", `EASY_RETEST_STEP`) stores nothing on the earlier week (WU-56 (2) as amended).
- The reason is not stored anywhere. `updateStatus` (`on_track` | `a_bit_behind` | `far_behind`) is stored per week and must never be shown (RULE-3). A week with no stored status is not `far_behind` (WU-53).
- `PUT /api/goal/weeks/:weekNumber/test-result` (`backend/src/routes/goal.ts`) already takes a result for a `completed` week while the open week's `retestOfWeek` names it (the latest wins). The app's client is `logWeeklyTestResult` in `frontend/src/lib/api.ts`; `components/today/LateTestCard.tsx` shows how Today logs a test with `ReviewTestResultStep` / `LightTestEntry` in a `Dialog`.
- Goal responses send full `RoadmapWeek` rows, so the app already receives `retestOfWeek`, `updateStatus` and `dailyTimeAskedAt` (column added in M1.2a, never written so far). The frontend reads none of them yet.
- Daily time is `Goal.routine.dailyMinutes` (options 30, 45, 60, 90: `DAILY_MINUTES` in `frontend/src/components/onboarding/StepSchedule.tsx`; `readRoutine` in `backend/src/lib/planV2.ts`). The week writer reads it through `readRoutine` when a week is written. No endpoint changes the routine today. `RoadmapWeek.plannedMinutes` is set for all 12 weeks at goal create (`roadmapWeekRows`).
- Verify each of these in the code before relying on it.

### Goal
On Today, the person sees why their week starts with a re-test, can log the measured re-test's result, and after two hard weeks is asked once whether their daily time still works (AC-4 Today, AC-5 daily time; RULE-5, RULE-6, WU-7, WU-17, WU-20).

### Requirements
1. **Server works out the re-test (WU-58 (1)).** The goal responses that carry `roadmapWeeks` (go through `presentGoal` or one helper next to it) add `retest: { ofWeek, reason: 'not_logged' | 'two_hard_weeks', logged: boolean } | null`. It is non-null only when the open (`active`) week has `retestOfWeek`. `reason` is `two_hard_weeks` when the `retestOfWeek` week and the week before it both stored `far_behind`, and `not_logged` otherwise, including when both apply (WU-58 (2)). `logged` is described in 2. Pure function with unit tests: each reason, both, none, a week with no status, week 1 as the re-tested week.
2. **Knowing the re-test is logged (WU-58 (3)).** When the test-result route stores a result through the re-test path (the week is `completed` and the open week re-tests it), it adds `retestLoggedInWeek: <open week number>` to the stored `testResult` JSON. This is one extra JSON key, no migration, and no change to any row already stored. `logged` is true when the re-tested week's `testResult.retestLoggedInWeek` equals the open week's number. Every write replaces the whole stored `testResult` (the latest wins), so a later result for that week stored any other way carries no key: the key never survives a write that did not set it. Check that every reader of `testResult` ignores the key, and list each one in the report with how you checked it: at least `isLogged` and `resultNumber` (`backend/src/lib/weekClose/update.ts`), `lastWeekResult` (`backend/src/lib/planV2.ts`), `validateWeeklyTestResult`, the review route, the update's history input, and every screen that shows a result (Progress, Achievement, the Roadmap, the review). Route tests: the key is stored on the re-test path only, never on an open week's own result; a later write replaces it.
3. **The line on Today (AC-4, RULE-5, RULE-6).** On the day that holds the re-test step (the open week's first day whose steps include a title starting "Re-test: " that is not the easy one), while `retest.logged` is false, Today shows one line, as a status line near the close line. The exact words are the copy table's: `not_logged` gives "Last week's test wasn't logged, so we're holding your target. This week starts with a quick re-test so we can adjust."; `two_hard_weeks` gives "The last two weeks were hard to fit in. This week starts with a re-test to find your real level." Not dismissible. Not shown on other days, after it is logged, or when `retest` is null (so never for the easy re-test). The re-test step itself keeps the normal step layout.
4. **The re-test result entry (AC-4, WU-17, WU-56 (2)).** From the re-test day to the end of the open week, while `retest.logged` is false, Today offers "Log re-test result", which opens a dialog like `LateTestCard`'s: the re-tested week's stored test (its instructions and pass mark) and `ReviewTestResultStep`. Save calls `logWeeklyTestResult(retest.ofWeek, …)`, then `refreshGoal()`; on failure it shows "That didn't save. Please try again." and saves nothing later. Reuse `LateTestCard`'s pieces, without a second copy of its dialog logic. A re-test of a light week can't happen (WU-56 (3)): if `test.light` is true anyway, show nothing. The late-test card for the open week's own test is unchanged.
5. **Daily-time check, server (AC-5, RULE-6, WU-7, WU-20 (1)).** The same responses add `dailyTimeCheck: { minutes, shorter: number[] } | null`. It is non-null only when `retest.reason` is `two_hard_weeks`, the open week's `dailyTimeAskedAt` is null, no earlier week of the same run of `far_behind` weeks (counting back from the re-tested week) was followed by a week with `dailyTimeAskedAt` set, and at least one option in 30/45/60/90 is shorter than the current `dailyMinutes` (`shorter` lists those, ascending). New `POST /api/goal/daily-time` with `{ minutes }`: refuses 409 `weekly_update_disabled` while `weeklyUpdateEnabled()` is false (either switch off), before reading anything, like the other new endpoints' `week_close_disabled`; 409 `no_daily_time_check` when `dailyTimeCheck` would be null, and 400 when `minutes` is neither the current value nor in `shorter`. It sets the open week's `dailyTimeAskedAt` to now and, when shorter, `routine.dailyMinutes`, in one transaction. A shorter time applies from the next written week only: the current week's tasks don't change. Route tests for each answer.
6. **`plannedMinutes` (WU-58 (4)).** Find every reader of `RoadmapWeek.plannedMinutes`. If any reader would be wrong for a week written after the change, set `plannedMinutes` on that week as it is written (inside `saveWeekClose`'s transaction, from the routine at write time), without rewriting any other week. Report what you found either way.
7. **Daily-time card on Today (AC-5).** While `dailyTimeCheck` is non-null, Today shows one card: "Does {N} minutes a day still work?" with "Keep {N} minutes" and "Make it shorter". Keep posts the current minutes. Make it shorter shows the `shorter` options (`{M} min`), and choosing one posts it. After a shorter choice, the card is replaced by "From next week, your sessions are {M} minutes." for the rest of that visit. Keep just closes the card. Both refresh the goal. The words are exact. Use the `components/ui` primitives; tests query by role and name.
8. **Switches (RULE-18, AC-19).** With either switch off nothing new shows: `retest` and `dailyTimeCheck` are null because nothing sets `retestOfWeek`, and the endpoint refuses. Add a test with both unset.
9. **Docs.** Update `CLAUDE.md`'s week-close paragraph and `docs/architecture/plan-v2.md` if they describe the re-test's result or the daily time.
