### Goal
Prove every acceptance criterion in each switch state with a named test or e2e spec, fill any gap with a test, run the whole e2e suite, finish the copy table, and leave `CLAUDE.md` and `docs/architecture/plan-v2.md` true. This covers AC-14, AC-19 and all the others.

### Decisions this prompt makes (WU-62, proposed by main - review)
1. **The four switch states:** A = both unset; B = only `WEEK_CLOSE_ENABLED=true`; C = both `true`; D = only `WEEKLY_UPDATE_ENABLED=true`. D must behave exactly like A (AC-19). Each AC is checked in the states where it means something. An AC built for C only also shows that A, B and D don't do it. An AC that has nothing to do with the switches (AC-20, light tests on goal create) is checked once.
2. **Evidence is a test name, not a reading of the code.** Each AC and state cell names a test file and test name, or an e2e spec and test. Where none exists, add a test. Put a gap in the existing file that already tests that area. Use a new `backend/test/weeklyUpdateAcceptance.test.ts` only when no file fits.
3. **A failing AC is a bug to fix only when the fix is small and inside this feature's code**, with a test that fails before the fix and passes after. Anything bigger, or anything that changes the behaviour with a switch off, is a stop.
4. **The app lines and step texts above join section 6's table** word for word as the code has them, each with its situation. "Next check, week {n}: {target}" and "I did it" are AC-20's light-week lines. They go in a short second table, "Light weekly tests", under the first one.
5. **The profile-call kind names** ("Drill block" and the like) are left as they are. Profile calls are off, and whether a broader "reads badly" check is wanted stays undecided (WU-61, Built). Note it under Problems found only if you see a real bad name.
