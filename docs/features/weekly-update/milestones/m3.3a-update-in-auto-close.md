## Prompt

### Context
Verify these; do not trust this prompt.
- **Where the update runs today:** only on the review path (`POST /weeks/:weekNumber/review` in `backend/src/routes/goal.ts`): `planWeeklyUpdate` → `writeWeekAfter(withUpdatedTargets(...), { coachNote, weekBefore })` → `saveWeekClose({ ..., update })` → `logUpdateLowered`. The automatic close (`POST /close-week`, same file) calls `writeWeekAfter` and `saveWeekClose` with no update (WU-45 (1)). `updateRuns` (`weekClose/update.ts`) already returns false for week 12, with a switch off, and for a break (which includes every past-the-limit close).
- **No time limit.** `askWeeklyUpdate` (`ai/weeklyUpdate.ts`) goes through `gemini.ts`, which retries rate limits with no deadline. M3.2/M3.2b runs took 21 to 27 s before a fallback. `gemini.ts` takes no abort signal.
- **Fallbacks.** `runUpdate` applies the holds code can see (`holdsOf`, WU-48) when the model gives no update. `planWeeklyUpdate`'s `catch` returns `fallback(['error'])`, which drops those holds (M3.2b review, finding 3).
- **Unlogged test.** `holdsOf`'s `notLogged` reads `testLogged` (`isLogged(thisWeek.testResult)`), also on a light week, where a light test isn't a result (WU-43). Nothing places a re-test step, and `RoadmapWeek.retestOfWeek` is never written (it exists, from M1.2a's migration).
- **The status.** `saveWeekClose` stores `updateStatus` only when the update has one; the fallback has none (WU-45 (7)). Nothing reads `updateStatus` for RULE-6 yet.
- **Test steps.** `testStepFor` / `codeMadeTestStep` / `LIGHT_TEST_STEP` in `ai/weekPlan.ts`; `TEST_STEP_TITLE` (`/^weekly test\b/i`) in `safety/weekLoad.ts` decides what counts as the week's test step for the load checks and the M1.5b light-step swap.
- **Late results.** `PUT /weeks/:weekNumber/test-result` refuses a `completed` week (`week_closed`) and any week not `active` (B-68).
- **Deliverables.** `WEEKLY_UPDATE_SCHEMA` lets `kind` be `number` or `deliverable` for every goal; M3.2b run 3's top first-attempt rejection was a deliverable week sent as a number (13).

### Goal
With both switches on, the automatic close runs the same weekly update as the review, within a time limit. An unlogged measured test holds the target and the next week starts with a re-test whose result is stored as the earlier week's late result; two `far_behind` weeks in a row start the next week with the same re-test. Deliverable goals get their own schema, and prompt 4 states the WU-51 rule. Server only: the app's lines and the daily-time card are M3.3b.

### Requirements
1. **The update in the automatic close (RULE-1, RULE-18, WU-52).**
   - In `/close-week`'s close (not `{ mode: 'check' }`), run `planWeeklyUpdate(goal, weekNum, { userId, reflection: '', now, timezone })` before `writeWeekAfter`, exactly as the review does: `withUpdatedTargets`, `coachNote`, `weekBefore`, `update` into `saveWeekClose`, `logUpdateLowered` after a won save. Prefer one shared helper over a copy, if it stays small.
   - It runs only when `updateRuns` says so: never for week 12, a break (so never before a past-the-limit choice is answered), or with either switch off. Then the close is exactly as today.
   - **The line:** with an update, the review row's insight is the update's insight; when the close also moved the plan (a short gap, M1.4), it is the move line followed by the update's insight, one space between (`autoCloseInsight(move)` then `update.insight`). With no update, as today.
   - A lost race saves nothing of the update (it is already inside the one transaction).
2. **The time limit (WU-52).**
   - One constant, `WEEKLY_UPDATE_TIME_LIMIT_MS = 15000`, in `weekClose/update.ts`, on both paths. It covers the model call (`askWeeklyUpdate`, both attempts together), not the reads before it.
   - On time out, the update is the WU-48 fallback with code's holds, reasons `['time_limit']`. Use `Promise.race` with a timer that is cleared; don't add abort plumbing to `gemini.ts`. The call left running must not write anything or change the answer.
   - An error thrown by the model call also gets the WU-48 fallback with code's holds (`['error']`). An error before the update's input is built keeps today's `fallback(['error'])` with no holds.
3. **No hold or re-test after a light week (WU-54).** An unlogged test on a light week (`test.light === true`) is not "not logged" for RULE-5: no `notLogged` hold (in `holdsOf`, the prompt's lines and the fallback), no re-test. On a light-test goal only the big weeks 4 and 8 can be not logged. Custom goals and pathways without light weeks are unchanged.
4. **The re-test week (RULE-5, RULE-6, WU-53, WU-56).** Code decides, after the update and before `writeWeekAfter`, whether the new week starts with a re-test of the closing week's test (`retestOfWeek` = the closing week), from these, and from nothing else:
   - **Unlogged (RULE-5):** the update ran, the closing week's test was not logged (measured weeks only, item 3), and next week does not show week 12's target (WU-15, WU-47).
   - **Two hard weeks (RULE-6):** the update ran, its `status` is `far_behind`, and the week before the closing week has a stored `updateStatus` of `far_behind`. A week with no stored status (a fallback, the week a break started in, any week before the switch) is not `far_behind` (WU-53). A fallback has no status, so it never starts one. Not when next week shows week 12's target.
   - Neither when the closing week is a light week (WU-56 (3)), or when the week written would have no practice day before its test day (item 5).
   - Both at once is one re-test (WU-56 (1)). Log it on the `[WeeklyUpdate]` line: `retest <not_logged|two_hard_weeks|not_logged,two_hard_weeks|none>`.
5. **The re-test step (WU-55, WU-56).**
   - Pass the re-test to `writeNextWeek` (a new option, e.g. `retest: { ofWeek, test }`, `test` being the closing week's stored test) and on into `generateWeekPlan`. The prompt's WRITE THE WEEK tells the writer that the first practice day starts with a re-test of week N's test, which code adds, and to plan the rest of that day around it, shorter.
   - Code places the step first on the week's first practice day that is offered (not rest, not not-offered) and is not the test day. It is code-made with fixed text: title "Re-test: " plus the same first-clause rule as `testStepFor` (it must not match `TEST_STEP_TITLE`, so it never counts as the week's own test step), the stored test's instructions and pass mark, half the daily minutes like `testStepFor`, the day's other steps trimmed as `testStepFor`'s day is (`keepTopSteps`). A recogniser beside `codeMadeTestStep` reads it back from its fixed text (a stored step too).
   - **Safety (WU-55):** on a load goal it counts in the week checks like the code-made measured test step: on a running goal a hard run of its minutes; the weeks 1 to 3 rules and the text scan read it like the measured test step. On the last attempt, when the only refusals are on the re-test step (alone, or with the test step under M1.5b's rule), code swaps it for a fixed easy re-test step ("Re-test: an easy version", like `LIGHT_TEST_STEP`, its own recogniser) and keeps the swap only when the swapped week passes the week checks again (as the M1.5b swap does). A refusal on any other step is as today. Log the swap as a `[Safety]` line with outcome `light_retest`. An easy re-test's logged result counts as a light test (not a result, WU-43).
   - The re-test step carries no `load` (code-made, like the code-made test step) and is never moved by the handoff placement or the carry planner as a step of a kind (treat it as the test step is treated there; check what that is).
6. **Storing it.** In `saveWeekClose`'s transaction, the new week's row gets `retestOfWeek` (both paths; null otherwise). A jumped week never gets one. No migration: the column exists.
7. **The re-test result (WU-17).** `PUT /weeks/:weekNumber/test-result` takes a result for a `completed` week when the goal's open (`active`) week has `retestOfWeek` equal to it, and stores it as that week's `testResult` (the latest wins, as today). Every other `completed` or non-active week is refused exactly as today. The next update reads it as part of the trend (`historyOf`); check that it does, and that the new week's own test is still its result.
8. **The deliverable schema (03-phases M3.3 note (a)).** When this week's target is a deliverable, the update call gets its own schema: `nextTargets` items with `kind` fixed to `deliverable` (enum of one) and `description` required, no `metric`, `value` or `unit`; the prompt's nextTargets line shows only the deliverable shape. Number goals keep today's schema and line, byte for byte. `checkWeeklyUpdate` is unchanged.
9. **The WU-51 rule in prompt 4 (note (b)).** One line in the target rules: don't say held, kept or stays when next week's target moves on, or goes up, raised or rises when it stays the same. Both schemas get it.
10. **Tests.**
