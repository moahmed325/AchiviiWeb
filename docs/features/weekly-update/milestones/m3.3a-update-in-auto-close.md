## Prompt

### Context
Verify these; do not trust this prompt.
- **Where the update runs today:** only on the review path (`POST /weeks/:weekNumber/review` in `backend/src/routes/goal.ts`): `planWeeklyUpdate` → `writeWeekAfter(withUpdatedTargets(...), { coachNote, weekBefore })` → `saveWeekClose({ ..., update })` → `logUpdateLowered`. The automatic close (`POST /close-week`, same file) calls `writeWeekAfter` and `saveWeekClose` with no update (WU-45 (1)). `updateRuns` (`weekClose/update.ts`) already returns false for week 12, with a switch off, and for a break (which includes every past-the-limit close).
- **No time limit.** `askWeeklyUpdate` (`ai/weeklyUpdate.ts`) goes through `gemini.ts`, which retries rate limits with no deadline. M3.2/M3.2b runs took 21 to 27 s before a fallback. `gemini.ts` takes no abort signal.
- **Fallbacks.** `runUpdate` applies the holds code can see (`holdsOf`, WU-48) when the model gives no update. `planWeeklyUpdate`'s `catch` returns `fallback(['error'])`, which drops those holds (M3.2b review, finding 3).
- **Unlogged test.** `holdsOf`'s `notLogged` reads `testLogged` (`isLogged(thisWeek.testResult)`), also on a light week, where a light test isn't a result (WU-43). Nothing places a re-test step, and `RoadmapWeek.retestOfWeek` is never written (it exists, from M1.2a's migration).
- **The status.** `saveWeekClose` stores `updateStatus` only when the update has one; the fallback has none (WU-45 (7)). Nothing reads `updateStatus` for RULE-6 yet.
- **Test steps.** `testStepFor` / `codeMadeTestStep` / `LIGHT_TEST_STEP` in `ai/weekPlan.ts`; `TEST_STEP_TITLE` (`/^weekly test\b/i`) in `safety/weekLoad.ts` decides what counts as the week's test step for the load checks and the M1.5b light-step swap.
- **Late results.** `PUT /weeks/:weekNumber/test-result` refuses a `completed` week (`week_closed`) and any week not `active` (B-68).
- **Deliverables.** `WEEKLY_UPDATE_SCHEMA` lets `kind` be `number` or `deliverable` for every goal; M3.2b run 3's top first-attempt rejection was a deliverable week sent as a number (13).

### Goal
With both switches on, the automatic close runs the same weekly update as the review, within a time limit. An unlogged measured test holds the target and the next week starts with a re-test whose result is stored as the earlier week's late result; two `far_behind` weeks in a row start the next week with the same re-test. Deliverable goals get their own schema, and prompt 4 states the WU-51 rule. Server only: the app's lines and the daily-time card are M3.3b.

4. **The re-test week (RULE-5, RULE-6, WU-53, WU-56).** Code decides, after the update and before `writeWeekAfter`, whether the new week starts with a re-test of the closing week's test (`retestOfWeek` = the closing week), from these, and from nothing else:

   - **Two hard weeks (RULE-6):** the update ran, its `status` is `far_behind`, and the week before the closing week has a stored `updateStatus` of `far_behind`. A week with no stored status (a fallback, the week a break started in, any week before the switch) is not `far_behind` (WU-53). A fallback has no status, so it never starts one. Not when next week shows week 12's target.
   - Neither when the closing week is a light week (WU-56 (3)), or when the week written would have no practice day before its test day (item 5).
   - Both at once is one re-test (WU-56 (1)). Log it on the `[WeeklyUpdate]` line: `retest <not_logged|two_hard_weeks|not_logged,two_hard_weeks|none>`.
5. **The re-test step (WU-55, WU-56).**

   - Code places the step first on the week's first practice day that is offered (not rest, not not-offered) and is not the test day. It is code-made with fixed text: title "Re-test: " plus the same first-clause rule as `testStepFor` (it must not match `TEST_STEP_TITLE`, so it never counts as the week's own test step), the stored test's instructions and pass mark, half the daily minutes like `testStepFor`, the day's other steps trimmed as `testStepFor`'s day is (`keepTopSteps`). ### Decisions I made

1. **Re-test day:** the first offered practice day before the test day (the test day is the last practice day, so this is "not the test day"); none when there is none. Other option: any offered non-test day, also after the test. Why: a re-test after the week's own test is pointless, and item 4 says "before its test day".
2. **Decided before the week is written:** the layout and the not-offered date are code's, so `retestOf` knows the day exists before the call and the `[WeeklyUpdate]` line logs the final answer. `retestOfWeek` is still stored only when the written week holds the step. Other option: decide after the write and log separately. Why: one line, one place.
3. **"The update ran" = `planWeeklyUpdate` returned an update, fallbacks included,** so an unlogged test starts a re-test after a time out or error too. Other option: only when the model answered. Why: RULE-5 is a fact code reads, as WU-48's holds are.
4. **Minutes:** the re-test takes half the daily minutes and the model's steps are fitted into the other half. Other option: the test day's rule (fit everything to the written minutes). Why: that would squeeze the re-test to about a third; the re-test day is a full practice day.
5. **The re-test day's 10-minute version** is the rest of the day's (the lead step passing over the re-test), and with a profile takes that step's kind. Other option: MR-15 as written (the priority-1 step, now the re-test). Why: a 10-minute re-test is not a re-test, and a `weekly_test` 10-minute version would be fixed for the carry planner.
6. **Safety (please confirm):** the easy swap is also tried when a *week* limit fails and the week holds a measured re-test (for example a third hard run), not only for refusals on the re-test step; it is kept only when the swapped week passes every week check again. Other option: M1.5b's rule exactly (no week breach before the swap). Why: the re-test's hard run is the likeliest breach on run10k (week 5 or 9 after an unlogged week 4 or 8, with two quality sessions); without this, both attempts fail and every open shows "Couldn't get your next week ready". The swap only lowers the effort; a week still over a limit fails as before (tested).
7. **PSL-3 on the re-test:** a rule the re-tested week's stored test text breaks is let through on the re-test step (logged `test_text`), as on the test step. Other option: refuse it. Why: "the text scan reads it like the measured test step".
8. **`dayQualityFailures` passes over the re-test step** (`taskRules.ts`). Other option: leave it in. Why: its text is the stored test's; a short stored instruction ("Type the passage and log", under 25 characters) or a title ending in "log" made a retry reason the model can't fix, on every first attempt.
9. **The easy re-test's result is read as light from the closing week's own tasks** (the week holding the easy step and its `retestOfWeek`), not from a marker. Other option: add a flag to the stored `testResult`. Why: no stored-data change. Limit: only the next update knows; see Problems.
10. **Removed `WeekCallInput.retestFirst`** (and its LAST WEEK lines and soft "Re-test" check), replaced by `retest`. No caller ever set it. Other option: keep both. Why: two ways to ask for a re-test would drift.
11. **The re-test's test is the week as read (`safeGoalTargets`)**, what the person was shown; the same as the stored test unless it was lowered on read.
12. **The PUT endpoint reads the asked week and the open week in one query** (`OR`). Other option: a second query only for a completed week.
