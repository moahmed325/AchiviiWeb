### Goal
The review can't be applied twice or to an old week, in any switch state. Behind `WEEK_CLOSE_ENABLED`, the server can close a week whose last day has passed, exactly as the review would but without a reflection, safely under repeats and races. The one migration for the feature is in.

### Requirements
1. **The review's guard (B-59, WU-27; every switch state).** A review of a week that is not `goal.currentWeek`, or not `active`, is refused with 409, code `week_closed`, and no model call. The winner is decided inside one transaction that holds all the review's writes (the review row, week N closed, week N+1's tasks, week N+1 active, `currentWeek`) and starts with a conditional update of week N from `active` to `completed`. If that update touches no row, nothing is saved and the answer is the same 409. The model call stays outside the transaction. Give `saveWeekTasks` (or a sibling) a way to run inside a caller's transaction without changing its behaviour for other callers. The review also sets the new `closedBy: 'review'` and `closedAt`. For a 409 `week_closed`, the modal says exactly "This week's review is already saved." and refreshes the goal. Everything else in the review's response and behaviour stays as it is (R-3).
2. **The migration (WU-21, WU-26 to WU-28).** One migration, additive only, with the fields in M1.1's Report section 8 (`Goal`: `movedDays`, `closeTriedAt`, `closeTriedWeek`; `RoadmapWeek`: `closedBy`, `closedAt`, `jumped`, `breakDays`, `updateStatus`, `retestOfWeek`, `dailyTimeAskedAt`; `DailyTask`: `notOffered`) plus `RoadmapWeek.closeLineSeenAt DateTime?`. Every field nullable or with a default. Only `closedBy`, `closedAt`, `closeTriedAt` and `closeTriedWeek` are written in this milestone. If no local database is available, write the SQL with `prisma migrate diff` into a new migration folder.
3. **The switches (RULE-18).** One small module with `weekCloseEnabled()` and `weeklyUpdateEnabled()` (the second is true only when both are exactly `'true'`). Both are listed in `render.yaml` (`sync: false`) and `backend/.env.example` with a comment, as the others are. Add a CLAUDE.md paragraph for the week close.
4. **One shared close.** The review and the automatic close save through the same function, so a week closed either way is stored the same, apart from the reflection, the test result and `closedBy`. An automatic close saves the review row with reflection `''` and the insight "Next week is ready. Your targets stay as planned." (exact), computes the score as the review does, and writes next week with `writeNextWeek` exactly as the review does (targets as planned, the profile and the week before as today).
5. **The close endpoint** (`POST /api/goal/close-week`, behind `WEEK_CLOSE_ENABLED`):
   - **Switch off:** `{ due: false }`, no reads beyond the goal, no writes.
   - **Not plan v2:** 409 `not_plan_v2`, as everywhere (ND-21).
   - **Due** only when `goal.currentWeek`'s week is `active` and its last day's close (`dayCloseInstant`, the user's bedtime and time zone) has passed (RULE-8, WU-30). Otherwise `{ due: false }`, fast, no writes.
   - **First attempt:** when due, record `closeTriedAt` and `closeTriedWeek` unless they already name this week (RULE-9).
   - **Check mode:** with `{ mode: 'check' }`, answer `{ due: true, weekNumber, testLogged }` without closing (for M1.2b's test card).
   - **Close** (the default): run the shared close. The response matches the review's shape for the new week, plus `closedBy: 'auto'`.
   - **Week 12:** mark week 12 completed (`closedBy: 'auto'`, `closedAt`), write no week and no review row (RULE-11).
   - **Week cannot be written:** 503 with "Couldn't get your next week ready. Please try again." (exact). Nothing is saved except `closeTriedAt` and `closeTriedWeek` (and the profile, as the review already does).
   - **Lost the race:** a request that loses the conditional update saves nothing and answers 200 with the week as already closed.
6. **Log line.** One line per close, by review or automatic: `[WeekClose] goal <id> week <n> by <review|auto> gapDays <d> ms <t>`, where `gapDays` is the number of days from the new week's planned start to now (0 when on time).
7. **Tests.**

   - **R-2:** reconcile's body after the week change is the same whether the week was closed by an on-time review or by an automatic close on the morning after the week ended. That includes `weekHandoff`'s result when reconcile has (today's order) or has not (the close-first order) written `toNextWeek` records onto the finished week before the handoff reads it.

### Decisions I made
- **A lost race on the close endpoint answers `{ due: false, alreadyClosed: true, weekNumber }`.** Other option: repeat the winner's body, which needs a second read of what the winner saved. The loser saved nothing, and M1.2b only needs to know there is nothing left to do before reconcile.
- **The close's success body adds `due: true`** to the review's shape plus `closedBy: 'auto'`, so M1.2b reads one field for every answer. **Its `testResult` is the week's stored result** (or null). Other option: always null, as the review returns only what it was sent. The stored one is what the week closed with.
- **With the switch off the endpoint answers before reading the goal** (after auth). Other option: read the goal first. The prompt allows reads up to the goal; none is cheaper.
- **Week 12's automatic close also stores the score and empty notes** on the week, as every close does; only the week and the review row are skipped (RULE-11). Other option: write only `status`, `closedBy` and `closedAt`.
- **The modal reloads the goal when it closes, not at once**, and its button becomes "Done" (the dialog's own X is already named "Close"). Other option: reload at once. That re-renders the still-open modal as next week's review with this error under it. It also clears the saved draft for that week.
- **The reload is `refreshGoal` (GET `/active`), not `reloadPlan`** (reconcile plus goal). The week was closed elsewhere, and that load already reconciled; the prompt says "refreshes the goal".
- **The first try is recorded with a conditional `updateMany`** (only when `closeTriedWeek` is not this week or `closeTriedAt` is empty), in check mode too. Other option: read, then write; two racing first tries could then overwrite the earlier time.
- **"The last day" is the latest stored task date of the open week**; a week with no stored rows is never due. Other option: work it out from `startDate`. The stored rows are what the screens show.
- **The `[WeekClose]` line never fails a saved close** (try/catch, and `gapDays` returns 0 for an unreadable start). Found while running the old review tests: a fixture with no `startDate` made the log throw after the save and turned a saved review into a 500.
- **The server's `week_closed` message stays "This week has already been reviewed."** (shared with the late-test PUT); the modal maps the code to its own copy. Other option: change the server text.
- **`ms` in the log** is measured from just after the guard (the model call plus the save), the same in both routes.
