# Missed Sessions — M1.1 Repository Verification (EV-1)

**Milestone:** P1 / M1.1 (read-only)
**Date:** 2026-10-03
**Status:** COMPLETE, with 7 decisions needed (section 5) and 2 findings that change the plan (section 1)
**Repository state:** `main` at `1ecbff2`. Only this report was added by M1.1.

## 1. Summary

The plan holds up on most points, but two findings change P1 and P2:

1. **The app has no user-timezone day boundary.** `DailyTask.date` is written as a UTC date string, and the frontend decides "today" from the UTC date. `backend/src/lib/timezone.ts` exists and is tested, but no production code imports it. `User.timezone` is stored but unused. OD-1 ("sleepTime + 2h, capped at 04:00, in the user's timezone") therefore cannot be applied on top of the current date model without a decision (ND-1).
2. **Completing the 10-minute version is stored exactly like a full session.** There is no flag, so OD-2 ("10-minute version counts as done but not as key-session done") is not currently possible without a new marker (ND-3).

Also corrected: a weekly-review route for v2 goals already exists (F-5), and the late-test idea in M4.1 does not fit how the test result is stored today (ND-4).

## 2. Answers to R1-R13

### R1. Sleep time and timezone
- `sleepTime` and `wakeTime` live inside `Goal.routine`, a JSON **string** column (`schema.prisma`, `routine String @default("{}")`). Written at goal create in `backend/src/routes/goal.ts:302-309`: `wakeTime` (default `07:00`), `sleepTime` (default `23:00`), `busyHours`, `preferredSlot`, `dailyMinutes`, `planVariant`, `commitments`.
- `readRoutine` (`backend/src/lib/planV2.ts:90`) parses the string but its `RoutineShape` type only declares `dailyMinutes`, `planVariant`, `preferredSlot`. It would need extending to read `sleepTime`.
- Timezone is **not** in the routine. It is `User.timezone String @default("UTC")` (`schema.prisma:15`), sent by the frontend at sign-in (`frontend/src/context/AuthContext.tsx:92-97`) and selected in `routes/auth.ts:10-17`.
- If either is missing: sleep time falls back to `23:00` at create time; timezone falls back to `"UTC"`.

### R2. `DailyTask.status`
- It is a free `String` with default `pending`. No enum, no validation.
- `PATCH /api/goal/tasks/:taskId` (`goal.ts:584-612`) accepts **any** string and sets `completedAt` only when status is `completed` (clears it for `pending`).
- Values written in code: `pending` (`planV2.ts:75`, `goal.ts:229,915`) and `completed`. No `skipped` or `missed` exists.
- Readers: backend compares `=== 'completed'` in the review counts (`goal.ts:727,789`), `planV2.ts:104,145,148` (key sessions skipped = `status !== 'completed'`). Frontend has about 55 status comparisons across about 25 files (task, week, and goal statuses mixed), including `lib/today.ts`, `journeyAdapter.ts`, `achievement.ts`, `Today.tsx`, `useTaskActions.ts`, and the journey and progress components.
- Impact of a new persisted `missed` value is **UNKNOWN per site** and likely wide. See ND-2.

### R3. Steps and the minimum version
- `DailyTask.detailedSteps` is a JSON **string** array. Backend `DetailedStep` (`backend/src/lib/ai/goalDecomposer.ts`): `stepNumber`, `title`, `durationMinutes`, `instructions`, `focusCue`, `pitfallToAvoid`, optional `passMark`, `output`, `timing`, **`priority`** (1 = most important, unique within the day; the test step gets 0), plus layer and resource fields.
- `rankSteps` (`weekPlan.ts:275-281`) rewrites priority as a unique rank, so "priority-1 step" and "lowest priority step" are well defined for v2 days.
- `minimumVersion` is a `Json` column holding one step object (`schema.prisma`, `DailyTask.minimumVersion`).
- A per-step `highLoad` flag needs **no migration** (it is inside JSON), but: the model only emits fields in `WEEK_RESPONSE_SCHEMA` (`weekPlan.ts:114-140`), and `checkWeekAnswer` normalizes the output, so both must be extended.
- Drift: the **frontend** `DetailedStep` type (`frontend/src/types/index.ts`) has no `priority` field even though the backend stores it.

### R4. Day types and "next eligible day"
- `DailyTask.isRestDay`, `isKeySession`, `isTestDay` (booleans) and `date` (string).
- `weekLayout` (`weekPlan.ts:45-60`) sets rest days from the plan variant and marks the **last practice day** as the test day.
- Weeks are 7 consecutive days **from the goal start date**, not Monday-based (`weekStartFor`, `planV2.ts:33`, uses `setDate` in server-local time).
- Next eligible day = same `weekNumber`, later `dayNumber`, `!isRestDay && !isTestDay`. The test day is always the last practice day, so the practice day before it has no eligible receiver and drops.
- **Next week's rows do not exist yet.** They are created only when the review runs (`saveWeekTasks`, `planV2.ts:168`, which deletes and recreates the week). So nothing can ever carry across a week boundary. The Feature Definition's drop rule already covers this.

### R5. Active-goal route
- `GET /api/goal/active` (`goal.ts:434-493`) is a **pure read**. It loads the goal with all roadmap weeks, daily tasks, and reviews, then returns `presentGoal(...)`. No writes.
- A reconcile there would turn a GET into a write, with a risk of double application from two open tabs. See ND-6.

### R6. `yesterdayUncompleted`
- `Today.tsx:275`: `isYesterdayPending(tasks, now) && task is today's && task.status === 'pending'`.
- `lib/today.ts:138-152`: looks back exactly one **UTC** day and requires status `pending` on a non-rest day.
- It renders a callout (`Today.tsx:442-448`): "Yesterday's step wasn't completed… Don't try to double up". It is purely frontend: nothing persists, nothing moves, and anything older than yesterday is ignored.
- `Today.test.tsx:500` and `WeeklyReviewModal.test.tsx:672` assert the word "missed" never appears.

### R7. "Mark today missed" and "swap day"
- **None found.** Searched `frontend/src` and `backend/src` for `markMissed`, `swapDay`, `swap.*day`, `missed`. Only marketing copy (`Faq.tsx:22`, `Product.tsx:10`) and preset prose.
- Preset prose promises behavior that does not exist: "Missed Tuesday? It shifts automatically into an open weekend buffer" (`presets/run10k.ts:528`, similar in `guitar.ts:544`, `saas.ts:546`).

### R8. Weekly update
- **Partly exists.** `POST /api/goal/weeks/:weekNumber/review` (`goal.ts:689+`) handles v2: it computes the score (practice days completed / planned), writes the next week with `writeNextWeek`, saves the review, marks the week completed, stores `testResult`, and returns `phaseGate` (`benchmarkMet` at 80%).
- `writeNextWeek` (`planV2.ts:112-153`) already passes `keySessionsSkipped` and done/planned counts to the week call. Its comment says: "Until prompt 4 exists there is no coach's note and targets stay as planned."
- **Not built:** on_track / a_bit_behind / far_behind status, `nextTargets`, checkpoint offer, `retestFirst` logic, extensions. Searched backend for those names: no matches.

### R9. `timezone.ts`
Exports (`backend/src/lib/timezone.ts`): `isValidTimezone`, `normalizeTimezone` (falls back to `UTC`), `getZonedDateString`, `getUserTodayDateString`, `getZonedTimeParts` (returns date string, hours, minutes, minutes-from-midnight, weekday), `getZonedDayBounds` (UTC instants for a zoned day's start and end, DST-aware via `Intl`). It has a unit test (`backend/test/timezone.test.ts`) and **no production importer**. It is enough to compute "sleepTime + 2h capped at 04:00" for a given local date, but needs a small wrapper.

### R10. The 10-minute version
- Shown in the Focus modal: `FocusSessionModal.tsx:40,246-247` (state `isMinimumVersion`), `FocusStepRunner.tsx` ("Low energy - do the minimum" button), `FocusCompletion.tsx` ("Minimum complete"). Today also has a reveal button ("The 10-minute version", `Today.test.tsx:248`).
- Completion calls the same `onCompleteSession(reflectionNotes)` (`FocusSessionModal.tsx:165`). The flag is **not passed on**, so the stored result is identical to a full session (`status: completed`). It cannot be told apart in the data.

### R11. High-load steps

- Presets reach users through the **v2 week call** (steps are model-written) and only use their hand-written plans on the v1 fallback (`saveV1PresetGoal`). A flag added to preset files would not affect v2 steps. See ND-5.

## 4. Day-boundary detail (supports ND-1)
Task dates come from `date.toISOString().split('T')[0]` (`weekPlan.ts:52`) while the weekday uses `getDay()` (server-local). The frontend's "today" is the UTC date (`lib/today.ts:todayKey`). For a user in UTC+3 (e.g. Addis Ababa) a day therefore rolls over at 03:00 local; for a user in the US it rolls over in the evening. The review is also due when every task date is before today's UTC date (`isWeekReviewDue`, `lib/today.ts:155-166`).
