**Status:** COMPLETE

## 1. Summary

- **New endpoint (ND-4).** `PUT /api/goal/weeks/:weekNumber/test-result` logs the week's test result into `RoadmapWeek.testResult` and nothing else. It does not change the week's status, write the next week, or call a model.
- **The review keeps it.** Both review paths (plan v2 and plan v1) used to write `testResult: null` whenever a review came without a result. They now leave the stored result alone. A result sent with the review still replaces it.
- **Pre-filled review.** `WeeklyReviewModal` starts the test-result step from the week's stored result, then from the local draft.
- **The card (UX-3, AC-8).** After test day, while the result is not logged and the week is not reviewed, Today shows one card: "This week's test is still open". Its "Log my result" button opens the existing result form in a `Dialog`. Saving calls the endpoint and refreshes the goal, so the card goes.
- **Unchanged:** no schema change, no change to the carry rules or the ND-15 switch, and old goals (plan v1) never show the card.
- **Today.tsx** gets one import and one self-contained element (`<LateTestCard … />`) after the review-due card. Everything else for the card lives in new files, to stay clear of the parallel M3.3 work.

## 7. Discrepancies and decisions

1. **"Closed" for a test day already marked done.** R4 defines the close as reconcile classifying the day `missed` or `done`. Reconcile classifies a completed day `done` as soon as it is completed, before its close. So a test day completed without logging a result shows the card that same day. That follows R4 as written. It is also useful: the result can only otherwise be entered in the review. Flagged because the objective says "after test day closes".
2. **Rest day today.** R8 lists "a rest day today" among the conditions without saying which way it goes. The card is not a miss message (AC-5 is about those), and RULE-7 gives the test grace until the week closes. So the card shows on a rest day too. Tested.
3. **Feature Definition wording.** UX-3 says "Take the test now" and RULE-7/AC-8 say "until the next week opens". The prompt's exact strings and its window (until the review, which is what closes the week today, per 04-phases M4.1) are used.
4. **Clearing in the review cannot remove a logged result.** Per R2, a review sent without a result keeps the stored one. If the user presses "Clear benchmark entry" in the review and submits, the stored result stays. The adaptation screen then shows no result for that review, because it uses the response or the local value. Not changed; recorded for P5.
5. **The review's response is unchanged.** Its `testResult` is still the result sent with the review, or null ("everything else unchanged"). The frontend already falls back to the week's stored value when updating its local goal.
6. **Validation before ownership.** A malformed body answers 400 before the week is looked up, as the M2.4 actions do (401, 400, 404, 409).
7. **Week numbers.** A week that does not exist in the user's active goal, or a non-numeric week, answers 404.
8. **Where the window logic lives.** It is in a new `lib/lateTest.ts`, not `lib/today.ts`, to keep clear of the parallel M3.3 work.

No STOP condition applied:
- the test and its result are stored only on `RoadmapWeek` (`test`, `testResult`);
- keeping the result conflicts with no documented rule (OD-1a only makes it optional on the review);
- the window is decided from stored data plus reconcile;
- no schema change was needed.
