## Prompt

### Context
M2.2's eval failed RULE-19 (report and review in `milestones/m2.2-eval.md`). Templates and safety passed, but the profile call renames most kinds, and the week call writes warm-ups, logging and the test day's warm-up and review as their own steps with other kinds. Once carry acts on kinds (M3.1a), a workout could move without its warm-up and the test's warm-up could move away from the test. MR-25 fixes this here, then runs the eval again. Verify these facts; do not trust this prompt.

- Profile prompt: `buildProfilePrompt` in `backend/src/lib/recovery/profileCall.ts`, "WRITE THE PROFILE" point 2 says "You may rename, add or remove kinds". `checkProfileAnswer` checks the answer.
- Week prompt: `backend/src/lib/ai/weekPlan.ts`. The base prompt's "WRITE THE WEEK" asks for the test step "with a short warm-up before it ... and a short step after it ... that compares the result with the target". `kindsBlock` (only with a profile) already says a move-kind step "starts with its own short warm-up ... inside its instructions".
- Test day in `checkWeekAnswer`: only steps whose title matches `TEST_STEP` get `weekly_test`; the other test-day steps keep the model's kind.
- Fixtures: `test/fixtures/weekPrompt.before-m2.1.txt` (no profile; must not change) and `weekPrompt.with-profile.txt` (changes on purpose).
- The eval: `backend/scripts/recovery-eval/` (`run.ts roadmaps | profiles --run N | weeks | score`, `score.ts`, frozen `answers.json`; `run.ts` refuses to run if `answers.json` changed).

### Goal
Profiles keep the template's kind ids where the job is the same, every test-day step is Weekly test, warm-ups and logs stay inside their session's step, and the eval has been run again on the same answers.

### Read first
- `docs/features/method-aware-recovery/02-feature.md`: RULE-3, RULE-6 to RULE-8, RULE-19
- `docs/features/method-aware-recovery/decisions.md`: MR-15, MR-16, MR-24, **MR-25**
- `milestones/m2.2-eval.md` (Report and Review), `milestones/m2.1-tag-steps.md` (Report)

### Requirements
1. **Keep template ids (RULE-3).** The profile prompt says: a kind that does the same job as one of the chosen template's kinds keeps that kind's id (its name and description may be adjusted to the goal); only a new kind gets a new id; a removed template kind is simply left out. Add a soft reason in `checkProfileAnswer` when no kind id matches the chosen template's ids at all (one retry with the reason; on the last attempt it gives way). Do not add a hard check.
2. **Every test-day step is Weekly test (RULE-7).** With a profile, code sets `weekly_test` on every step of the test day, not only the step titled "Weekly test: ...". Without a profile, nothing changes.
3. **Warm-ups, cool-downs and logs inside their step (RULE-8).** With a profile only, the week prompt says a warm-up, cool-down or log of a session is written inside that session's step, never as a step of its own (the test day keeps its warm-up and review steps; requirement 2 covers them). Add a soft reason for a practice-day step whose title starts with a warm-up, cool-down or logging word (pick a short, tested word list), naming the step. Soft: it gives way on the last attempt, like the other soft reasons. Without a profile, the prompt and checks are exactly as today.
4. **No-profile path unchanged.** `weekPrompt.before-m2.1.txt` passes unchanged; `weekPrompt.with-profile.txt` is updated on purpose.
5. **The eval again.** Do not change `answers.json` or `score.ts`'s rules. Keep every M2.2 result file unchanged.
   - Profile runs 3 and 4 (`profiles --run 3`, `--run 4`) with the new code, scored as before.
   - New weeks for the same 6 goals, saved to new files (for example `weeks-2.json`). **Write and commit the new gold tags from the steps alone before the model's tags are saved to the repo**: have `run.ts weeks` keep the model's tags out of the repo until you pass a flag, so the order shows in `git log`.
   - Score both runs and the new tags; the RULE-19 table goes at the top of the report with M2.2's numbers beside them.
6. **Tests.** The profile prompt's new lines; the soft id reason (fires, gives way on the last attempt); every test-day step tagged `weekly_test` with a profile and untouched without; the warm-up word check (fires, gives way, no false hit on ordinary titles); both fixtures.

### Out of scope
- Loosening MR-24's scoring, or editing `answers.json` (MR-25).
- RULE-4's continue catch-all for deliverable goals (MR-25 point 4).
- Switching the profile call on (O1, Mo). Any carry or recovery behavior (M3.1a). B-21, B-27.

### Checks

- Run backend `npm run typecheck`, `npm test`, `npm run build`, on your starting commit first (the baseline) and at the end. The frontend should be untouched; say so.
- Live runs need `GEMINI_API_KEY` in `backend/.env`. Never put keys in the repo or the report. If Gemini's rate limit (429) stops a run, wait and rerun that goal; say so.

### Done when
Requirements 1 to 4 are in place with tests, both fixtures pass, the eval has run again (runs 3 and 4, new weeks and tags in the order above) and its table is in the report, and CI is green.

### Stop if
