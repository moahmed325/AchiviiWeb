## Prompt

### Context
M1.2 built the profile in `backend/src/lib/recovery/`, and M1.3a saves one on every plan v2 goal with no model call (read both reports in `milestones/`). This milestone adds the **profile call**: a model call that adapts a template to a custom goal. It ships **switched off**; until M2.2's eval passes and Mo agrees (O1), custom goals keep their keyword template. Verify these facts; do not trust this prompt.

- From M1.3a: `makeGoalProfile` and `isDeliverableTarget` (`recovery/forGoal.ts`), `ensureRecoveryProfile` (`recovery/store.ts`), and `recoveryProfileAtCreate` in `backend/src/routes/goal.ts`. Today both the create and the review paths pass the week-12 deliverable fact to `profileFailures` for every profile.
- Goal creation order in `POST /create` (`goal.ts`): roadmap (`generateRoadmap`), then week 1 (`generateWeekPlan`), then the profile (`recoveryProfileAtCreate`), then `saveV2Goal`. The stream sends `step` events (`method`, `plan`) that the generation screen shows.
- Model calls: `generateWithOneRetry(prompt, system, schema, accept, label)` in `backend/src/lib/ai/retry.ts` gives two attempts and sends the rejection reason on the second; `generateStructuredContent` in `gemini.ts` runs the Gemini-then-Groq cascade. `generateRoadmap` (`ai/roadmap.ts`) is the model to follow, and `backend/test/roadmap.test.ts` shows how tests mock `gemini.js`.
- Switches: `carryEnabled()` reads `MISSED_SESSIONS_CARRY_ENABLED === 'true'` per request (`backend/src/lib/reconcileCore.ts`); it is declared in `render.yaml` with `sync: false`, and `backend/test/reconcileCarry.test.ts` checks that declaration.

### Goal
A checked profile call exists and can be run on its own (M2.2 scores it). With its switch on, a new custom goal is saved with the profile it makes; with the switch off (the default), nothing changes. MR-22's fix is in.

### Requirements
1. **MR-22.** Pathway profiles and unchanged templates are saved without the deliverable check, at creation and at the review. The check applies only to a profile the call made. (MR-22)
2. **The profile call.** A function, callable on its own, that takes the goal text, the clarify domain (optional), the clarify answers, the roadmap's method (name, summary, rules), its phases and its 12 weekly targets, and returns a checked profile or a failure. The model sees all 13 templates (their kinds, actions, flags, rest gap and return rule) and answers with the template it picked plus the adjusted profile: it may rename, add or remove kinds, change actions and flags, and change the rest gap and return rule, within RULE-4. Code adds RULE-5's two kinds itself; the model never writes them. (RULE-3)
3. **Checked, retried, then the template.** The answer is checked with `profileFailures`, including the deliverable fact. One retry with the reasons (as `generateWithOneRetry` does). If both attempts fail: the template the model picked, unchanged, when it picked a valid one; otherwise the keyword template. A half-made profile is never saved. (RULE-4, MR-4, MR-14)
4. **The switch.** `CUSTOM_RECOVERY_PROFILES_ENABLED`, read per request, on only when exactly `true`; declared in `render.yaml` with `sync: false`, with a test like the carry switch's. Off: no profile call anywhere. Never turn it on from code or tests. (03-phases section 3, O1)
5. **Wired into creation, before week 1.** For a custom goal with the switch on, the call runs after the roadmap and before week 1 (M2.1 will need the kinds for week 1). Pathway goals never call it. Move the existing keyword-profile step before week 1 too, so both paths make the profile in the same place. No new stream `step` event, no change to what the generation screen shows. A failed call never fails creation. Older goals at the review keep the keyword template (MR-14).
6. **Tests.** The call with a mocked model: a good answer is saved with RULE-5's kinds added; a bad first answer is retried with the reasons; two bad answers give the picked template unchanged, or the keyword template when no valid template was picked; a deliverable goal whose answer has a non-continue catch-all is rejected; the model writing a Weekly test kind itself is handled. Creation: switch off makes no call; switch on calls it for a custom goal only, before week 1; a pathway goal never calls it; a failed call still creates the goal. MR-22: a pathway goal with a deliverable week 12 is saved with its profile. The `render.yaml` declaration.
