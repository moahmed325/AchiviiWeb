## Prompt

### Context
Custom goals now get a keyword-picked template (M1.3a). The profile call exists but is switched off (M1.3b), and the week call tags every step with a kind (M2.1). This milestone measures both against hand-written answers, so Mo can decide whether to switch the profile call on (O1). It changes no product code. Verify these facts; do not trust this prompt.

- Profile call: `generateRecoveryProfile(input)` in `backend/src/lib/recovery/profileCall.ts`. It never throws, and returns `{ profile, source: 'model' | 'picked_template' | 'keyword_template', pickedTemplate }`. It does not read `CUSTOM_RECOVERY_PROFILES_ENABLED` itself (the caller in `routes/goal.ts` does), so a script can call it directly.
- Its input (`ProfileCallInput`): goal text, clarify domain, answers, the roadmap's method, phases and 12 weekly targets. The deliverable fact comes from week 12's target (`isDeliverableTarget`, `forGoal.ts`).
- Profile helpers in `backend/src/lib/recovery/`: `templateProfile`, `pickTemplate`, `profileFailures`, `withFixedKinds`, `TEMPLATE_IDS`. The 13 templates are in `reference/domain-templates.md`.
- Week call: `generateWeekPlan` and the pieces `scripts/tag-failure-rate.ts` already uses (`buildWeekPrompt`, `checkWeekAnswer`, `weekResponseSchema`). That script is the model for this one: it loads `backend/.env`, makes live roadmaps and writes weeks.
- Roadmaps: `generateRoadmap` (`lib/ai/roadmap.ts`). Live roadmaps sometimes fail their checks (backlog B-21), so retry a failing one.
- Custom means: `findPresetForGoal` finds no pathway, and `screenQuery` (`research/safetyFilter.ts`) does not refuse it.
- Gemini is the only provider now (ND-22).
- `backend/vitest.config.ts` has no `include`, so a `*.test.ts` under `backend/scripts/` runs in `npm test`. `tsconfig.json` builds only `src/`.

### Goal
The eval set, the script and one recorded result against RULE-19, scored the way MR-24 says, plus how long the profile call takes.

### Requirements
Put everything under `backend/scripts/recovery-eval/`. Do the steps in this order, with one commit per step, because the order is what makes the answers honest (MR-24).

1. **The 26 goals.** Two custom goals per template (all 13, including `general`), each with a raw goal, a short clarify domain and 2 to 3 clarify answers, in `goals.json`. Pick goals a coach would place in one template without doubt. A check fails if any goal matches a pathway or is refused by the unsafe screen.
2. **Their roadmaps.** A script step makes one live roadmap per goal and saves the profile call's inputs to `roadmaps.json` (retry a failing roadmap up to 3 times; if one still fails, swap that goal for another of the same template and say so). Commit.
3. **The answers, before any profile call runs.** In `answers.json`, for each goal: the right template and a hand-written profile. Start from the template and change it only where this goal clearly needs it, with a one-line `why` per change. Each kind may list `aliases` (other ids or names that mean the same kind). Every answer passes `profileFailures` with the goal's deliverable fact. Commit this before step 4 runs, and do not change it afterwards (MR-24).
4. **Score the profile call.** The script runs the real `generateRecoveryProfile` on each goal and scores the saved profile as MR-24 says: right template (out of 26), action agreement (out of all answer kinds except `weekly_test` and `fixed_time_session`), unsafe results, and how many came from `model`, `picked_template` or `keyword_template`. Also score `pickTemplate` alone on the same 26 goals as a baseline. Run it **twice**, and record both runs.
5. **Time it.** For each profile call, record the time from start to result, including the retry. Report the median and the slowest.
6. **The 6 weeks.** Choose 6 of the goals on 6 different templates, including one with a high-load kind and one with a game-and-review step. The script writes week 1 for each with its answer profile, and saves the steps **without their kinds** to `weeks.json` and the model's kinds to `weeks.model-tags.json`. Write `weeks.gold-tags.json` from `weeks.json` alone, without opening the model's tags, then commit it.
7. **Score the tags.** Agreement over practice-day steps, leaving out the steps code tags itself (the test step and the 10-minute version), as MR-24 says.
8. **Scoring code with tests.** The scoring is pure functions (`score.ts`) with a test file next to it: kind matching by id, name and alias; a missing kind counts as a disagreement; each unsafe case; template and tag counts.
9. **Commands.** `npx tsx scripts/recovery-eval/run.ts roadmaps | profiles | weeks | score`. The script stops with a clear message if `GEMINI_API_KEY` is missing. Never put keys in the repo or the report. Save each run's raw results as JSON next to the script, so the review can re-score them without new calls.
