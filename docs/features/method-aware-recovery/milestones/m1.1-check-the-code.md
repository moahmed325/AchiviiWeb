#### 4. The kind list in the week call
- **Schema:** turn `WEEK_RESPONSE_SCHEMA` into `weekResponseSchema(kinds: string[])`. Add a step property `kind: { type: 'string', enum: [...kinds] }`, required, where the kinds are the profile's kinds plus "Weekly test" and "Fixed-time session" (RULE-5). Keep the constant (built with no enum) for the test at `weekPlan.test.ts:262`, or update that test.
- **Gemini:** `responseJsonSchema` accepts `enum` on a string. But `gemini.ts:142-144` drops the whole schema after any 400 INVALID_ARGUMENT, so even Gemini can return a free-text kind.
- **Groq:** `groq.ts:104` pastes the schema into the prompt, so the enum list reaches the model as text, unenforced.
- **So the check is the only guard for both.** Put it in `toStep` (read `raw.kind`, trimmed, matched to the list) and `checkWeekAnswer`. Every practice-day step with a missing or unknown kind becomes a reason like the others ("Day 3 step 2 has kind 'Cardio'; use one of: ..."). The retry already sends the reason back (`retry.ts:16`).

Exceptions code can fill safely: the test step (RULE-7: always "Weekly test") and the test step code adds itself (`:390`). Open points: a rest-day light step, and the minimum version (section 11, Q7).
- **The `highLoad` field:** keep it required and keep `isHighLoadStep`. It becomes "this step is hard" (RULE-7) instead of "drop this step" (ND-5).
- **The goal-level rule (`markHighLoad`, `:465`):** with a profile, skip `markHighLoad` and let the kinds decide. Without a profile (RULE-18 goals), keep it. `isHighLoadGoal` stays for old steps (`carryForward.ts:274`). A conflict to settle: a step flagged `highLoad` whose kind is continue (section 11, item 10).
- **The prompt:** add the kind list with one line per kind (name and a short description from the profile), plus RULE-8's line ("a step of a move kind starts with its own short warm-up"). #### 5. Order and rest gaps in the carry planner
- **What stays pure:** all of RULE-9 to RULE-14 can be pure functions in `carryForward.ts` (or a new `methodRecovery.ts`). Input: `CarryInput` plus the profile. Output: `CarryPlan` extended with `letGo`, `continued` (with receiving task), `noRoom`, and multi-day `shifts`.
- **Kind and action of a step:** `actionOf(step, profile)` returns null when the step has no kind or the profile is missing, and null means today's path (RULE-18). The test step is always fixed. A `highLoad` step is always hard (RULE-7).
- **RULE-9 (move):** today `lead` = the P1 step (`:269`). The new rule takes the highest-priority step whose kind moves (the "highest priority" is the lowest `priority` number). Then it looks for a receiving day that passes the RULE-12/13/14 checks.
  - **Conflict with ND-17:** ND-17 fixes exactly one receiving day so a later reconcile can never carry a step that was dropped earlier. RULE-9 says "the next day that passes is used instead".
  - **Proposal:** keep it stateless. The receiving day is the first later practice day of the week, not the test day, that passes the checks, judged against the week **as written plus stored markers**. If that day is closed, done or taken, drop the step (as today). Mo must agree (Q2).
- **RULE-12 (fixed):** `fitCarriedStep` must never remove a fixed step (add it to the "never replaced" list with the P1 and test steps). A day holding a fixed step can still receive a carry if the fixed step survives. The rule "no step is carried onto it" reads as "onto the fixed step's place", not the whole day; that needs confirming (Q9).
- **RULE-13 (order):** "the next step of the same kind" = scan the later days of the same week in date order for a step whose `kind` equals the moved step's kind. Order = date, then `stepNumber`.
  - The shift moves each later step of that kind into the next same-kind step's place. Each displaced step must pass the fit rule on its new day, because the steps can differ in minutes and no day may get longer.
  - The last one goes to `noRoom`.
  - **This writes up to N days in one operation. Today's `writeCarries` (`reconcileCore.ts:102`) writes each day on its own and skips a lost race.** A half-written shift would duplicate or lose a lesson. The shift needs one `prisma.$transaction` with a CAS per touched day, as the swap already does (`goal.ts:632-644`), and every touched day needs a marker so it is idempotent.
- **RULE-14 (rest gap):** a pure `restGapOk(days, profile)` over the week after the change.
  - Each day gets a "hard" flag (any hard step). Measure the gap in calendar days between hard days, counting done days too.
  - **Across the week boundary:** the last day of every layout is a rest day (`restDayIndices`: index 6 in all three, `weekPlan.ts:28`). So a hard Monday sits 1 full day after the previous Saturday. A rest gap of 2 would need last week's days too. They are loaded already (reconcile loads all `dailyTasks`).
  - **RULE-13 against RULE-14:** strength is both hard and in order (template 2), so a shift can break a rest gap. Which rule wins is not decided (Q10).
- **Swap (RULE-14, RULE-12, RULE-13):** a pure `swapAllowed(week, a, b, profile)`. Swap the two days' contents in memory, then run `restGapOk`, the fixed check (refuse any day with a fixed step), and an order check (the same-kind order by date must be unchanged). Call it in `goal.ts:615` next to today's checks. Also return the allowed day ids in the reconcile body, so the browser stops computing `swapWith` itself (`today.ts:306`).
- **What touches the guarded writes:** only `writeCarries` (the new multi-day shift transaction and the continue marker write). The swap transaction's shape does not change.

#### 6. Continue
- **Where it lives:** a marker on the receiving step inside `detailedSteps`, `continuedFrom: { taskId, date }`, like `carriedFrom` (ND-13). The words "Pick up where {Weekday} stopped." are worked out from the date on screen (ND-16), and are never written into `instructions`. That keeps the copy in the frontend and the step's text unchanged.
- **Day length:** the marker changes neither `durationMinutes` nor the steps, so the day never gets longer (RULE-10).
- **Shown:** Today (`Today.tsx:623`, above the step's instructions) and Focus (`FocusSessionModal.tsx:225`, `FocusStepRunner.tsx:47`) read `step.continuedFrom`.
- **Idempotent:** written with the same CAS on the receiving day (`status` + `detailedSteps` unchanged). `handledTaskIds` must treat the source of a `continuedFrom` marker as handled, so it is never planned again. With the carry switch off, nothing is written; the plan only reports it.
- **Open points:**
  - (a) A swap copies `detailedSteps` (`goal.ts:555-558`), so the marker would travel with the step, possibly onto a day **before** its source. Suggest refusing the swap of a day holding a continue marker, as `holds_carry` does today.
  - (b) A later carry onto the same day must not remove the marked step. The fit rule must treat it as "never replaced", or keep the marker.

#### 8. Old steps and old goals
