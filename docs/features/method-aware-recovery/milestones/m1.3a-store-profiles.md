## Prompt

### Context
M1.2 built the recovery profile as pure code in `backend/src/lib/recovery/` (read its report in `milestones/m1.2-profiles-and-templates.md`). This milestone saves a profile on every plan v2 goal, with **no model call** and no change the person can see. Verify these facts; do not trust this prompt.

- From M1.2: `profileForPathway(presetId)` (`recovery/pathways.ts`), `templateProfile(id)` (`recovery/templates.ts`), `pickTemplate(...)` (`recovery/pickTemplate.ts`), `profileFailures(profile, { deliverableGoal })` and `readRecoveryProfile(roadmap, facts)` (`recovery/profile.ts`).
- Goal creation: `POST /create` in `backend/src/routes/goal.ts` finds the preset with `findPresetForGoal(rawGoal) || findPresetForGoal(clarifiedOutcome)` (around `:223`) and receives the clarify `domain` in the body (`:166`, used at `:232`). `saveV2Goal` (`:92`) writes `Goal.roadmap` from `storedRoadmap(roadmap, answerList)` (`backend/src/lib/planV2.ts:27`).
- `StoredRoadmap` (`planV2.ts:18`) has no `recovery` field; the 12 weeks' targets live in `RoadmapWeek` rows, not in the stored roadmap, so the week-12 target kind must be read from the generated roadmap (`roadmap.weeks`) at creation and from the week-12 `RoadmapWeek.target` for older goals.
- Older goals: the only place a later week is written is the weekly review route, which calls `writeNextWeek` (`goal.ts`, around `:949`). The goal's preset id is never stored; `isHighLoadGoal` (`backend/src/lib/highLoad.ts`) re-matches it from the goal's text.

### Goal
Every new plan v2 goal is saved with a checked profile under `recovery` in `Goal.roadmap`, and an older goal gets one at its next weekly review without ever blocking that review. Nothing uses the profile yet.

### Requirements
1. **The stored roadmap holds the profile.** `StoredRoadmap` gets an optional `recovery` field. Reading a stored roadmap without it keeps working exactly as today. (MR-9)
2. **Pathway goals at creation.** A goal whose preset matched is saved with `profileForPathway(preset.id)`. (RULE-2)
3. **Custom goals at creation.** A custom goal is saved with `templateProfile(pickTemplate(...))`, using the clarify domain from the request (when present), the goal text and the roadmap's method name. No model call. (RULE-3, MR-13, MR-14)
4. **Checked before saving.** The profile is checked with `profileFailures`, with `deliverableGoal` true when the generated roadmap's week-12 target is a deliverable. A profile that fails is not saved (the goal is saved without one, which means RULE-18) and the reasons are logged with `console.warn`. Goal creation never fails because of the profile. (RULE-4, MR-21)
5. **Older goals at their next weekly review.** In the review route, before `writeNextWeek`, a plan v2 goal whose stored roadmap has no readable profile gets one: the pathway's if its text matches a preset, otherwise the keyword template (no domain is stored for older goals). It is checked as in 4 (the deliverable fact from the week-12 `RoadmapWeek.target`) and saved into `Goal.roadmap`, keeping every other field. Any failure is logged and the review carries on exactly as today. Do not pass the profile to `writeNextWeek`; M2.1 does that. (RULE-1, MR-14)
6. **Nothing else changes.** No response body, prompt, carry, swap or screen behavior changes. `GET /active` will now include `roadmap.recovery`; check that the frontend type and every screen ignore it.
7. **Tests.** Creation saves a pathway profile (one pathway) and a custom keyword profile (sourdough gives General practice, a domain-only match gives its template); a failing profile is not saved and creation still succeeds; the deliverable fact reaches the check; the review gives an older goal a profile and keeps the rest of the roadmap; a review on a goal that already has one does not rewrite it; a failure while making the profile does not change the review's result.

### Out of scope
- The profile model call and its switch: M1.3b.
- Passing kinds to the week call, or any `kind` on steps: M2.1.
- Carry, swap, reconcile, routes other than create and review, and any screen: M3.1a onwards.
- Storing the preset id or the clarify domain as new fields (no migration in this feature).
