## Prompt

### Context
Every plan v2 goal now has a recovery profile (M1.3a, M1.3b; reports in `milestones/`). This milestone makes the week call tag every practice-day step with one of the goal's kinds. Nothing acts on the tags yet (M3.1a). Verify these facts; do not trust this prompt.

- Week call: `backend/src/lib/ai/weekPlan.ts`: `WeekCallInput` (`:82`), `WEEK_RESPONSE_SCHEMA` (a constant, `:116`; `highLoad` required on every step), the prompt builder, `toStep` (`:262`, builds each step field by field, so an unknown field is lost), `checkWeekAnswer` (`:340`; on the last attempt soft reasons give way (`:460`) and a missing test step is added by code), the minimum version (`:406-418`), `markHighLoad` (`:465`, a physical preset goal gets every step marked).
- `backend/test/weekPlan.test.ts:274-276` compares the built prompt with `test/fixtures/weekPrompt.before-m2.1.txt`, and `:262` reads `WEEK_RESPONSE_SCHEMA`.
- Callers: goal create in `backend/src/routes/goal.ts` (the profile is now made just before week 1, by `recoveryProfileAtCreate`), and the weekly review, which calls `ensureRecoveryProfile(goal)` (`backend/src/lib/recovery/store.ts`) and then `writeNextWeek(goal, ...)` (`backend/src/lib/planV2.ts`). **`ensureRecoveryProfile` writes the profile to the database but not to the in-memory `goal`**, so `writeNextWeek` cannot see a profile made at that moment.
- Profile helpers: `readRecoveryProfile` and `actionOf` (`backend/src/lib/recovery/profile.ts`); kind ids are snake_case and include `weekly_test` and `fixed_time_session`. `DetailedStep.kind` is already an optional field (`backend/src/lib/ai/goalDecomposer.ts`).
- Model calls: Gemini can drop the schema after a 400 (`gemini.ts:142-144`) and Groq never enforces it, so the code check is the only real guard.

### Goal
When a goal has a profile, every saved practice-day step carries a valid kind id from it, or the week is not saved. When it has none, the week call is exactly as today.

### Requirements
1. **The profile reaches the week call.** `WeekCallInput` takes an optional profile. Goal create passes the profile it made; the weekly review passes the goal's profile, including one `ensureRecoveryProfile` has just made (return it, or read it again). (RULE-6)
2. **No profile: no change.** Without a profile, the prompt, the schema and the checks are exactly as today; the existing prompt fixture test passes unchanged.
3. **Schema and prompt with a profile.** The schema becomes a function of the profile: each practice-day step requires `kind`, an enum of the profile's kind ids. The prompt lists each kind (id, name, one-line description) and says: a step of a move kind starts with its own short warm-up; work that only makes sense together (such as a game and its review) is written as one step. Do not show the model the actions. Add a second prompt fixture for the profile case. (RULE-6, RULE-8, MR-20)
4. **Kept on every step.** `toStep` keeps `kind` as the profile's kind id (an exact id, or an exact name matched case-insensitively and mapped to its id).
5. **The hard check.** With a profile, any practice-day step with a missing or unknown kind is a reason, naming the day, the step and the allowed ids. It is a hard reason: it does not give way on the last attempt, so two failures mean the week is not saved, at the weekly review and at goal creation alike. (RULE-6, MR-5, MR-16)
6. **What code sets itself.** The test step, and a test step code adds, get `weekly_test`. Rest-day steps carry no kind. The 10-minute version takes the kind of the day's priority-1 step. (RULE-7, MR-15)
7. **High load.** With a profile, skip `markHighLoad`'s goal-level marking: the model's per-step `highLoad` stays, and the kinds decide the rest (RULE-7). Without a profile, keep it exactly as today.
8. **Measure the tag failure rate (MR-16).** A script (not run in CI) that writes sample weeks with the real models: week 1 for each of the 10 pathways and for 4 custom goals on different templates, using their saved profile shapes. It reports, per week, whether the first attempt failed the kind check, whether the second did, and the overall rates. Run it if `backend/.env` has `GEMINI_API_KEY` or `GROQ_API_KEY`, and put the numbers in the report; if not, say so. Never put keys in the repo or the report.
9. **Tests.** Schema with and without a profile; the prompt fixture for each case; `toStep` keeps an id and maps a name; a missing, an unknown and a rest-day kind; the hard check stays on the last attempt; the test step and the minimum version's kind; `markHighLoad` with and without a profile; create and review pass the profile, including the one just made at the review.

### Out of scope

- Requirement 2 cannot hold (the no-profile prompt or schema would have to change).

### Differences from the docs, open questions, carry-overs
- **Question for Mo: Groq and "Day N is missing".** On Groq, no week was saved in the profile run. The cause was the day check, not the kind check. It may also happen without a profile, but that is unmeasured. Next step: once the Groq limit resets, run `npx tsx scripts/tag-failure-rate.ts --groq --no-profile`.
  - If the baseline also fails, this is an existing Groq problem: the fallback can't write weeks at all. That belongs in the backlog.
  - If the baseline passes, the profile's longer prompt or schema breaks Groq, and M2.1 should not merge until that is fixed.
- **Rest-day steps:** the schema requires `kind` on every step, rest days included, because the schema cannot tell rest days apart. Code drops a rest-day kind and never checks it.
- **The test day's 10-minute version gets `weekly_test`,** because the test step is the day's priority-1 step after ranking (MR-15 says "the kind of the day's priority-1 step"). So M3.1a will treat a test-day minimum version as fixed.
- **"Move" kinds for the warm-up line** are the profile's kinds whose action is `move`. The line names their ids but never says "move". A `highLoad` step of a continue kind (treated as move by `actionOf`, MR-11) is not covered by the warm-up line.
- **The kind reasons list at most 8 problems,** like the soft reasons. The second attempt sees those 8.
- **Prompt changes are visible at once** (03-phases section 3): every new week for a goal with a profile now gets the kinds block and the warm-up rule as soon as this merges. Mo should be told when it merges.
