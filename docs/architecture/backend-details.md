# Backend details

The full backend description, moved out of `CLAUDE.md` on 2026-10-24 so it is read only when a task needs it. Code is the authority when this disagrees with it.


`src/index.ts` mounts `/api/health`, `/api/auth`, `/api/goal`, `/api/billing`. The Lemon Squeezy webhook (`/api/billing/webhook`) is mounted **before** `express.json()` with `express.raw()` so its signature can be verified against the raw body; keep that order. CORS allows `CLIENT_ORIGIN` (comma-separated), localhost :5173/:3000, and any `*.vercel.app` origin.

Auth: the frontend signs in with Supabase and sends the access token as `Authorization: Bearer`. `lib/supabaseAuth.ts` verifies it, and `routes/auth.ts` resolves it to a Prisma `User` by `auth_user_id`, linking an existing user by email the first time.

Goal creation (`POST /api/goal/create` in `routes/goal/create.ts`; B-102 split `routes/goal.ts` into `routes/goal/`):

1. **Clarify** (`lib/ai/clarify.ts`, `POST /api/goal/clarify`) turns the raw goal into a clarified outcome, a domain and follow-up questions.
2. **Preset match** (`findPresetForGoal`): the 10 certified pathways in `lib/ai/presets/` (run10k, guitar, saas, spanish, recomp, youtube, book, deepwork, chess, speech) give the roadmap a fixed method. Any other goal is custom and needs Pro (`authorizeNewCustomGoal`).
3. **Roadmap** (`lib/ai/roadmap.ts`, `generateRoadmap`): one model call picks the method (or keeps the preset's) and writes the final goal, the phases, each week's `focus` and, for a goal counted in one number, its `measure` (`metric`, `unit`, `direction`) with `startingPoint.value` as today's level (null without a measure). No weekly targets, tests or final test since 2026-10-30 (ND-33). Goal text that matches the unsafe-framing rules in `research/safetyFilter.ts` (`screenQuery`) is refused with a 422 before any model call, and a method the model rates below 3 on safety is rejected (twice: 422). `checkRoadmapAnswer` checks the phases cover the plan's weeks with no gaps, exactly the plan's weeks, 5 to 8 rules, the chosen method among the candidates, that `finalGoal` keeps every number the person typed in their goal (`statedNumbers`, not lengths of time; soft, sent back once; not on a shorter plan, which may aim at a safe point on the way), and holds a next plan's starting point to the level the person typed (`measuredStart`, sent back once, replaced on the last attempt; `sameUnit` compares spellings, never conversions). A preset's method text still names its old weekly tests; the prompt tells the model the plan has none.
4. **Recovery profile** (`lib/recovery/`, docs/archive/method-aware-recovery): before week 1, the goal gets a checked profile saying what each kind of step does when its day doesn't happen, stored under `recovery` in `Goal.roadmap`. The profile call reads each week's focus and the goal's measure (`profileCall.ts`); the deliverable check it used to make on week 12's target is gone with the targets. A pathway gets its hand-written profile; a custom goal gets a keyword-picked template, or the profile call when `CUSTOM_RECOVERY_PROFILES_ENABLED` is exactly `true` (`sync: false`; on in production since 2026-10-28, O1). Only the carry planner acts on it, and only behind `METHOD_RECOVERY_ENABLED` (see Missed sessions below). Actions: move, continue, let go, fixed and (B-38) restart, for a timed process such as sourdough: a missed step moves nothing and the kind's next session gets a continue marker with `restart: true` (its own line, `restarted`, and "Start the process again from its first step"); the `process` template, picked by words like sourdough, ferment, kombucha and brew, has the restart kind `process_step`. Due dates (B-39): the week writer may give a step `dueDate` (YYYY-MM-DD, kept only when it is a real date, `dueDateOf`) when an outside deadline sets it. A missed one moves only to a day on or before it, earliest first, in both planners; when none is left and the date is before today, nothing moves, the drop reason is `due_date_passed`, the method outcome `due_passed` and its line says the deadline passed. The handoff never hands on a step whose date fell in the finished week. The profile call (2026-10-28) also asks for each kind's `why` (one sentence naming the method rule behind its action; soft: missing, empty or over `MAX_WHY` characters is just not kept; stored only, never sent to any prompt) and saves `templateChanges` on the profile (`templateChanges` in `profileCall.ts`: rules that differ from the template it started from, wording not counted; 0 means copied; absent on fallbacks), logged as `[Recovery] Profile from the model: template <t>, rule changes <n>`. On the eval's stored run 6 (2026-10-28, no new calls) Gemini copied its template for 11 of 26 goals; our hand-written answers also copied 10 of those 11, and Gemini changed rules we kept on 4 goals: it adapts, if anything a little more than we did.
5. **One week at a time** (`lib/ai/weekPlan.ts`, `generateWeekPlan`): only week 1 is written at creation, polished and checked by `taskRules.ts` and `scheduleRepair.ts`; `highLoad.ts` marks strain steps. Each later week is written when the week closes (the review or the automatic close; `lib/planV2.ts`, `writeNextWeek`), told what last week was (`lastWeekOf`: sessions done of planned, key sessions skipped, the feel taps on done sessions, every note word for word, the review's reflection) and the pace code picks (`paceOf`, docs/architecture/plan-v2.md). On a load goal (plan-safety-limits M2.1, RULE-4, PSL-8; `loadGoalFor` in `lib/safety/stepLoad.ts`: `isHighLoadGoal`, or the goal's `measure` has a family (`measureTarget` in `lib/planV2.ts`; a goal made before the weekly tests read its stored week target)) both callers pass `loadGoal: { running }`, and the schema and prompt ask for a step `load` (`runMinutes`, `runKm`, `hardRun`, `kcalDeficit`, `kcalIntake`, `percent1RM`, `rir`, `toFailure`, `maxTest`; `parseStepLoad` keeps only finite numbers 0 or more, `percent1RM` at most 100, and real booleans), stored as written in the step JSON (no migration; the app never shows it). A step the model flags `highLoad`, a step of a run kind (`easy_session`, `quality_session`, `long_session`) or the lift kind (`strength_workout`), a strength-template cardio step (`conditioning`, the runs of a custom weight-loss goal), must carry it (the 10-minute version when the day's priority-1 step must); any load that names `runMinutes` or `runKm` must also give `hardRun`. A missing one is a soft retry reason, listed first among the soft reasons, and on the last attempt the step is kept and logged as `[Safety]` `load_missing` / `kept`. Code-made steps (the fallback 10-minute version and `describeDay`'s; a stored code-made test or re-test step on an older week) carry no load; when code changes a step's minutes (`fitStepMinutes`, the 10-minute cap) `load.runMinutes` scales down with them when a step is shortened and never grows when one is made longer (`withMinutes`), `runKm` never. On a load goal `writeNextWeek` also passes `baseWeek` (M2.2a, B-64, `baseWeekOf` in `lib/safety/weekLoad.ts`, from the closing week's rows; on a first week back M2.2b's `firstWeekBackBaseOf`, below), and its week call always gets `goalId`; goal create's week 1 has no base. Any other goal's call is exactly as before (its input only adds `goalId`, which only the log reads).
6. **Safety limits.** Every limit number lives in `lib/safety/limits.ts` (plan-safety-limits RULE-1); the week call (its prompt, its checks) and the text scan read them from there. No weekly tests (ND-33): the safe target climb, the week-12 line and the light-test swap went with the targets; the limits that stay check the sessions themselves. `targetFamily` (`lib/safety/targetSteps.ts`) reads the goal's measure (running distance, running time, lift load, body weight, body fat, calorie deficit) to pick the load goal, and `runLevelOf` raises a week with no base week's longest-run cap to what the starting point says they already run (PSL-19). The week load checks (`lib/safety/weekLoad.ts`, M2.2a/M2.2b): the running total against the base week plus 10% or 10 minutes / 1 km (a first week back against the newest done week, no allowance, half after 21 days away, never below 30 minutes / 5 km), the longest run, at most 2 hard runs, each step's deficit and intake, and in weeks 1 to 3 the lifting caps (kept for an experienced lifter's method, PSL-20). The text scan (`lib/ai/safetyScan.ts`) refuses unsafe wording in any step. A breach is a retry reason; a second fails the week. Every hit is logged as one `[Safety]` line with the goal id.
7. **No fallback plan**: if the roadmap or week 1 can't be written, goal create answers an honest 503 ("Couldn't design your roadmap right now" / "Couldn't write your first week right now. Please try again.") and saves nothing, for certified presets and custom goals alike. An unsafe goal answers 422. No new plan v1 goal is ever created (docs/decisions.md ND-21).
8. **Fixed date** (B-106, `docs/archive/fixed-date/plan.md`): the body may carry `fixedDate` (`YYYY-MM-DD`, optional), checked by `readFixedDate` (a real date after the start date, else 400 before any model call) and stored as `Goal.fixedDate` (that date at 00:00 UTC, null for none). B-109 (`docs/features/fixed-date-plans/plan.md`): `planLengthFor` (`lib/planLength.ts`) works out the plan's weeks from it. With no date, or one 12 weeks away or more, 12 weeks and `targetDate` start + 90 (never after the date, so a date 84 to 89 days away shortens the closing stretch). Closer, the whole weeks before the date (4 to 11), saved as `Goal.totalWeeks` (default 12), with `targetDate` the date itself. Under 4 weeks: 400 `fixed_date_too_close` before any model call. The roadmap call gets `totalWeeks` only for a shorter plan (its prompt names the weeks, the final test week, the ready week, and for a preset says the method text's week numbers are for 12); the week call gets "week n of N", and in the ready week a line asking for a lighter week. Nothing is carried on the server: for a fresh plan or a next plan the app fills the old plan's date in the field (while it is still ahead), so what the person sees is what is saved.

Next plan (`docs/features/next-plan`, NP-1 to NP-10): every goal response carries `journeyResult` (`lib/nextPlan.ts`, `journeyResultOf`: `kind` `number` or `other` from the goal's measure (`measureOf`; an older goal's last number target), the start, the final goal, weeks finished, sessions done and planned) and `previousPlan`. `POST /api/goal/create` with `nextPlan: { fromGoalId, mode: 'keep_going' | 'go_further' | 'fresh', level? }` runs `authorizeNextPlan` (Pro for every goal, 403 `NEXT_PLAN_REQUIRES_PRO`; it replaces the custom-goal check), loads the person's old plan (completed, or active for `fresh`) with its tasks, adds the `measured_level` answer (the level typed and what they did, or for any other goal what they did), passes `measuredStart` so `checkRoadmapAnswer` holds `startingPoint.value` to it, and stores `Goal.roadmap.previousPlan` (`{ goalId, number, mode, summary }`, summary "11 of 12 weeks, 52 of 60 sessions"). A goal measured in a number needs `level` in every mode (400 otherwise): nothing is measured by the plan any more. Not behind any switch.

`goalDecomposer.ts` now only holds the shared plan types (`DailyTaskPlan`, `DetailedStep`, `UserRoutineInput`) and re-exports `clarifyGoalWithAI`. `lib/research/` holds the unsafe-goal screen, stated targets, safety clamps and `formatBasisBadge` (`planGrounding.ts`); there is no live web search, research cache or embedding call.

LLM providers: `lib/ai/gemini.ts` holds the cascade: **Gemini only**, then a miss. Gemini retries busy and rate-limit errors, and retries once without the schema if the API rejects it. There is no fallback provider for now (Groq was removed); a second provider would go in the cascade. `modelJson.ts` repairs and parses model JSON, `retry.ts` gives one retry.

Plan v2 (`lib/planV2.ts`, `ai/weekPlan.ts`, `ai/roadmap.ts`, spec in `docs/architecture/plan-v2.md`): one week written at a time from what the person did (ND-33, no weekly tests). A day can be completed from its own date on (`PATCH /api/goal/tasks/:taskId`, 409 `not_yet` for a day ahead), and a done day can carry `feel` (`too_easy`, `just_right`, `too_hard` or null; 400 on any other value or a task not done; marking it not done clears it; `DailyTask.feel`, migration `20261030120000_task_feel`). The review (`POST /api/goal/weeks/:weekNumber/review`, a reflection only) is accepted from the week's last day on (409 `week_not_over`), both in the person's time zone (ND-24). `POST /api/goal/complete` saves the closing reflection only. Plan v2 is the only plan model (ND-21): every goal is created with `planVersion: 2` and plan v1 code is gone. Endpoints that need a roadmap refuse a goal that is not v2 with `409 not_plan_v2` (weekly review, reconcile and the missed-session actions). Don't add v1 branches back. The `planVersion` column and its default of 1 stay in the schema for now. The goal response (`presentGoal`) never sends a week's `updateStatus`, `target`, `test`, `testResult` or `retestOfWeek`, nor the roadmap's `finalTest`, `checkpoints` or `loweredTargets` (all still stored on older goals, B-111).

Missed sessions (`lib/missedSessions.ts`, `lib/carryForward.ts`, `POST /api/goal/reconcile`): carry-forward writes happen only when `MISSED_SESSIONS_CARRY_ENABLED` is exactly `true`. It is on in production (the notice that explains a moved step shipped in missed sessions M3.1). It is managed in the Render dashboard only (`sync: false` in `render.yaml`, so unset means off) and is the kill switch (ND-15); never turn it on or off from code or tests. In the app (ND-25), Today answers a past day's swap offer itself with the swap call (`components/today/useAutoSwap.ts`), showing the question only if the swap is refused, and a day holding a moved step shows where it came from (`movedHereLine` in `lib/stepLines.ts`).

Method-aware recovery in carry-forward (`lib/recovery/carry.ts`, `planRecovery`, M3.1a to M3.1d): when `METHOD_RECOVERY_ENABLED` is exactly `true` (read per request; `sync: false` in `render.yaml`, so unset means off; on in production since 2026-10-16, O2; managed in the Render dashboard only, and it is this feature's kill switch), a missed day whose steps all have known kinds in a valid profile follows each kind's action (move to the first later day that fits, a `continueFrom` marker for continue, nothing for let go and fixed), and the reconcile body adds `carry.outcomes` (which rules each missed day followed and its outcome), `carry.continues`, `carry.alreadyContinued`, `carry.reorders`, `carry.easyStart` and what was stored (`writtenContinues`, `writtenReorders`, `writtenEasyStart`). A moved hard step skips any day within the profile's rest gap of another hard step (RULE-14, counted over every done or open day of the goal); a hard step that takes the place of a hard step is only checked for sharing that day (MR-29). Steps of an in-order move kind are never lost (RULE-20, MR-30): `recovery/inOrder.ts` (`inOrderQueue`) lists each week's steps of the kind not done yet, in written order, from the stored week, ignoring any step a later week already holds or that is done on any day; for the week holding today and the week before it (older weeks keep the ordinary move rules), the remaining sessions of the kind keep their days and hold that queue in order (`shiftedFrom` marker naming the day the step was written on); a session that cannot take the next step safely gives its own step up, unless it is the day's only step (then the kind waits, `only_step`: a day is never left empty); the steps left over are listed for next week (`toNextWeek` records on the queue's first missed step, `reorders[].toNextWeek`, counted in `weekCounts.toNextWeek`, outcome `next_week`; in week 12 they are `reorders[].leftOut`, outcome `left_out`, and the count is 0). Next week continues from them (M3.1d, MR-32, `recovery/handoff.ts`): with the switch on, `writeNextWeek` reads the finished week (`weekHandoff`), tells the week writer where the person is (`whereTheyAre`, a prompt block), and after the call code places the carried steps in the new week's first sessions of their kind (`placeHandoff`, same fit and rest-gap rules, a `shiftedFrom` marker); what does not fit waits as `toNextWeek` records inside the new week, and a carry or reorder that removes a step holding records moves them onto a step it keeps (`keepRecords`). A day whose priority-1 step code changes gets a matching title, 10-minute version and intention (`recovery/dayText.ts`; `writeRecovery` writes them for reordered days). The review route passes the week before so a break across the week change counts, and each wait is logged (`[Recovery] Handoff wait`). A non-hard moved step that found no room takes next week's first session of its kind when it fits; a hard one is only told. Nothing in the handoff can fail the week call. `writeRecovery` saves every reordered day in one `prisma.$transaction`, all or nothing. After an open gap, the first hard step back gets RULE-21's easy line (on the hard test step when the test day is the first day back; `recovery/easyStart.ts`), and a swap keeps it on that step, once, written in the swap's transaction (B-49, `easyLineAfterSwap`); the warm-up line goes only on physical steps (MR-31). The person's actions follow RULE-16 (M3.2, `recovery/swap.ts`): one pure check (`methodSwapRefusal`, RULE-12 to RULE-14, refusing only a breach the swap creates or a rest-gap closeness it narrows) decides the swap route, the key-session hold (a key session is held only when its priority-1 step moves and that swap passes; a held offer's receiving day never takes a continue marker, the continue is no room) and `carry.choices` (`today`: `taskId`, `setAside`, `swapWith`; `held[]`: `taskId`, `receivingTaskId`, `moveNowTaskId`), listing the same hold as the body's `carry.held`, with the move-now and swap days read from the plan as stored after the run's writes (`planChoices`, `openSwapRefusal`, `moveNowTarget` in `reconcileCore.ts`); with the carry switch off it is `{ today: null, held: [] }`. Swap refuses `fixed_step`, `out_of_order` and `rest_gap` with the switch on, and a day holding a `shiftedFrom` step (`holds_carry`) or a `continueFrom` marker (`holds_continue`; not when the marker's day is done, B-50) in any switch state, and an open swap also refuses a day holding a `carriedFrom` step (`holds_carry`; not when its source day is done and still holds that step, B-52, B-55, MR-37, `isDoneCopy` in `recovery/inOrder.ts`); carry-now refuses `would_not_move` (switch on) when the held main step of a day that follows the new rules would not move; a held day under RULE-18 keeps today's carry-now. With the switch on, the signals add `line` (M3.3, `buildSignals`, MR-35): the one miss line Today and the Dashboard show, chosen on the server from `carry.outcomes` and the stored markers (`carriedFrom`, `shiftedFrom`, `continueFrom`; a done source day names no day, B-50, and a carry from a done day that still holds the step gets no line or `carried` signal in any switch state, B-52, B-55); Today's actions read `carry.choices` instead of working them out. Off, or for a day without kinds, the plan and body are exactly missed sessions' (`planCarries`). Writes still need `MISSED_SESSIONS_CARRY_ENABLED`. Never turn it on from code or tests.

Week close (weekly update M1.2a, `lib/weekClose/`, docs/features/weekly-update): a week closes through one shared save, `saveWeekClose` in `weekClose/close.ts`, by the review (`POST /api/goal/weeks/:n/review`) or automatically (`POST /api/goal/close-week`, behind `WEEK_CLOSE_ENABLED`, read through `weekClose/switch.ts`) once the open week's last day has closed (bedtime plus 2 hours, never after 04:00, in the person's time zone; `weekCloseDue`). Both write the next week first (`writeWeekAfter`: `writeNextWeek` with the closing week's tasks, the review's reflection, the break and the choice), then save in one transaction: the closing week `completed` with `closedBy`, `closedAt` and `executionScore`, its review row (the review's insight is what was done, `reviewInsight`; the automatic close's `AUTO_CLOSE_INSIGHT` "Next week is ready." or the move line, `autoCloseInsight`), the next week's rows and `currentWeek`. A lost race (another close won) saves nothing and answers `week_closed` / `due: false`. A close after a gap moves the plan (`planWeekMove`: the next week starts today, the plan's end moves by the gap, up to 28 days, `movedDays`; days already past are stored not offered). A gap of 7 days or more is a break (`weekClose/breaks.ts`): the next week is a first week back (`firstWeekBackFor`: the days away, the return rule's note and restart level from the profile, the high-load flags), a high-load goal's hard steps take the first-week-back line, and past the 28-day limit the close waits for the person's choice (409 `choice_needed`; "Keep going" jumps weeks, "Do my final week" goes to `PlanShape.finalWeek`). `mode: 'check'` answers whether a close is due, its week, `break` and `choice`, and writes only the first-try marker. `POST /api/goal/weeks/:n/close-line-seen` and `/reflection` record the line dismissed and a reflection typed after an automatic close. The daily-time question (`POST /api/goal/daily-time`, `weekClose/dailyTime.ts`, behind `WEEK_CLOSE_ENABLED`): after two closed weeks in a row under half done (`executionScore` < 50), once per run of hard weeks, never in the last week; a shorter time is read when the next week is written. No weekly update call, test card, re-test, late test or test-result route since 2026-10-30 (ND-33).

Plan length (B-109): every place that read 12 weeks reads the goal's `PlanShape` (`shapeOf(goal)`: `weeks`, `finalWeek` (the last full week, where "Do my final week" goes) and `readyWeek` (a shorter plan's easier last week, null on 12 weeks)). The roadmap and week prompts name a shorter plan's weeks and its ready week; nothing is carried out of the last week; the daily-time question is never asked in it.

Fixed date in the week close (B-106): with `Goal.fixedDate` set and not yet passed on the first try's local date, `planWeekMove` cuts the room to `fixedDateRoom` (`weekClose/breaks.ts`: days from day 90, the day before `targetDate`, to the date, never below 0), so the plan's end never moves past it; what doesn't fit is not offered, or jumped with "Keep going" (the choice card shows sooner). "Do my final week" moves week 12 only as far as the date allows (its passed days not offered) but always keeps today in week 12. A date that has passed holds nothing back. The move carries `dateRoom`, `dateCut` (the date made the move shorter than it would have been) and `finalStartedBefore` (week 12 started before today, so the close saves `FINAL_WEEK_DATE_INSIGHT` instead of "starts today"); `logFixedDate`, on both the review and the automatic close, logs `[WeekClose] goal <id> week <n> fixedDate room <r> moved <d> gap <g>` when `dateCut`. Today's line (`fixedDateLine`) goes once the date has passed in the person's time zone, since the plan can move again then. The app shows the date next to the plan end on Today (`lib/fixedDate.ts`, `fixedDateLine`) and asks for it on the schedule step.

Edit my schedule (B-108, `docs/archive/edit-schedule/plan.md`): `Goal.routine` may hold `restWeekdays` (0 Sunday to 6 Saturday; kept by `readRoutine` only when `validRestWeekdays` says it fits the variant: whole weekdays, no repeats, `7 - activeDaysFor(variant)` of them, two in a row allowed). `weekLayout(variant, weekStart, restWeekdays)` rests on those weekdays, otherwise on the variant's fixed positions from the week's first day; the test is the last practice day either way. The week call (`WeekCallInput.restWeekdays`), `writeNextWeek` and the weekly update's re-test layout read it. Goal create takes `routine.restWeekdays` from onboarding (400 when it doesn't fit). `PATCH /api/goal/schedule` (`routes/goal/schedule.ts`, `readScheduleChange`, `nextRoutine`) changes `planVariant`, `restWeekdays` (null resets), `dailyMinutes` (10 to 480) and `preferredSlot`; rest days not sent stay while they fit the new variant; it saves the routine and the pending weeks' `plannedMinutes` in one transaction, refuses week 12 (409 `last_week`) and, with the week close on, an open week that is over but not yet closed (409 `week_closing`: that close writes next week from the routine it already read), answers `{ routine, startsWeek, startsOn }` and logs `[Schedule] goal <id> from week <n>: <before> -> <after>`. The open week is never rewritten; the next week written follows the change. Every goal response carries `schedule` (`goalScheduleOf`: the variant, minutes, time of day as `slotTimeFor` reads it, and the rest weekdays in force read off `weekLayout`, with `restWeekdaysChosen`). The app: the weekday picker on onboarding's schedule step and "Edit my schedule" in the account menu (`EditScheduleDialog`, which reads `schedule` and sends the rest days only when the person changed them; `lib/schedule.ts` mirrors only the variants' own rest days, for the picker's defaults).

Checkpoints (built 2026-10-24) were removed with the weekly tests on 2026-10-30 (ND-33): no offer at weeks 4 and 8, no `POST /api/goal/checkpoint`. Older goals keep `Goal.roadmap.checkpoints` unread (B-111).

Billing (`lib/billing/`, `config/billing.ts`): Lemon Squeezy, test mode by default, selected by `LEMON_SQUEEZY_ENVIRONMENT` with separate `_TEST_` / `_LIVE_` variables. Custom (non-preset) goals are a Pro entitlement (`goalAuthorization.ts`, `entitlement.ts`). Webhooks are deduplicated through `WebhookEvent`.

Dates use IANA time zones via `lib/timezone.ts`; don't split dates in naive UTC.

Backend is ESM with `NodeNext` resolution, so relative imports need the `.js` extension (`'./routes/goal.js'`).
