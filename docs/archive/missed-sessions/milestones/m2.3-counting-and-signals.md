# Missed Sessions — M2.3 Counting Rules and Signals

**Milestone:** P2 / M2.3
**Date:** 2026-10-07
**Status:** COMPLETE
**Prompt:** docs/archive/missed-sessions/05-prompts.md, M2.3 (commit `9f88a75`)

## 1. Summary

- **OD-2 in the week call.** A key session completed only through the 10-minute version is now reported to the week call as skipped, while it still counts as a done session.
- **Week counts.** A tested, pure `weekCounts` function gives M4.2 the per-week numbers it will need. It is not wired into any route or prompt.
- **Signals.** Plan v2 reconcile responses gain `signals`, derived on every call from the classification, the open gap, the carry plan and the stored `carriedFrom` markers.
  - Only stored moves are ever reported as carried, so with the ND-15 switch off no "moved" notice can appear.
  - At most one `notice` is chosen.
  - On a rest day no miss line is chosen.
- **Unchanged:** nothing new is stored, no copy, no schema change, no frontend change, and no change to carry decisions. `MISSED_SESSIONS_CARRY_ENABLED` stays unset.

## 4. Signals: rules as implemented, and tests

All times below: user timezone UTC, bedtime 23:00, so day D closes at 01:00 UTC on D+1. Week: Mon-Wed practice, Thu rest, Fri practice, Sat test, Sun rest.

| Field | Rule | Tests |
|---|---|---|
| `carried` | Stored carries only (`carry.written` from this request, plus `carry.alreadyCarried` markers), from the missed day's close until the receiving day's close. Each `{ fromDate, fromTaskId, toDate, toTaskId, stepTitle }`. | "a carry written by this request concerns today until its receiving day closes"; "a carry stored by an earlier reconcile is reported from its marker, until the receiving day closes" (still there at 00:59 Wed, gone at 01:00); "a carry that was only planned (switch off) is never reported as moved"; route: "switch on… reported", "race lost… nothing reported". |
| `dropped` | The most recent closed practice day (close instant ≤ now), if it is missed and was dropped: `[{ date, taskId, reason }]`, otherwise `[]`. | "is shown while the dropped day is the most recent closed practice day, then not"; "is not shown before the day after closes…" (00:30 vs 01:00). |
| `swapOffer` | The held key session whose receiving day is classified `planned`: `{ missedTaskId, missedDate, receivingTaskId, receivingDate, offerUntil }`, else null. | "offers a swap while the key session is held, and drops the offer once the receiving day closes" (`swap_unanswered`, offer null). |
| `shortOnTime` | Today's task is an open (`planned`) practice day and its week has 2+ `missed` practice days. | "is false at 1 miss in the week and true at 2…"; "is false on a rest day, and false once today is done". |
| `gentleReturn` | There is an open gap and today's task is the first `planned` practice day dated after the gap: `{ gapLength, firstDate, lastDate }`. | "is set on the first open practice day after a gap, and not the day after once that day is done"; "is not set on the rest day between the gap and the return day". |
| `notice` | `gentle_return` › `swap_offer` › `carried` › `dropped` › null. On a rest day today, only `gentle_return` can be chosen, and it never is, because it needs an open practice day. | "picks gentle_return over a drop from the gap"; "follows gentle_return, swap_offer, carried, dropped when several apply"; "never pick a carried or dropped line on a rest day, and never describe a rest day" (AC-5). |

### Example `signals` objects (generated from the planner)

**`carried`**: Mon missed, carried onto Tue and written by this request; at Tue 10:00.
```json
{ "carried": [{ "fromDate": "2026-09-21", "fromTaskId": "mon", "toDate": "2026-09-22", "toTaskId": "tue", "stepTitle": "mon lead" }],
  "dropped": [], "swapOffer": null, "shortOnTime": false, "gentleReturn": null, "notice": "carried" }
```

**`dropped`**: Mon missed with a high-load lead step; at Tue 10:00.

```json
  "swapOffer": null, "shortOnTime": false, "gentleReturn": null, "notice": "dropped" }
```

**`swap_offer`**: Tue key session missed, Wed open; at Wed 10:00.
```json
{ "carried": [], "dropped": [],
  "swapOffer": { "missedTaskId": "tue", "missedDate": "2026-09-22", "receivingTaskId": "wed", "receivingDate": "2026-09-23", "offerUntil": "2026-09-24T01:00:00.000Z" },
  "shortOnTime": false, "gentleReturn": null, "notice": "swap_offer" }
```

**`gentle_return`**: Mon, Tue, Wed missed (gap of 3), Thu rest; at Fri 10:00.
```json
{ "carried": [], "dropped": [{ "date": "2026-09-23", "taskId": "wed", "reason": "in_gap" }],
  "swapOffer": null, "shortOnTime": true, "gentleReturn": { "gapLength": 3, "firstDate": "2026-09-21", "lastDate": "2026-09-23" },
  "notice": "gentle_return" }
```

**null**: Mon missed, carry only planned (switch off); at Tue 10:00.
```json
{ "carried": [], "dropped": [], "swapOffer": null, "shortOnTime": false, "gentleReturn": null, "notice": null }
```

## 5. Discrepancies and decisions

1. **Rest days (AC-5).** The prompt's rule for `carried` ("concerns today from the missed day's close until its receiving day closes") also covers a rest day between the two, as in Wed missed → Fri with Thu rest. AC-5 says rest days never show a miss message, so on a rest day `notice` is never `carried`, `dropped` or `swap_offer`. The fields keep their data, so nothing is hidden from P3, but P3 should take the line from `notice`. Tested.
2. **"Most recent closed practice day"** is decided by close instant, not date, so in the hours after midnight before yesterday's close, yesterday is still open and an older drop is not shown. This matches the M1.2 classification.
3. **`gentleReturn` and `shortOnTime` can both be true** (a gap of 3 in one week is also 2+ misses). They are independent fields, as the prompt says; P3 decides how the two combine (both point to the 10-minute version).
4. **More than one held key session** cannot happen in a well-formed week (the second's receiving day would be the first's), but if it did, `swapOffer` takes the most recent one.
5. **`keySkipped` in week counts** counts a key session that is `missed` or done only by the 10-minute version. An open (planned) key session is neither done nor skipped, so mid-week counts don't call a future session skipped. `writeNextWeek` runs at week close, where "not completed" and "skipped" are the same.
6. **No other "key done" decider.** `writeNextWeek` (`planV2.ts`) is the only place that judges whether a key session was done. The frontend only shows a "Key session" badge. So the STOP condition did not apply.
7. **Mark-missed timing (for M2.4).** `carried` starts at the missed day's close. A step carried by "mark today missed" (M2.4) would only show from tonight's close under this rule. M2.4 should decide whether that is right or whether marking counts as the close.

## 7. Carry-overs

**P3 (exact fields to render)**, from the plan v2 reconcile response `signals`:
- `notice`: the one line to show, or nothing. `'gentle_return' | 'swap_offer' | 'carried' | 'dropped' | null`.
- For `carried`: `signals.carried[0]` → `stepTitle`, `toDate` (the "[day]" in the copy), `fromDate`.
- For `dropped`: `signals.dropped[0]` → `date`, `reason` (data, not copy; the line must not say "missed").
- For `swap_offer`: `signals.swapOffer` → `missedTaskId`, `missedDate`, `receivingTaskId`, `receivingDate`, `offerUntil` (the swap action is M2.4).
- `signals.shortOnTime`: make the 10-minute version prominent (UX-2). It does not change the line.
- `signals.gentleReturn`: default to the 10-minute version (UX-4, AC-10), with `gapLength`, `firstDate`, `lastDate` available.
- The frontend `ReconcileResult` type needs `carry` and `signals` added in P3; nothing is stored or rendered today.

**M4.2 (week counts)**
- `weekCounts(weekNumber, { tasks, days, carry })` from `backend/src/lib/missedSignals.ts`. `tasks` must include `usedMinimumVersion`, which the reconcile `select` does not load today. `days` comes from `classifyDays`/`buildReconcileResult`, and `carry` is the M2.2 plan (with `written` when relevant).
- Returns `{ practicePlanned, practiceDone, doneByMinimum, keySessions, keyDone, keySkipped, missed, carried, dropped }`.
