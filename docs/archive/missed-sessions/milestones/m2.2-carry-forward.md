## 1. Summary

`POST /api/goal/reconcile` now plans carry-forward for the active plan v2 goal. It decides which missed priority-1 steps move to their fixed receiving day, which are dropped and why, and which key sessions wait for a swap answer. The response reports all of it in a new `carry` field. Writes happen only when `MISSED_SESSIONS_CARRY_ENABLED` is exactly `true`, which is set nowhere: `render.yaml` ships it as `"false"`. With the switch on, each carry is one compare-and-set on the receiving day's `detailedSteps`, so concurrent or repeated calls carry once. No schema change, no migration, no frontend change, no user-facing copy.

## 5. EV-4: one week before and after a miss

The route-test fixture, user timezone UTC, bedtime 23:00, at Tuesday 2026-09-22 10:00 UTC. Every day is 30 minutes: lead 15 (priority 1), second 10 (priority 2), third 5 (priority 3).

Classification: Mon `missed` (closed Tue 01:00), Tue `planned` (today), Wed `planned`.

**Before:**

| Day | Steps (stepNumber · priority · title · min) |
|---|---|
| Mon | 1·1 mon lead 15, 2·2 mon second 10, 3·3 mon third 5 |
| Tue | 1·1 tue lead 15, 2·2 tue second 10, 3·3 tue third 5 |
| Wed | unchanged |

**Planned carry (same with the switch on or off):** Mon → Tue. To fit 15 minutes, the fit rule removes "tue third" (5), which is not enough, then "tue second" (10).

**After, switch on** (one `updateMany` on Tue, `durationMinutes` 30):

| Day | Steps |
|---|---|
| Mon | unchanged; no status or field written (ND-2, ND-14) |
| Tue | 1·1 tue lead 15, 2·2 mon lead 15 with `carriedFrom: { taskId: "mon", date: "2026-09-21", replaced: [tue second, tue third] }` |
| Wed | unchanged |

**After, switch off:** nothing is written; all three days stay as before. The response's `carry.carries` lists the same Mon → Tue move, and `carry.written` is `[]`.

**Next reconcile after the write:** `carries: []`, `drops: []`, `alreadyCarried: [{ fromTaskId: "mon", toTaskId: "tue", … }]`, no write.

## 6. Discrepancies and decisions

1. **ND-12 can't arise in a well-formed week under ND-17.** A receiving day is the next practice day after the missed day that is not the test day. Any practice day between a missed day and its receiving day would itself be the receiving day, so two missed days can share one only if a test day sits between them and a later practice day, and the current week layout always puts the test on the last practice day. The planner still implements ND-12 generally (latest wins, others `lost_to_later_miss`), and the test builds that shape directly with a mid-week test day. In practice, an earlier miss whose receiving day was itself missed is dropped as `receiving_day_closed`, which gives the same result ND-12 wants: the most recent miss carries.
2. **"Nothing crosses a week boundary"** is enforced by looking for the receiving day only within the same `weekNumber`, even when next week's rows already exist (tested).
3. **Order of drop reasons.** When more than one applies, the first in this list wins: `in_gap`, `no_receiving_day`, `lost_to_later_miss`, `no_priority_step`, `high_load`, `receiving_day_done`, `receiving_day_closed` / `swap_unanswered`, `receiving_day_taken`, then held (key sessions), then `receiving_day_closed` (receiving day dated before today), then `does_not_fit`. Every path is still a drop; only the label differs.
4. **Key sessions.** The offer is open while the receiving day is classified `planned`, and `offerUntil` is that day's close instant (`dayCloseInstant`). When the receiving day closes missed, the step is dropped as `swap_unanswered`. If it is done instead, the reason is `receiving_day_done`; if it already holds a carry, `receiving_day_taken`.
5. **Stored test steps have priority 1, not 0.** `checkWeekAnswer` sets the test step to 0 and then `rankSteps` renumbers every step 1…n, so a stored test step is priority 1, as the existing week-plan test asserts. The receiving day is never the test day, so this changes nothing. As a belt-and-braces guard, the fit rule also never removes a step titled "Weekly test: …".
6. **Planned minutes.** The fit rule keeps the new total at or below both the old step total and the day's `durationMinutes`, so neither can grow even if the two ever disagree.
7. **A receiving day with no priority-1 step, or with unranked steps,** is `does_not_fit`. This keeps a carried step from ever becoming a day's priority-1 step, so a carried step is never carried again. Plan v2 steps always have priorities (`rankSteps`), so the STOP condition on missing priorities did not apply.
8. **Extra guard on `status`.** The compare-and-set's `where` also includes the receiving day's `status` as read. If the user completes that day between the read and the write, the carry is not written onto a done day. This is stricter than the prompt's example `where`, not looser.
9. **Other writers of the same rows** (STOP check). `PATCH /tasks/:taskId` never writes `detailedSteps`. Goal create and the v1 paths write new rows only. `saveWeekTasks` (v2 weekly review) deletes and recreates the **next** week's rows; if a week's review were resubmitted during the following week, it would replace that week's rows, including any carry. That cannot corrupt a carry: a reconcile write aimed at a replaced row matches nothing (`count 0`), and a carry written just before is replaced along with the week, by design. Listed here; not a race that needs a code change.
10. **Roadmap wording.** ND-13 describes "one database transaction that re-reads the receiving day". The single conditional `updateMany` the prompt asks for gives the same guarantee in one atomic statement.

## 8. Carry-overs

**M2.3**
- Derive the notices (ND-16) from `carry`: carried (from `carries` and `alreadyCarried`, with `fromDate`/`toDate`), dropped (from `drops`; the reason is data, not copy), and the swap offer (from `held`).
- Short-on-time and gentle-return come from classification and `gap`; nothing new is stored.
- `alreadyCarried` lists moves made by earlier requests; with the switch off it stays empty, because nothing is written.

**M2.4**
- Swap answers a held key session. Until then, held steps end as `swap_unanswered` when their receiving day closes.
- Mark missed should reuse `planCarries` and the same guarded write and switch (ND-14): with today forced to `missed`, the same rules apply.
- Undo is possible from the marker (`carriedFrom.replaced`), but no endpoint exists (out of scope).

**P3 / release**
- With the switch on, a carried step appears on the receiving day as an ordinary step. The frontend ignores `carriedFrom` and `priority` today (`parseSteps`), which is why the switch stays off until M3.1's notice is live (ND-15, section 2.4).
