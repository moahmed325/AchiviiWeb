## 1. Summary

Every plan v2 step written from now on carries a `highLoad` boolean. For custom goals it is the model's answer, normalized so that anything but a real `true` is `false`. For the two physical presets (`run10k` and recomp), code sets it to `true` on every practice step, the test step and the 10-minute version, whatever the model said. One pure reader, `isHighLoadStep(step, goal)` in `backend/src/lib/highLoad.ts`, answers "is this step high-load?" for old and new goals alike. Nothing reads the flag yet and nothing moves. No schema change, no migration, no route change, no frontend change.

## 6. Discrepancies and decisions

1. **The recomp preset's id is `body_recomposition_90day`, not `recomp`.** The prompt lists preset ids by file name. `run10k.ts` has the id `run10k`, but `recomp.ts` has `body_recomposition_90day`. `HIGH_LOAD_PRESET_IDS` uses the real ids, and `highLoad.test.ts` asserts them against `run10kPreset.id` and `recompPreset.id`, so a rename can't silently break the check. No other preset is physical: `book`, `chess`, `deepwork`, `guitar`, `saas`, `spanish`, `speech` and `youtube` were checked by id, title and match patterns.
2. **`minimumVersion` in the model schema.** R2 adds `highLoad` to the step schema "for practice steps". I added it to the `steps` items only and left the separate `minimumVersion` schema unchanged. So for custom goals, the model's 10-minute version normally arrives without a flag and normalizes to `false`. Two cases give it a meaningful value: on physical preset goals it is stamped `true`, and when code derives the 10-minute version from the day's lead step (no `minimumVersion` in the answer) it takes that step's flag. M2.2 carries only priority-1 steps, never the 10-minute version, so this does not affect the drop rule. Open question below.
3. **Rest-day light steps.** R4 stamps practice days only, so on a physical preset goal a rest day's one light step keeps the model's value. `isHighLoadStep` still answers `true` for it, because the goal is high-load. This is tested.
4. **The code-added test step** (`testStepFor`, used only on a last attempt) is `false` for custom goals and `true` on physical preset goals, so every new step carries an explicit boolean.
5. **Preset matching is by goal text, as R4 requires.** The existing matcher has quirks that `isHighLoadGoal` inherits. For example, `run10k`'s `/\b10\s*k\b/` pattern also matches "10k subscribers", and `run10k` is checked first, so such a goal would count as high-load. That is the same preset goal create already picks for it, so the flag stays consistent with the plan, but it is worth knowing for M2.2.

## 7. Carry-overs for M2.2

- **Call `isHighLoadStep(step, goal)`; never read `step.highLoad` directly.** Only the helper covers `run10k` and recomp goals written before M2.1, whose stored steps have no flag.
- The helper needs `rawGoal` and `clarifiedOutcome`; load them with the goal in `POST /reconcile`.
- Custom-goal steps written before M2.1 have no flag and count as normal, as the roadmap says.

## 8. Open questions

- Should the model also flag the 10-minute version (add `highLoad` to the `minimumVersion` schema)? That would be one more schema property and no prompt change. It only matters if a later milestone reads the flag on the 10-minute version.
